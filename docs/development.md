# Development

How to run WebCraft locally, how the code is laid out, how to test it, and the conventions every change follows. Terms follow `GLOSSARY.md`; decisions are in `docs/adr/`.

## Layout

A Bun-workspaces monorepo, scaffolded once with Better-T-Stack (TanStack Start, oRPC, Better Auth, Postgres + Drizzle, Biome, Turborepo) and reshaped to the spec's layout.

| Path | What it is | Runs on |
| --- | --- | --- |
| `apps/server` | The web process. One request handler routes every request by hostname: the admin host to the admin side (the TanStack Start admin, `/healthz`, `/readyz`, the Management API at `/api/rpc`, later `/api/v1`, `/mcp`, OAuth and the Caddy ask endpoint), every other hostname to the Site pipeline. | Bun 1.4 |
| `apps/worker` | The worker: runs pg-boss jobs, including image processing (the only process that loads the image library). | Node LTS |
| `apps/cli` | The `webcraft` command (`webcraft admin migrate`, `rotate-key` and `create-superadmin` for now). | Bun |
| `packages/core` | Domain modules (the permission check and the list of Sensitive actions, the tenant data layer, Workspaces, Sites, Staff, the Audit log, the content store and publishing, the Design system, the Site side of rendering, Edit mode and Code mode, Site script safety (the Content Security Policy, Libraries, outside scripts), the Media library and storage, secrets, setup, people and their own account, Install settings, rate limits, the Master key banner, email, the guarded fetcher, the Module host) and the ports every process shares: `Clock`, `Mailer`, outgoing HTTP, DNS, `Logger`, image processing, job definitions, `InstallServices`. | both |
| `packages/db` | Postgres: Drizzle schema and migrations, connections, the migrate step, the schema check, the pg-boss job queue. | both |
| `packages/auth` | WebCraft's auth interface (`Auth`): signing in and out, sessions, the recent identity check, lockout, creating people, password rules and the leaked-password check. Better Auth sits behind it; no other package imports Better Auth. | both |
| `packages/api` | The Management API: oRPC procedures, served to the admin at `/api/rpc`. | both |
| `packages/mcp` | The MCP server, generated from the API (placeholder). | both |
| `packages/module-sdk` | `@webcraft/module-sdk`, the Module SDK: the one versioned package a Module may import from WebCraft (see "Modules"). | both |
| `modules/*` | First-party Modules, one workspace package each, importing only the Module SDK (none yet). | both |
| `packages/renderer` | Element trees (the stored form of Templates and Components), Placements of Components, Template markup (their lossless text view: parse, check, print), Conditions' expressions, formatters, the rich text cleaner, the Body field's Blocks (their registry, rendering, derived values and Checks), the renderer that turns trees into HTML, and the Design system compiler (tokens, CSS checking, the stylesheet, DTCG files). It reads nothing itself. | both |
| `packages/ui` | shadcn components for the admin (preset `b1Fk3bmIS`) and its theme. | browser |
| `packages/config` | The shared `tsconfig.base.json`. | |
| `tests` | The seam-1 test harness and its tests, and the seam-2 browser harness (`tests/browser`). | Bun |
| `scripts` | `dev.ts`, the licence check and the denylist check. | Bun / sh |

  --addons biome turborepo --examples none --db-setup docker --web-deploy none --server-deploy none \
  --no-git --package-manager bun
```

## Setup

You need Bun 1.4, Node 22.18 or later (CI and the images use the current LTS), and either Docker or a Postgres 18 server you can create databases on.

```sh
bun install
cp .env.example .env     # then set DATABASE_URL (see "Databases" below) and WEBCRAFT_SECRET_KEY
bun run dev
```

Make the Master key for `WEBCRAFT_SECRET_KEY` with `openssl rand -base64 32` (see "Secrets and the Master key").

`bun run dev` does everything in one go:

1. Checks the settings web and worker need, and stops with the reason when one is missing or malformed.
2. Checks that Postgres answers at `DATABASE_URL`. Only when it doesn't, and the host is this machine, it starts `docker-compose.dev.yml` with the user, password and port from `DATABASE_URL`. A server that already answers is never touched.
3. Creates the database named in `DATABASE_URL` if it's missing.
4. Runs the migrate step.
5. Starts the web process (`vite dev` on Bun, port `PORT`) and the worker (Node, restarting when its files change). Ctrl-C stops both.

Open `http://admin.localhost:3000/` for the admin. On a fresh database the web log prints a setup token and a link to the setup wizard (`setupUrl`); open it to create the Superadmin (see "Signing in and the setup wizard"). Every other hostname is a Site; names under `.localhost` reach your machine without DNS changes. With `WEBCRAFT_SITES_DOMAIN=sites.localhost`, a Site with the slug `shop` answers on its Staging address `http://shop.sites.localhost:3000/` (`sites.get` gives it as `stagingUrl`). Vite refuses hostnames outside `.localhost` in development.

Run every command from the repo root: Bun loads `.env` from the directory it runs in.

## Environment variables

| Variable | Used by | Meaning |
| --- | --- | --- |
| `DATABASE_URL` | all | The Install's Postgres database. Tests derive their database names from it. |
| `WEBCRAFT_ADMIN_HOST` | web, worker | The admin's hostname, without scheme or port (`admin.example.com`). Reserved: it never resolves to a Site. |
| `WEBCRAFT_SITES_DOMAIN` | web, worker | Optional. The domain Staging addresses sit under: each Site answers on `<site slug>.<sites domain>` (`sites.example.com` gives `bakery.sites.example.com`; point a wildcard DNS record at the Install). Without it Sites have no Staging address. When the admin host sits right under it (`cms.example.com` under `example.com`), its first label can't be a Site slug. |
| `WEBCRAFT_EDGE` | web, worker | What answers HTTPS for the Install (ADR 0015): `caddy` (the default: Caddy on a VPS, issuing certificates on demand after asking the Install), `coolify` or `railway` (the platform's own proxy; Staff also add each domain in its panel). It decides the steps the Domains screen shows first. |
| `WEBCRAFT_PUBLIC_ADDRESSES` | web, worker | Optional. The Install's public IP addresses, IPv4 and/or IPv6, separated by commas (`203.0.113.10,2001:db8::10`): Site domains point A and AAAA records at them, as the Domains screen shows. Without it, the screen offers only a CNAME record to the admin host. Together with the admin host's own addresses, they are "the Install's addresses" the domain checks compare a domain's DNS with, and the only internal addresses those checks may call (see "Domains"). |
| `PORT` | web | The web process's port (default 3000). |
| `WEBCRAFT_STORAGE_DIR` | web, worker | The folder files are kept in while the Install's storage is local disk (Install settings › Storage): an absolute path, `storage` in the folder the process starts in when unset. Web and worker must share it (a mounted volume on a server); `bun run dev` sets it to the repo's `storage/` (gitignored). |
| `WEBCRAFT_SECRET_KEY` | web, worker, `rotate-key` | The Master key, at least 32 characters (`openssl rand -base64 32`). It encrypts every stored secret. Keep a copy outside the server. |
| `WEBCRAFT_OLD_SECRET_KEY` | `rotate-key` | The Master key being replaced, only while `webcraft admin rotate-key` runs. |
| `WEBCRAFT_DENYLIST` | denylist check | The denylist itself, one pattern per line. CI fills it from the `REFERENCE_DENYLIST` secret. |
| `WEBCRAFT_DENYLIST_FILE` | denylist check | The path of a file holding the denylist, kept outside the repo. |
| `CI` | denylist check | When set, a missing denylist fails the check instead of skipping it. |

Web and worker refuse to start when a setting is missing or malformed (a Master key that is missing or shorter than 32 characters prints the `openssl rand -base64 32` command), when the database is behind (see "Migrations"), and when `WEBCRAFT_SECRET_KEY` isn't the Install's current Master key (see "Secrets and the Master key").

## Databases

Several worktrees and CI jobs share one Postgres server, so names must never collide:

- **Each worktree uses its own database**, named `wc_t<N>` after the ticket it works on (`wc_t48` for #48): `DATABASE_URL=postgres://postgres:webcraft@localhost:55432/wc_t48`. Outside the ticket workflow, any unique name works.
- **Tests never use that database.** Each run creates `<name>_test_<run id>_tpl`, migrates it once with the real migrations, and copies it into a fresh `<name>_test_<run id>_<n>` for every test Install (`CREATE DATABASE ... TEMPLATE`, which is fast). All of them are dropped when the run ends. The run id holds the start time, so a run that was killed leaves databases the next run of the same worktree recognises and drops once they are six hours old.
- Never drop or change a database that doesn't start with your own name.

## How a request flows

`apps/server/src/handler.ts` is the web process: `createWebHandler({ services, adminApp })` returns a plain `(Request) => Promise<Response>`.

- **Admin host** (`apps/server/src/admin/side.ts`): the web process answers its own paths first (`/healthz`, `/readyz`, Caddy's ask at `/caddy/ask` (see "Domains"), the Management API at `/api/rpc`, Media previews at `/api/media/<site id>/<name>`; add `/api/v1`, `/mcp` and the rest there), then hands the request to the admin app. In production the admin's built files are served from `apps/server/dist/client` here too, so Sites never expose them.
- **`/api/rpc`** is the Management API as the admin's own pages call it: every procedure in `packages/api/src/router.ts`, over oRPC's RPC protocol, signed in with the session cookie. A request another site's page makes (by its `Origin` or `Sec-Fetch-Site` header) is refused with 403, so no other site can act with a signed-in person's cookie. Procedures get `{ services, headers, resHeaders, via }`; start them from `procedure`, `signedIn` or `onInstall(permission)` in `packages/api/src/context.ts` (see "Writing a procedure"), and throw WebCraft's own errors: `packages/api/src/errors.ts` turns them into API error codes, which the admin translates.
- **Every other hostname** (`apps/server/src/site/pipeline.ts`): the Site pipeline (see "The Site pipeline and the page cache"). A hostname that is no Site's gets the unbranded 404 (`Not Found`, plain text), and nothing on a Site hostname ever reaches the admin. Anything a Site visitor sees must stay unbranded: use `plainText`, `notFound` and `json` from `apps/server/src/responses.ts`.
- **The client address** of a request comes from one function, `clientAddress(request, config)` in `apps/server/src/client-address.ts`: for now the address of the connection itself (`serve.ts` sets it from Bun's server, the development server sets it the same way). Rate limits, lockout records and the sessions list take it from there and nowhere else; `X-Forwarded-For` and similar headers are ignored until trusted proxies (`WEBCRAFT_TRUSTED_PROXIES`) are added, which changes only that function. Procedures get it as `context.clientAddress` (null when the web process can't tell).
- `/healthz` answers 200 while the process is up. `/readyz` answers 200 when the database is reachable and has had every migration this version expects, 503 otherwise. Both answer only on the admin host; container health checks must send `Host: <admin host>`.
- `apps/server/src/server.ts` is the TanStack Start server entry: it builds the services and wraps the admin renderer in the hostname router. `vite dev` runs it in development; `vite build` bundles it into `dist/server/server.js`, which `apps/server/src/serve.ts` serves with `Bun.serve` in production. Tests call `createWebHandler` directly, without the admin app.

## Tenancy and permissions

An Install holds Workspaces (one per client), and each Workspace holds Sites. The Superadmin and Staff hold an Install-level role; Members hold a Membership in a Workspace (ADR 0001). Every procedure checks a Permission with `can()`, and every query on tenant data goes through the data layer (ADRs 0007, 0028).

### Permissions and roles

`packages/core/src/permissions/`:

- **`PERMISSIONS`** (`roles.ts`) names every Permission and the levels it is checked at: the Install, a Workspace or a Site (`entry.publish` is checked on a Site, `site.create` on a Workspace, `workspace.create` on the Install).
- **`ROLES`** is the role table: each built-in role (`superadmin`, `staff`, `owner`, `editor`, `author`) is a Permission set, plus what it reaches: the whole Install, the Workspaces its holder is assigned to (Staff), or one Workspace and the Sites its Membership names (Members). Roles are stored as text keys (`install_roles.role`, `memberships.role`); an unknown key grants nothing. Which Workspaces Staff reach (`install_roles.all_workspaces`, `staff_workspaces`) and which Sites a Membership reaches (`memberships.all_sites`, `membership_sites`) are kept apart from the role.
- **`can(actor, permission, resource)`** answers whether an actor may do something; `permissionsOn(actor, resource)` lists what they may do there (the admin reads these lists to decide what to show). Actors are people (`PersonActor`) and Modules acting by themselves (`ModuleActor`: in one Site or Workspace where they run, holding `site.view`/`workspace.view` there and the Permissions they add; see "Modules"); API tokens and OAuth grants become more kinds of `Actor`, each limited by what stands behind it. Code that only a person may do (confirming, writing a value that records its writer) takes `actingPerson(actor)`, which refuses any other kind. A Permission a Module adds is passed to `can()` as an `AddedPermission` (its key, level and the built-in roles holding it).
- **Media**: `media.upload` uploads to a Site's Media library and changes your own uploads (every role on a Site it reaches); `media.manage` changes every file and the folders (Staff, Owners and Editors, not Authors). Seeing the library needs only `site.view`.
- **Adding a Permission**: add it to `PERMISSIONS` with its level, add it to the roles that hold it, and change the role's row in `tests/permissions/roles.test.ts` (one test per role). Never check a role name in code: check a Permission.
- **Nobody grants more than they hold**: `holdsAccess(actor, workspaceId, { role, sites })` answers whether an actor holds at least the access a Membership gives: every Permission of the role on the Workspace, and on every Site it reaches (`"all"` means every Site, including later ones, so only someone reaching every Site holds it). Inviting a Member or changing a Member's access needs it for the new access; changing or removing a Member, or resending or revoking their invite, needs it for the access they have now. It compares Permission sets, never role names.
- Staff never hold a Membership: a Staff invite refuses an address someone already signs in with, a Member invite refuses Staff and the Superadmin, and `services.memberships.add` refuses Staff, the Superadmin and a second Membership in the same Workspace.

### The tenant data layer

`services.data` (`packages/core/src/tenancy/data-layer.ts`) is the only way to tenant data. It opens a scope after checking the Permission, and a scope's queries are limited to its Workspace (and Site):

```ts
const site = await services.data.site(access, siteId, "entry.publish"); // can() runs here
const drafts = await site.select(entries, eq(entries.status, "draft")); // only this Site's rows
const entry = await site.insert(entries, { title, createdAt: site.now() }); // fills workspace_id and site_id
await site.audit("entry.publish", { entryId: entry.id }); // who, when, how, Workspace and Site filled in
```

- `services.data.install(access, permission)`, `.workspace(access, workspaceId, permission)` and `.site(access, siteId, permission)` open the three levels. A Workspace or Site the actor can't see answers `WorkspaceNotFoundError` / `SiteNotFoundError` (404), one they see without the Permission `PermissionDeniedError` (403), so nobody learns what exists outside their reach.
- A Workspace scope works on **Workspace tables** (a `workspace_id` column); a Site scope on **Site tables** (both `workspace_id` and `site_id`, with a composite foreign key to `sites (workspace_id, id)` so a row can never point at another Workspace's Site). Module tables follow the same rule. A Workspace table may also name one of its Workspace's Sites (`membership_sites`, `invite_sites`): a Workspace scope's `insert` fills in only `workspace_id`, and the same composite foreign key keeps the Site in the Workspace.
- Scope queries: `select(table, where?, { orderBy, limit })`, `first`, `count`, `insert`, `update(table, set, where?)`, `delete`. For a join, a lock (`.for("update")`) or anything else, run your own query on `scope.db` (the scope's transaction inside `scope.transaction`) and include `scope.where(table, extra?)`: every query on a tenant table must carry it. `scope.transaction(work)` runs queries and Audit log entries together.
- **Visitors** have no person behind them: `services.data.visitors(site)` opens a Site read-only (`select`, `first`, `count`, `where`, `db`), with no Audit log and no secrets. Only the Site pipeline opens one, after finding the Site by hostname, and code reading through it reads only what any visitor may see (published content).
- **Background work** has no person behind it either: `services.data.background(siteId)` opens a Site for WebCraft's own work in a job (the worker cleaning an upload), with the queries of a Site scope, no `can()`, no Audit log and no secrets; null when the Site is gone. Only jobs open one, for the Site named in a payload that a checked procedure queued.
- `scope.secrets` holds the Workspace's or Site's secrets (`set(name, value)`, `useWith`, `describe`, `remove`); `services.secrets` holds only the Install's own.
- The Install scope's `db` is for Install-level tables (Workspaces, Staff, invites); a domain function takes the scope it needs as its first argument, such as `createSite(workspace, input)`.

### Writing a procedure

A procedure validates its input with Zod, opens the data layer with the Permission it needs, and calls a domain function that takes the scope:

```ts
create: signedIn
	.input(z.object({ workspaceId: id, name: z.string().trim().min(1).max(100), slug: z.string().max(100) }))
	.handler(async ({ context, input }) => {
		const workspace = await context.services.data.workspace(context.access, input.workspaceId, "site.create");
		return { site: await context.services.sites.create(workspace, input) };
	}),
```

- `signedIn` gives `context.access`: the person as `can()` sees them (read fresh on every request, so a change to someone's access takes effect at once) and `via`, how the call came in. Install-level procedures start from `onInstall("staff.manage")`, which gives `context.install`.
- A Site procedure takes `siteId` only: the data layer finds its Workspace.
- Every procedure here is internal to the admin; `/api/v1` and the public ones come later.
- Add one isolation line for it (below) when it takes a `workspaceId` or `siteId`.
- A Sensitive action adds `.use(sensitive("<action>"))` after its permission check (see "Sensitive actions" below).
- A procedure that checks a password, a setup token or an invite link starts from `authEndpoint` (or adds `.use(rateLimited("auth"))`): it is rate-limited per client address.

### Sensitive actions

A Sensitive action (`GLOSSARY.md`) needs a password, passkey or 2FA check within the last 10 minutes, in the admin session the request comes with, and is never available to API tokens or OAuth grants (ADR 0030).

- **The list** is `SENSITIVE_ACTIONS` in `packages/core/src/permissions/sensitive.ts`, one place for every Sensitive action with the reason it is one. So far: `installSmtp.change`, `staff.invite`, `staff.changeWorkspaces`, `member.invite`, `member.changeAccess`, `member.remove`, `masterKey.confirmStored`, `password.change`, `leakedPasswordCheck.change`, `storage.change` and `module.approve`.
- **The gate** is the `sensitive(action)` middleware (`packages/api/src/context.ts`), which calls `assertSensitiveActionAllowed(access, action, now)` from core. Put it after the permission check, so nobody is asked to confirm something they may not do:

  ```ts
  invite: onInstall("staff.manage").use(sensitive("staff.invite")).input(…).handler(…),
  ```

  It answers `IDENTITY_CHECK_REQUIRED` (403, `data.action`) when the session's last check is older than 10 minutes, and `SENSITIVE_ACTION_REFUSED` (403) for anything that isn't a person's admin session: only `signedIn` gives `access.identityCheckedAt`, so later actor kinds (API tokens, OAuth grants, Modules) are refused without a change here. Its type needs `context.access`, so it can't be put on a procedure that has no signed-in person.
- **The check**: signing in counts as one; `session.confirmIdentity({ password })` makes a fresh one for this browser's session only (wrong passwords count towards lockout). Later sign-in factors (passkeys, 2FA) add their own ways to confirm in `@webcraft/auth`, recording the check the same way.
- **In the admin**, run the call through `useSensitiveAction()` (`apps/server/src/ui/identity-check.tsx`): on `IDENTITY_CHECK_REQUIRED` it opens "Confirm it's you", then tries the call again; closing the dialog rejects with `IDENTITY_CHECK_CANCELLED`, which `errorMessage` shows like any refusal.

  ```ts
  const runSensitive = useSensitiveAction();
  await runSensitive(() => api.staff.invite({ email, workspaces }));
  ```

- **Adding one** (member invites and role changes, 2FA changes, Impersonation, API tokens, deleting a Site or Workspace, a Site's secrets): add it to `SENSITIVE_ACTIONS`, mark its procedure with `sensitive("<action>")`, wrap the admin's call in `useSensitiveAction`, and add its row to `tests/auth/sensitive-actions.test.ts`: one call that takes the action as the Superadmin. That file checks each row is refused without a recent check and allowed after one, and its last test fails while an action in the list has no row. The MCP server and the CLI leave Sensitive procedures out.

### The Audit log

The Audit log is one append-only table (`audit_log`; triggers refuse updates and truncation). `recordAudit` (`packages/core/src/audit.ts`) is the only function that writes it; code calls it through `scope.audit(action, details)`, which fills in who, when, how (`via`), the Workspace and the Site. An Install scope's `audit` takes the Workspace (and Site) the action concerns as a third argument, a Workspace scope's the Site.

- **Actions** are `<noun>.<verb>`: `install.claim`, `superadmin.create`, `masterKey.confirmStored`, `workspace.create`, `site.create`, `staff.invite`, `staff.revokeInvite`, `staff.join`, `staff.changeWorkspaces`, `member.invite`, `member.resendInvite`, `member.revokeInvite`, `member.join`, `member.changeRole`, `member.changeSites`, `member.remove`, `postType.create`, `postType.update`, `entry.publish`, `entry.delete`, `template.publish`, `designSystem.publish`, `globals.update`, `globals.publish`, `homePage.change`, `notFoundPage.change`, `language.add`, `language.update`, `language.remove`, `domain.add`, `domain.remove`, `domain.makePrimary`, `defaultLanguage.change`, `browserLanguageRedirect.change`, `installSmtp.change`, `leakedPasswordCheck.change`, `storage.change`, `media.upload`, `media.update`, `mediaFolder.create`, `mediaFolder.rename`, `mediaFolder.delete`, `component.create`, `component.rename`, `component.publish`, `component.delete`, `script.publish`, `csp.change`, `allowedHost.add`, `allowedHost.remove`, `outsideScript.add`, `outsideScript.update`, `outsideScript.remove`, `library.add`, `library.update`, `library.remove`, `editMode.start`, `password.change`, `session.revoke`, `session.revokeOthers`, `account.lock`, `module.approve`, `module.withdraw`, `module.switchOn`, `module.switchOff` and `module.removeData`; a Module's own actions are named under its id (`sample.note.add`). Saving a Draft isn't logged; publishing and deleting are. Install-level actions about a person's own account (their password, their sessions) are recorded with the core function `recordAudit` and no Workspace; `account.lock` has no person who acted (WebCraft locked it) and names the locked person in its details.
- **How** (`AuditVia`): `admin` for `/api/rpc`, `command` with the command's name for `webcraft admin …`, `editMode` for requests from a page in Edit mode (see "Edit mode"), `module` with the Module's id when a Module acts by itself (a job, an event, a Site route; no person). A person calling a Module's procedure is recorded `admin`, with the Module's action name. Later kinds: an API token's name, an AI client's name, Impersonation.
- **After the commit**: the data layer hands every entry a scope writes to `afterAudit` once it is saved (when the scope's outermost transaction commits; never when it rolls back). The Module host turns some into Modules' events.
- **Details** are plain JSON about what changed (a name, an email address); never a secret's value.
- `audit.list` gives the Superadmin the newest entries; the screens and the Staff and Owner views come with the Audit log screens.

### Staff and invites

The Superadmin invites Staff by email (`staff.invite`), to all Workspaces (including later ones) or chosen ones. The invite is the `staff-invite` System email (see "Email"), in the Install's default Admin language, with a link to `/invite?token=…` that works once, for 7 days; only the token's hash is stored. Inviting the same address again replaces the invite. Accepting creates the account with the role and its Workspaces, records `staff.join`, and signs the person in.

### Members and invites

Members are the client's people in one Workspace (`packages/core/src/tenancy/members.ts`, procedures in `packages/api/src/procedures/members.ts`). Each holds one Membership: a Workspace role (`owner`, `editor`, `author`) and every Site of the Workspace or chosen ones. One person has one account, with at most one Membership per Workspace.

- **Permissions**: `member.invite` invites Members and resends or revokes their invites; `member.manage` opens the Members screen, changes a Member's role and Sites, and removes them. Staff and Owners hold both; Editors and Authors neither. Within those, `holdsAccess` (above) limits what each person may give or touch: an Owner reaching some Sites offers only those Sites, never "All Sites", and can't change or remove a Member who reaches more.
- **Inviting** (`members.invite`): the invite is a row in `invites` with the Workspace (`workspace_id`), the role, and `all_sites` or the Sites in `invite_sites`. It is the `member-invite` System email, in the person's Admin language when the address already has an account (the Install's default otherwise), with the same one-time, 7-day `/invite?token=…` link as Staff invites. Inviting the address again into the same Workspace replaces the invite; `members.resendInvite` sends a new link valid for 7 more days, and the earlier link stops working.
- **Accepting**: `invites.get` says whether the address already has an account. Without one, `invites.accept` creates it (password rules as everywhere) with the Membership and signs the person in; with one, the person signs in with that address and `invites.join` adds the Membership. Both record `member.join`. A Member invite to Staff or the Superadmin, or to a Member of the Workspace, is refused when it is sent.
- **Changing and removing** (`members.changeAccess`, `members.remove`): the change is read on the Member's next request, like every change to someone's access (`signedIn` loads the actor fresh), so sessions already open lose access at once. Removing keeps the person's account and their Memberships elsewhere. Role and Site changes are recorded as `member.changeRole` and `member.changeSites`, with the old and new values.
- **The Members list** (`members.list`) names only the Sites the viewer can see (`otherSites` counts the rest), lists the Staff assigned to the Workspace (read-only: the Superadmin manages Staff), and gives `offer`: which roles the viewer may grant, and on which Sites.

## Content and publishing

The content store is `packages/core/src/content/`, behind `services.postTypes`, `services.entries`, `services.globals`, `services.templates`, `services.components`, `services.scripts`, `services.pages` and `services.publishing`. Its tables (`post_types`, `entries`, `published_slugs`, `entry_links`, `globals`, `templates`, `components`, `scripts`, `special_pages`) are Site tables.

- **Post Types** are Structure without a Draft: `create`, `update`, `list`, `get`. Each has a `key` (`blog`, made from the name when not given; it never changes), a `name`, a URL pattern and its Fields, in order. Changing one applies at once and clears the Site's page cache. Every Site also has the built-in **Page Post Type** (`builtIn: "page"`, see "Pages"); Staff made the rest (`builtIn: null`).
- **URL patterns** (`content/url-patterns.ts`) are fixed path parts (lower-case letters, digits, dashes) and exactly one `{slug}`: `/blog/{slug}`, `/{slug}`. When several patterns match a path, the most specific is tried first (a fixed part beats `{slug}` at the first place they differ). A pattern **owns** every path it matches (`/blog/{slug}` owns `/blog/<anything>`, not `/blog` itself), and Pages live outside every pattern, so a path never belongs to both: publishing a Page (or moving one) onto a path a pattern owns, and creating or changing a pattern that would own a published Page's path, are refused with `PATH_TAKEN` (409, `data: { path, by }`, `by` naming the Post Type or the Page). The Site pipeline tries the patterns first, then Pages.
- **Built-in Fields** every Entry has: `title`, `slug` (both translatable, stored like Fields), `status`, `author`, `createdAt`, `updatedAt` (Draft saved), `publishedAt` (first publish) and `lastPublishedAt`. A Post Type lists them as `builtInFields`.
- **Entries** keep two versions side by side in `entries.draft` and `entries.published` (null until the first publish). `status` is worked out: `draft` (never published), `published`, `changed` (the Draft differs). Each Entry the API answers also carries `problems` (what keeps its Draft from being published, see "Values and validation") and `linkedFrom` (see "Relationships").
- **The Draft is written in one place**: `changeDraft` in `content/entries.ts`, which `entries.create`, `entries.saveDraft`, deleting a linked Entry and `undoDraftChanges` (putting values back as they are published, for Edit mode's Publish menu) go through, with the Entry row locked. Co-editing (#71, ADR 0025) replaces it with changes to the Draft's shared document; nothing else writes `entries.draft`. The Globals' Draft is written only by `saveGlobalsDraft` and `undoGlobalsChanges` in `content/globals.ts`. Edit mode saves through the same functions as the admin.
- **Slugs**: made from the title when not given (accents dropped, `crème brûlée` gives `creme-brulee`), unique within the Post Type (`-2`, `-3`, …; for a Page, among the Pages under the same parent), and never changed by a new title, before or after publishing. A slug another Entry of the Post Type has, in its Draft or published, is refused (`ENTRY_SLUG_TAKEN`). `published_slugs` holds each Entry's published slug per language (and a Page's published parent), so the Site finds an Entry by URL with one indexed lookup.
- **Paths**: every Entry the API answers carries `path`, where visitors find it once published (`/blog/fresh-bread`, `/about/team`, `/` for the home page), null before.
- **Templates** (`content/templates.ts`) are `templates` rows holding element trees in `draft` and `published`, of two kinds so far: the **Site template** (`site`, one per Site, see "The Site template") and **Entry templates** (`entry`, one per Post Type). Saves and publishes check a tree against what its kind may hold (`TemplateTarget`, `rulesFor`). An Entry template may read the built-in Fields, the Post Type's Fields and their parts, and the Globals (see "What a binding reads"), and holds neither `<main>` nor `{{@outlet}}` (both belong to the Site template around it). The Page Post Type has no Entry template (`PAGES_HAVE_NO_ENTRY_TEMPLATE`): Pages are arranged with a Page layout. Archive templates become another kind.

### The Site template

Each Site has one Site template (Structure, `structure.edit`), which wraps every page: its header, its footer and, in between, the page's content at `{{@outlet}}`. Until the Site publishes one, every page gets the plain built-in one (`BUILT_IN_SITE_TEMPLATE`: `<main>{{@outlet}}</main>`).

- **What it holds** (`checkSiteTemplate`, `packages/renderer/src/page-structure.ts`): exactly one `<main>`, with only `<div>` elements around it (so it stays a landmark of its own) and no Template command (every page has it), without an `id` or `tabindex` (WebCraft writes those); inside it exactly one `{{@outlet}}`, not inside a Template command either (every page shows its content once). Each problem is reported where its node is (line and column in markup, `nodes[0].children[1]` in a tree).
- **What it reads**: the Globals as `site.x` (it wraps every page, the 404 page too, so no Entry's values). It is checked again on publish, since a Global it reads may have gone.
- **API**: `templates.getSiteTemplate`, `saveSiteTemplate` (a tree), `getSiteTemplateMarkup`, `saveSiteTemplateMarkup` (Template markup), each taking `siteId` and answering as their Entry template counterparts do; `templates.publish` publishes it. In core, `services.templates.siteTemplate`, `saveSiteTemplate`, `siteTemplateMarkup`, `saveSiteTemplateMarkup`.

### Pages

Pages (`content/pages.ts`) are the Entries of the built-in Page Post Type, which every Site gets when it is made (`addPagePostType`; a custom migration gave Sites made earlier theirs). Its key is `page`, its URL pattern is `/{path}` (not one Staff can write: a Page's path is its parent's path and its own slug) and it can't change; its name and Fields can. Its built-in Fields add `parent` (`PAGE_BUILT_IN_FIELDS`), a key its own Fields can't take.

- **Nesting**: `entries.create` and `entries.saveDraft` take `parentId` (null for the top level; only Pages have one). The parent is stored in each version beside `title` and `slug`, as one value shared by every language (`parentIn`, `withParent`), and shows as `parentId` in the Entry's Draft and published values. It must be another Page of the Site, never the Page itself or a Page under it, at most `MAX_PAGE_DEPTH` (10) deep (`ENTRY_INVALID` at `parentId`).
- **Publishing** moves a Page, with every Page under it: its published path becomes its published parent's path and its slug. The parent must be published (`PAGE_PARENT_UNPUBLISHED`, 409), the published Pages can't loop, the Pages under it still nest at most 10 deep, and no path may be one a URL pattern owns (`PATH_TAKEN`). A Draft move changes nothing visitors see.
- **Finding one**: the Site pipeline walks the path one part at a time through `published_slugs` (`findPublishedPage`).
- **Rendering**: a Page's content is its Page layout, the Components placed in its content area (#63, #75); until then it is empty, and a Page shows its title and the Site template around an empty `<main>`.
- **Deleting** a Page with Pages under it, in their Drafts or published, is refused (`PAGE_HAS_CHILDREN`, 409, `data.children`).
- **The home page and the 404 page** (`content/special-pages.ts`, table `special_pages`, one row per job): Staff choose them with `pages.setHomePage` and `pages.setNotFoundPage` (`structure.edit`; `pageId` null for none; anything but a Page of the Site is `PAGE_NOT_FOUND`); everyone who sees the Site reads them with `pages.settings`. A change applies at once (it clears the page cache) and is logged as `homePage.change` or `notFoundPage.change`. A Page that isn't published yet can be chosen and shows once it is. The home page answers at `/`, and its own path redirects there (301). Deleting a chosen Page gives its job up. A 404 page may also be chosen for one language (`pages.setNotFoundPage({ siteId, pageId, language })`, rows with `special_pages.language`; `settings` answers them as `languageNotFoundPages`): it answers there, and the Site's own answers in the languages without one. Rollback caveat (ADR 0031): the migration that added `special_pages.language` replaced the table's `(site_id, role)` primary key, so a release from before languages, reading one row per job without a language, may pick a language's 404 page once one is chosen. The home page has one row for every language and answers at each language's root (`/fr`); its own path in a language redirects there.

### Field types

Every Field type lives in one registry, `FIELD_TYPE_SPECS` in `content/field-types.ts`: each type reads its own settings, checks and reads its values, and lists the rules a value breaks. Its name, traits (translatable by default, can be required, can have a default) and the limits Fields keep are in `content/field-rules.ts`, which imports nothing so the admin's browser code reads it too (`@webcraft/core/field-rules`, with `VALUE_RULES`, the rule codes a value's problems carry, and `SETTING_RULES`, the codes a refused setting of a Post Type, a Field or the Globals carries, with `params` to fill in its wording; every settings check names one, through the `Report` it is given, and keeps an English `message` for API clients). Add a type in both, and its control and settings in the admin (see "The admin"); `content/fields.ts` checks definitions and `content/field-values.ts` walks values, both through the registry. A type's value spec can place a refusal or a broken rule inside a value (`within`, such as a Block: `fields.body[2].url`) and name what a stored value points at (`references`), which is checked whenever the version is.

Every Field is `{ key, label, type, help, required, translatable, default }` plus its type's settings (the API answers every setting, null when unset):

| Type | Value (as the API gives it) | Settings |
| --- | --- | --- |
| `text` | text, trimmed (at most 2,000 characters) | `minLength`, `maxLength`, `pattern` |
| `richText` | HTML, cleaned on save (see "Rich text") | `maxLength` (characters of text) |
| `body` | a list of Blocks (see "The Body field") | `blocksOff` (Block types switched off) |
| `number` | a number | `min`, `max`, `integer` |
| `boolean` | `true` or `false` (unset reads `false`; can't be required) | |
| `date` | `2026-03-02`, `09:30` or `2026-03-02T09:30:00Z` (an offset is turned into UTC) | `mode` (`date`, `time`, `dateTime`), `min`, `max` |
| `select` | an option's value, or a list of them | `options` (`{ value, label }`), `multiple`, `min`, `max` (with `multiple`) |
| `media` | the id of a file in the Site's Media library | |
| `link` | `{ url, text }`; the URL is an http, https, mailto or tel address, a path or an `#anchor` | |
| `email` | an address, in lower case | `pattern` |
| `relationship` | an Entry id, or a list of them | `postTypes` (keys), `multiple`, `twoWay` (default `true`), `min`, `max` (with `multiple`) |
| `group` | its Fields' values, by key | `fields` |
| `repeater` | a list of rows, each `{ id, …its Fields' values }` | `fields`, `min`, `max` (rows) |

- **Keys** start with a lower-case letter, then letters, digits and underscores, and never change, so values and bindings follow them. A Post Type's Field can't take a built-in Field's name, one Template markup reads from (`site`, `props`, `item`, `url`, …) or a word Conditions use (`and`, `or`, `not`, `true`, `false`); inside a Group or Repeater only `id` and those words are kept. A Field keeps its type, inside Groups and Repeaters too.
- **Groups and Repeaters** nest 3 deep at most, with at most 200 Fields in all. They hold no language and can't be translatable themselves: their Fields are, one by one.
- **Translatable**: text, rich text, Body and link Fields are by default; number, true/false, date, select, media and email only when chosen; Relationships, Groups and Repeaters never (ADR 0003).
- **Defaults** fill a new Entry's Fields (and a new Repeater row's), and a Global added with one starts the Globals' Draft with it. Fields added to a Post Type later don't change existing Entries. Body, Media, Relationship, Group and Repeater Fields have none (a Group's Fields have their own). A default must keep its Field's rules.
- **`pattern`** is a regular expression the whole value must match, as an HTML `pattern` attribute reads it (so the admin can use it as is). Patterns are Staff's input and run on every save, list and publish, so they run on a linear-time engine (RE2, through `re2js`): no pattern can keep the web process busy, whatever its shape (`(a+)+b` is as quick as `[a-z]+`). The engine has no look-around and no back-references, so patterns using them are refused when the Field is defined.

### Values and validation

Values are stored per key and per language, inside each version (ADR 0003): a leaf Field's values as `{ <language>: { value, by } }`, where `by` is who wrote it (a person; AI translation joins later); a Group's as `{ values: { … } }`; a Repeater's as `{ rows: [{ id, values: { … } }] }`, so rows are the same in every language and each Field in them falls back to the Default language one at a time. A shared Field keeps one value under the Default language. Values are written and read in any of the Site's languages (`language` on `create`, `saveDraft`, `get`, `list`, `globals.*`, `media.*`; a language the Site doesn't have is `ENTRY_INVALID` / `GLOBALS_INVALID` / `MEDIA_INVALID` at `language`); see "Languages".

- **Saving** (`create`, `saveDraft`, `globals.saveDraft`) gives Fields by key; only those given change. A Group's value is its Fields by key (again only those given change; `null` clears them all); a Repeater's is its whole list of rows: a row with an `id` it had keeps that row and its values in other languages, changing what is given; a row without one (or with a new one) is new and starts with the defaults; rows left out are removed. `null` or `""` clears a value.
- **The wrong kind of value is refused** with `ENTRY_INVALID` (`GLOBALS_INVALID`) and `data.problems`, each at its path: `fields.price`, `fields.address.city`, `fields.team[1].name`, `fields.team[1].id`. A Relationship pointing at an Entry that isn't one of its Post Types' on this Site is refused the same way.
- **Broken rules and empty required values are kept** in the Draft, so autosave and Co-editing never lose what someone typed, and are listed in the Entry's (or the Globals') `problems`, each with its `rule` (`required`, `min`, `max`, `minLength`, `maxLength`, `pattern`, `integer`, `email`, `options`, `url`, `postTypes`, `media`, `blockType`, `video`) for the admin to word. `min` rules only apply to values that aren't empty; empty is `required`'s job. A required Group needs a value in one of its Fields; the required Fields of an optional Group count once it has a value; a required Repeater needs a row.
- **Publishing checks every value again** (Fields' rules may have changed since): `ENTRY_INVALID` with the same `problems` when a rule is broken, else `ENTRY_INCOMPLETE` with `data.missing` (`["title", "price", "address.city", "team[0].name"]`) when required values are empty. The Globals answer `GLOBALS_INVALID` and `GLOBALS_INCOMPLETE`.

### The Body field

A Body field (ADR 0018, `GLOSSARY.md`) holds long-form text as a JSON list of typed **Blocks** with stable ids, never HTML or Markdown. A Post Type has at most one, among its own Fields (not inside a Group or Repeater), so "the body" is never ambiguous; the Page Post Type (Pages have Page layouts), the Globals and Components' Props have none (`owner` in `DefineContext`: `page` for the Page Post Type). It is translatable by default: each language keeps its own Block list, stored like any leaf value (`{ <language>: { value: [Blocks], by } }`).

- **The Block-type registry** is `BLOCK_TYPE_SPECS` in `packages/renderer/src/body/blocks.ts`: for each type, the settings it holds and how they are read into the canonical form, its formatted text and plain text (for excerpts, reading time and translation), whether it shows anything, and its HTML. The renderer, the admin's block editor (`@webcraft/renderer/body`, which runs in the browser) and the Checks all read it. Module Block types (#110) and Components in a body (#79) join it.
- **Blocks** (each `{ id, type, …its settings }`, and on a translation `source`: `{ id, by: "person" | "ai" }`, the Block it translates and who wrote it, kept for #80 and AI translation):

  | Type | Settings | HTML |
  | --- | --- | --- |
  | `paragraph` | `text` | `<p>` |
  | `heading` | `level` (2, 3, 4), `text`, `anchor` (optional) | `<h2 id="anchor">` |
  | `list` | `style` (`bulleted`, `numbered`), `items` (`{ text, items }`, 3 deep) | `<ul>`/`<ol>`, nested |
  | `quote` | `text` | `<blockquote><p>` |
  | `image` | `media` (a Media id, or null until one is chosen) | `<figure>` with the Media image (`<picture>`) and the item's caption as `<figcaption>` |
  | `video` | `url` (YouTube or Vimeo), `title` | `<figure class="wc-embed">` with a link to the video (see below) |
  | `table` | `headerRow` (default true), `rows` (lists of cells) | `<table>`, the first row in `<thead>` with `<th scope="col">` |
  | `callout` | `tone` (`info`, `success`, `warning`, `danger`), `text` | `<aside class="wc-callout" data-tone="…"><p>` |
  | `code` | `code`, `language` (optional) | `<pre><code data-language="…">` |
  | `divider` | | `<hr>` |
  | `toggle` | `summary`, `text` | `<details><summary>` |

- **Formatted text** (`body/inline.ts`) is runs, `[{ text, marks?, link? }]`, with the marks `bold`, `italic`, `strike` and `code` and links to addresses the renderer keeps (http, https, mailto, tel, paths, `#anchors`); `\n` is a line break. Text alone is a shorthand for one run. The canonical form joins runs with the same marks and link and writes marks once each in order, so equal text is stored the same way.
- **Saving** (`readBody`): Blocks without an `id` get one; given ids are kept (two Blocks with one id are refused). A Block of an unknown type, a setting a type doesn't have, an unsafe link, a heading level outside 2–4, an anchor starting with `wc-` and anything past `BODY_LIMITS` (2,000 Blocks, 500,000 characters, 20,000 per text, 50,000 of code, 20 columns, 500 rows) are refused at their place (`ENTRY_INVALID` at `fields.body[3].text[1].link`). Kept and listed in `problems` instead (the whole list is saved at once, so nothing typed is lost): a Block of a type switched off (`blockType`), a video that isn't on YouTube or Vimeo (`video`) and an image that isn't in the Media library (`media`). A required body needs a Block with something in it (an empty paragraph or a divider alone doesn't count). `null` or `[]` clears it.
- **Rendering**: `{{ body }}` renders the Blocks (`renderBody`) through `BodyValue` (`bodyValue(blocks)` in the renderer's values); in an attribute or through a formatter a body is its text on one line. Blocks with nothing in them render nothing. Headings carry anchors: the one written by hand, else made from the text (`creme-brulee`), with `-2`, `-3`… when taken. Images take their alt text and caption from the Media item in the page's language, and count for the page's first image in `<main>`. The only classes are `wc-callout` and `wc-embed` (`PAGE_HOOKS`), styled in the Design system's base layer.
- **Videos load nothing until clicked**: a video renders as a link to its page on YouTube or Vimeo (`data-wc-embed` holds the player's address, YouTube's no-cookie one or Vimeo's with `dnt=1`; `data-wc-title` its title), which works without JavaScript. A page showing one links WebCraft's embed script (`VIDEO_SCRIPT`, `/_wc/js/<hash>.js`, served from the Site like the theme toggle's), which swaps the link for the player on a click, only from `PLAYER_ORIGINS`, and focuses it. No outside script runs (ADR 0023); the policy of a page showing a video lets those two origins' frames in, and only there (see "Site script safety").
- **What Templates read** (`BODY_PARTS`, `content/render-values.ts`): `body.excerpt` (the first paragraph's text), `body.image` (the first image, as `media:<id>`, so `<img src="{{ body.image }}">` is a Media image), `body.reading_time` (minutes at 200 words a minute, 0 when empty) and `body.toc` (the headings with their anchors: on its own a nested `<ol>` of links, `TocValue`; `{{@if body.toc}}` tests that there are headings). A related Entry's body reads the same way (`category.body.excerpt`). Loops (#62) read them per item.
- **Checks** (`bodyChecks`, `body/checks.ts`): a heading that skips a level (a body starts at H2), an image whose Media item has no alt text, link text that says nothing ("click here", "read more"; English and Italian lists), a table without a header row, a video without a title. Entries answer them as `checks` (`{ at: "fields.body[3]", check, detail?, message }`, `content/body-checks.ts`); they never stop publishing. The Site's list of open Checks (#95) collects them.
- **Languages**: a body is written in a language like any Translatable field (`language` on `entries.saveDraft`); a language without its own list shows the Default language's, and the page shows that language's Blocks (with WebCraft's video words in the page's language). The admin's editor starts a translation from the Default language's Blocks, so they keep its ids until AI translation and Outdated translations (later) set each Block's `source`.
- **Edit mode** shows a page's body from its Draft but never tags it as an editable region; the block editor in Edit mode is #79.
- **Seams**: Markdown in and out, pasting documents and Components in a body (#79), `?body=html|blocks|markdown` in the Content API (#108, `renderBody` and `readBody`), Module Block types (#110, the registry), translation one Block at a time (#80 and AI translation, `source` on each Block).

### Relationships

A Relationship value is a list of Entry ids inside a version. `entry_links` also keeps every link per Entry, version (`draft`, `published`) and Field path (`categories`, `credits.person` inside a Repeater), written by `changeDraft` and `publish` (`content/relationships.ts`), so what points at an Entry is one indexed lookup. Categories and tags are ordinary Post Types joined by Relationships.

- **Two-way** (the default): the Entries pointed at show the link back, as `linkedFrom` (`{ entryId, postTypeId, field, title }`, from the linking Entries' Drafts). **One-way**: nothing shows on them. Loops over Relationships (#62) and the Content API (#108) read the same links.
- **Rendering** shows only published Entries pointed at (see "What a binding reads").
- **Deleting an Entry** (`entries.delete`, Permission `entry.delete`: Staff, Owners and Editors) takes two calls. The first deletes nothing and answers `{ deleted: false, links, confirmation: { id, expiresAt } }`, `links` being how many other Entries link to it; the second, with `confirmation`, deletes it, removes the links to it from those Entries' Drafts and published versions (their status doesn't change), clears the page cache and logs `entry.delete`. While another Entry must point at it through a required Relationship, both calls answer `ENTRY_LINKED` with `data.blockedBy`.
- **Globals** can't hold Relationships.

### Two-step confirmation

`askConfirmation` and `useConfirmation` (`packages/core/src/confirmations.ts`, table `confirmations`) are how destructive procedures confirm (spec › Management API): the first call works out a preview and asks; the second works it out again inside the transaction that goes ahead and uses the id. A confirmation is for one person, one action and one target, lasts 5 minutes (`CONFIRMATION_LIFETIME_MS`), works once, and only while the preview is unchanged. Otherwise the API answers `CONFIRMATION_INVALID` with `data.problem`: `unknown`, `expired` or `changed`. They take a Site scope or a Workspace scope (a Workspace's confirmations have no Site), such as removing a Workspace-level Module's data. Changing the Default language and removing a language use them too; Publish all, emptying Trash and deleting Structure are to.

### Components

Components (`content/components.ts`, table `components`) are reusable element trees with Props: Structure (`structure.edit`, Staff only) with a Draft and a published version. Each version is `{ props, tree }`, published together as one item through `publish` with `{ kind: "component", id }`.

- **Name**: the Component's tag in Template markup, PascalCase (`PostCard`: a capital letter, then letters and digits, at least one lower-case, at most 64), unique on the Site and never the name of one of the Install's Modules' Components (`COMPONENT_NAME_TAKEN`, `data.by`). Trees place Components by id, so renaming (`components.rename`, logged as `component.rename`) only changes how markup writes them, everywhere at once.
- **Props** are declared with the Field types (`parseFields` with `listName: "props"`, so problems say `props[1].options` and "Prop"); every Field type works, a Prop keeps its type (in the Draft and the published version), and only the words Conditions use are kept from keys.
- **What its tree reads** (`componentKnownValues`): its Props as `props.x`, with their parts as for Fields (`props.link.url`, `props.category.title`), and the Globals as `site.x`. Nothing of the Entry it is placed on: that comes in through Props. It holds neither `<main>` nor `{{@outlet}}`. Its elements name the Site's Classes and token utilities as Templates' do (an inline style becomes a generated Class, which goes live when the Component is published); the stylesheet holds those its published version uses, and a Class it uses can't be deleted (`CLASS_IN_USE`, a use of `kind: "component"`).
- **Placements** are a node of their own (`PlacementNode` in `packages/renderer/src/components.ts`): `{ type: "component", id, component, props: [{ name, value }] }`, `component` being the Component's id and each value fixed text and values, as an attribute's. A Placement holds nothing else: a stored one with any other key (`children`, `tree`) is refused, since a copy's internals are never edited on their own, and Components have no slots. Its id shares the tree's element ids.
- **In Template markup** a Placement is the Component's tag with its Props as attributes, written as declared (`heroImage`), closing itself: `<PostCard heading="{{ title }}" featured data-wc-id="…" />`. A Prop with an empty value prints as its name alone. Content between `<PostCard>` and `</PostCard>` is refused, as are unknown Components and Props, a Prop given twice and a required Prop (one without a default) left out.
- **Prop values** (`content/props.ts`): fixed text is read through the Prop's Field type and checked against its rules on save: text, rich text, email, dates and a select's value as they are; numbers (`3`, `2.5`); true/false as `true`, `false` or the Prop's name alone; media as `media:<id>`; several choices or Entries separated by commas; a link as its address or JSON `{"url", "text"}`; Groups and Repeaters as JSON of their Fields' values. A value that is one binding alone (`heading="{{ title }}"`) passes the value on as it is, parts and all (`props.heading.url` reads `title.url` where it is placed); text with values in it is text. A Prop left out has its default.
- **Drafts and publishing**: Drafts of Templates and Components place Components' Drafts (`siteComponents(scope, "draft", …)`); a publish checks against the published versions, so publishing a Template (or Component) that places a Component never published is refused ("isn't published yet"). Publishing a Component changes every copy at once and clears the page cache.
- **Placing Components in Components**: never in a loop back to itself, in Drafts or what is published; at most `COMPONENT_LIMITS.depth` (10) deep; a tree shows at most `COMPONENT_LIMITS.expandedNodes` (100,000) nodes through its Components (refused on save; the renderer stops past it). What a Component shows must be HTML a browser keeps as it is where it is placed (`boundaryProblem`: its `<div>` can't go inside a `<p>`), checked on save, on publish, and when a new version of the Component is published (`checkPublishedPlacements`).
- **Rendering**: `RenderOptions.component` (a `PlacementRenderer`) renders a Placement's Component; on Site pages `pageComponents` (`site-pages/index.ts`) loads the published Components the page shows (Relationship Props written as Entry ids included) and reads Props with `placementValues`. A Component that isn't published, or a Module's that doesn't run on the Site, shows nothing.
- **Usage** (`usage` on `components.list`, `get`, `getMarkup` and `saveMarkup`): `usedIn` lists every Template and Component whose Draft or published version places it directly, and `pages` how many published pages show it: every page (published Entries with a published Entry template, and published Pages) when the published Site template places it, directly or through published Components, else the published Entries of the Post Types whose published Entry templates do. Code mode shows it as the "used on N pages" warning.
- **Deleting** (`components.delete`) takes two steps (`askConfirmation`) and is refused while anything places it, in its Draft or published version (`COMPONENT_IN_USE`, `data.usedIn`). Logged as `component.delete`; creating as `component.create`.
- **Locking**: Component saves, renames, deletes and publishes, and Template saves and publishes, take `lockComponents(scope)` (one advisory lock per Site) before any row lock, so what places what is never read half-changed.
- **API**: `components.list`, `get`, `create`, `saveDraft` (Props and a tree), `getMarkup`, `saveMarkup` (markup and, optionally, new Props), `rename`, `publish`, `delete`, each taking `siteId`; `componentId` is a UUID, or `<module id>:<Name>` for a Module's (whose changes answer `COMPONENT_FROM_MODULE`).
- **Seams**: Component custom CSS (#64) is published with the Component, beside its Props and tree in `ComponentVersion`. Page layouts (#75, which Pages render empty until then) and Components in a Body (#79) place Components with the same node and render them through `PlacementRenderer`; their Prop values, Content edited by Members, may be stored per language. Allowed components (#75) choose among the Site's Components.

### Globals

The Globals (`content/globals.ts`, one `globals` row per Site, made the first time it is needed) are one set of Fields per Site, read by every Template as `site.x`.

- `globals.get` (`site.view`): the Fields, the Draft and published values, `status`, `problems` and dates.
- `globals.setFields` (`structure.edit`): the full list of Fields, in order. Like a Post Type's, it applies at once, keeps each Field's type, clears the page cache and logs `globals.update`. Keys can't be `name`, `url`, `language` or `languages`, kept for the Site's own values under `site.`.
- `globals.saveDraft` (`entry.edit`, so Authors too) and `globals.publish` (`entry.publish`), which goes through `publish` with `{ kind: "globals" }`.

### Scripts

The Site script and page scripts (`content/scripts.ts`, table `scripts`) are the JavaScript Staff write in Code mode's JS panel: Structure (`structure.edit`, Staff only) with a Draft and a published version, as text, published through `publish` with `{ kind: "script", id }` (logged as `script.publish`). The Site script (`kind: "site"`, one per Site) runs on every page; a page script (`kind: "page"`, one per Entry, gone with it) runs on its Entry's page only, after the Site script.

- **Never inline** (ADR 0023): each version is a file named by the first 16 hexadecimal digits of its text's SHA-256 (`draft_hash`, `published_hash`). `PageToRender.scripts` lists them, the Site script first, and the renderer writes each as `<script src defer>` at the end of `<head>`. Published ones are `/_wc/js/<hash>.js` (`pageScripts`, served by the Site pipeline beside the theme toggle's, `public, max-age=31536000, immutable`); empty ones aren't loaded.
- **Who runs what**: visitors run the published versions, and so does Edit mode (ADR 0022: the Site's own scripts run there, for Members too); Code mode runs the Drafts, from `/_webcraft/edit/js/<hash>.js`, served only to Staff in Code mode (`no-store`). Safe mode runs none of them (see "Site script safety"). In Edit mode each `<script>` says which it is (`data-wc-script="site"` or `"page"`), so the editing bar can name one that fails.
- **API** (all `structure.edit`): `scripts.get({ siteId, entryId })` (`entryId` null for the Site script; null while there is none), `scripts.saveDraft({ siteId, entryId, code, basedOn? })` (makes it the first time; an `entryId` that isn't the Site's is `ENTRY_NOT_FOUND`) and `scripts.publish({ siteId, scriptId })`. A script's `version` is its Draft's hash.
- A published script a publish replaces is kept, like stylesheets, in `retired_script_files` and still served under its name for 30 days, so a page loaded just before the publish finds it; `site-files.purge` forgets it after that.

### Publishing

`services.publishing.publish(scope, item)` (`content/publishing.ts`) is the one way anything is published. `item` is `{ kind: "entry" | "template" | "component" | "script", id }`, `{ kind: "globals" }` or `{ kind: "designSystem" }`; Forms become more kinds. Open the Site with `publishPermission(item)` (`entry.publish` for Content: Entries and the Globals; `structure.edit` for Structure: Templates, Components, scripts and the Design system); `publish` checks it again, so the worker's Scheduled publishes (#69) hold it too. In one transaction it:

1. locks the item and checks it can be published: an Entry's (or the Globals') values must keep their rules (`EntryInvalidError`, `GlobalsInvalidError`) and every required value must be there, the title and slug included (`EntryIncompleteError`, `GlobalsIncompleteError`); an Entry's slug must be free among published Entries of its Post Type (`EntrySlugTakenError`; for a Page, among the Pages under its parent); a Page's parent must be published (`PageParentUnpublishedError`) and its new path, and those of the Pages under it, free of URL patterns (`PathTakenError`); a Template must still fit what it renders: its Post Type, the Globals, what its Relationships point at and the published Components it places (`ElementTreeInvalidError`); a Component must still fit what it reads and places, and every published Template and Component placing it (`checkPublishedPlacements`);
2. copies the Draft over the published version and sets `publishedAt` (first time) and `lastPublishedAt` (an Entry's published links too);
3. clears the Site's page cache (`clearPageCache`: raises `sites.page_cache_generation`);
4. writes the Audit log (`entry.publish`, `template.publish`, `component.publish`, `script.publish`, `globals.publish`). `entry.publish` holds the Entry's `path` and `pathChanges`: every published path the publish changed (`{ entryId, language, from, to }`: an Entry's new slug, a Page that moved and every Page under it). The result (`Published`) carries the same `pathChanges`: Redirect rules (#94) follow them so old links keep working.

Revisions (#67), Publish all (#68), Scheduled publish (#69), Review (#70), Webhooks and the CDN purge hook in here.

### Languages

A Site's languages (ADRs 0003, 0010; `content/languages.ts`, `content/site-languages.ts`, table `site_languages`, procedures `languages.*`) are Structure: everyone who sees the Site reads them (`languages.list`), Staff change them (`structure.edit`), each change applies at once, clears the page cache and is logged. They aren't part of Publish all.

- **A language** is a BCP 47 tag kept in its canonical form (`canonicalLanguage`: a language, an optional script and region: `fr`, `pt-BR`, `zh-Hant`, `es-419`; `LANGUAGE_INVALID` otherwise), a name (its own name, `Français`, unless given), a direction (`ltr`/`rtl`, from the code unless given) and an optional domain of its own (in lower case and its ASCII form, unique on the Install among every Site's domains; never the admin host or under the sites domain; `LANGUAGE_TAKEN` with `data.field`). A language's domain is also on the Site's domain list (`site_domains`, role `language`), where it is verified like any other domain; once verified, it serves that language without a prefix (see "Domains"). Every Site has a row for its Default language (`sites.default_language`, `en` for a new Site); `siteLanguages(scope)` answers them, the Default language first.
- **Addresses**: the Default language is unprefixed; every other language's paths start with its code in lower case (`/fr/blog/pain-frais`, `/pt-br/…`; its home page at `/fr`). `languageOfPath` reads a path's language, `languagePath` writes one. A prefix belongs to its language: a top-level Page, an Entry under a `{slug}`-first URL pattern, or a URL pattern whose first part is a prefix is refused with `PATH_TAKEN` (`by: { kind: "language", code, name }`), and adding a language whose prefix the Site's paths already start with is refused naming the Page or Post Type there (`checkPrefixFree`). These take `lockSitePaths` first. A path starting with the Default language's own code goes on (301) to the path without it where nothing else answers, so a new Default language's old addresses keep working.
- **Adding** (`languages.add`) makes every published Entry answer in the new language at once, at its Default language slug (`publishSlugsIn`); **removing** (`languages.remove`, two steps: the first answers `preview.pages`) deletes its published slugs and its 404 page; values written in it stay in the content store, so adding it again brings them back. The Default language can't be removed.
- **Changing the Default language** (`languages.setDefault`, two steps; the first answers `preview: { from, to, changedPaths, withoutOwnTitle }`, the warning the admin shows) moves every shared value (shared Fields, `parent`, `hiddenLanguages`, in Entries' Drafts and published versions and the Globals) to the new Default language's key, so it keeps its value; Translatable fields now fall back to the new one. Every published address that changes is answered and logged as `pathChanges` (`defaultLanguage.change` logs their count); Redirect rules (#94) follow them.
- **Slugs** are translatable and never change on their own once published: publishing gives each language the slug of its own, else the one it was published with before, else (the first time) the Default language's (`published_slugs` has a row per Entry and language). An Entry's `path` and `published.slug` are its address in the language asked for. Slugs clash per language (`ENTRY_SLUG_TAKEN` with `data.language`).
- **Publishing** checks every language the Entry (or the Globals) is shown in; a problem of another language's own value carries `language`.
- **Language visibility** (Content, in the Draft): `hiddenLanguages` on `entries.create` / `saveDraft` lists the languages an Entry is hidden in, stored beside `parent` as one shared value. Once published, the Entry answers 404 there, has no `hreflang` alternate there, and is left out where Entries are listed in that language: Relationships on pages now; Loops (#62) and sitemaps (#92) call the same rule, `isVisibleIn(version, languages)` or, in a query, `publishedVisibleIn(languages)` (`content/visibility.ts`).
- **Pages**: `<html lang dir>` are the page's language's; every page of a Site with more than one language lists `<link rel="alternate" hreflang>` for each language it is shown in, at that language's address (absolute, from `SiteHost.addresses`: on the Staging address every language under its prefix there; on the Site's domains each language on its own verified domain, else under its prefix on the Primary domain), then `x-default` at the Default language's; the 404 page lists none.
- **The Language switcher** is the Template command `{{@languageSwitcher}}`: a `<nav class="wc-language-switcher">` named in the page's language, a list of links to the page in each language (that language's home page where the Entry is hidden, and on the 404 page), each named in its own language with `lang`/`hreflang` (and `dir` when it differs), the page's own marked `aria-current`. It renders nothing on a Site with one language, and goes only where a `<nav>` can. A link to a language on another of the Site's domains goes straight there (its address); the others go through `/_wc/lang/<path>` (`LANGUAGE_CHOICE_PATH`): the pipeline keeps the language of the path in the `webcraft.language` cookie (`__Host-` on HTTPS, a year) and sends the visitor on (303, `no-store`), without JavaScript; any other path there is a plain 404.
- **The browser-language redirect** (`languages.setBrowserRedirect`, off by default, `sites.browser_language_redirect`): a request to `/` with no language cookie, from a browser (not a robot by its user agent, not without one), not coming from the Site itself, goes on (302, `no-store`) to the home page in the language its `Accept-Language` prefers among those the home page is shown in, which is then remembered in the cookie. Deep links are never redirected, nor anything on a language's own domain (its `/` is already that language's). A language on its own domain is sent to its address there. While it is on, `/` answers with `Vary: Accept-Language, Cookie`.
- **Fixed text** in Templates (and Components, Forms) has a value per language: a text node keeps its text as written and, optionally, `translations` by language tag; pages in those languages show theirs, every other page the text as written (`textIn`, `packages/renderer/src/languages.ts`). Template markup writes it as `{{ "Read more" fr: "Lire la suite" }}`, in text and in attribute values (`\"` for a quote, `\\` for a backslash, `\r` for a carriage return); text with other languages is never joined with the text beside it.
- **Edit mode** shows a page in its path's language: its Drafts in that language, regions saved in it (`save` takes `language`), and the editing bar lists the page in every language (`state.languages`).
- **AI translation** (#81) builds on this: each stored value keeps who wrote it (`by`), which is how Outdated translations will be told from AI ones.

## The Site pipeline and the page cache

`apps/server/src/site/pipeline.ts` answers every hostname other than the admin host (ADR 0004):

0. **Domain verification** comes first: `/_webcraft/verify/<token>` on any hostname answers the Install's own answer for one of its domains' tokens (`services.domains.verificationAnswer`), else the plain 404, before the hostname step, as a domain waiting for DNS belongs to no Site yet (see "Domains").
1. **Hostname → Site** (`services.sitePages.resolveHost`), compared in lower case without a trailing dot: a Staging address, `<site slug>.<WEBCRAFT_SITES_DOMAIN>`, or one of the Site's **verified** domains (see "Domains"). The answer (`SiteHost`) says how the hostname reaches the Site (`address`: `staging`, `primary`, `redirect` or `language`, with the `language` a language's domain serves) and where the Site's pages are (`addresses`). A **Redirect domain** answers every request with a 301 to the same path and query on the Primary domain (`Cache-Control: public, max-age=0, must-revalidate`, so a later change of Primary domain can't loop in a browser), or the plain 404 while the Site has no verified Primary domain. Anything else gets the unbranded 404. The admin host never resolves to a Site, and no Site slug can make a Staging address equal to it (`reservedSlugs`).
2. **Only `GET` and `HEAD`** for now (405 otherwise), except where a reserved path's feature takes more (a Module's Site routes); Form posts come with their reserved paths.
3. **Paths the Install keeps** (`isReservedPath`): every path whose first part starts with `_` (`/_webcraft/…`, `/_media/…`, `/_content/v1/…`, `/_wc/m/<module>/…`) and every path naming a file, with a dot in a part (`/sitemap.xml`, `/robots.txt`, `/llms.txt`, Markdown copies such as `/about.md`). No slug or URL pattern part can start with `_` or hold a dot, so no Page or Entry is ever there. Each feature answers its own (add its step here), before Entry routing and never kept as pages: Media files at `/_media/<hash>-<name>.<ext>` (see "Media"); the Site's stylesheet at `/_wc/css/<hash>.css` and scripts at `/_wc/js/<hash>.js`: WebCraft's own (the theme toggle's and the embed script of a body's videos, see "The Design system" and "The Body field"), the Site's published Site script and page scripts (see "Scripts"), the code of its outside scripts' snippets, and any of them replaced in the last 30 days; its Libraries at `/_wc/lib/<hash>-<file name>` (see "Site script safety"); Edit mode and Code mode at `/_webcraft/edit/…` (see "Edit mode"); the Language switcher's links at `/_wc/lang/…`, which remember the visitor's language and send them on (see "Languages"); Modules' Site routes at `/_wc/m/<route prefix>/…`, which go to the Module host (`services.modules.answerSiteRoute`) and are answered where the Module runs, with any method it declares (see "Modules"). The rest get the plain 404 until their features come.
4. **Edit mode**: a request carrying an edit cookie that still holds gets the page rendered afresh for Edit mode, never from or into the page cache (see "Edit mode"); an edit cookie that no longer holds is cleared and the request goes on as a visitor's.
5. **The browser-language redirect**, when the Site has it on: a first request to `/` may go on to the home page in the browser's language (see "Languages").
6. **Page cache lookup** by the address's origin and normalised URL (`canonicalPath`): decoded path segments, no trailing slash, no query parameters (none changes a page yet; Filters will keep theirs, sorted). The same path is another page on each of the Site's addresses (its language, its absolute links), so each address keeps its own.
7. **Render on a miss** (`services.sitePages.render`): in the language the hostname and the path name (`pathOnHost`: on the Staging address, and in Edit mode, the language the path's prefix names, the Default language without one; on a language's own domain, that language, without a prefix, a path starting with any language's prefix going on (301, keeping the query) to where that language's path is; on the Primary domain, as on the Staging address, except that the prefix of a language with a verified domain of its own goes on (301) there), the published Entry whose Post Type's URL pattern and published slug match, through its published Entry template (an Entry whose Entry template isn't published has no page yet); else the published Page at that path; at `/`, the home page. Every page renders inside the Site template. The page is kept in the cache. The home page's own path answers a 301 to `/`.
8. **Answer** with `Content-Type: text/html`, `Cache-Control: public, max-age=0, must-revalidate` (browsers and proxies revalidate every time, since a publish must show at once), a strong `ETag` (SHA-256 of the HTML; `If-None-Match` gets 304), `X-Cache: HIT` or `MISS`, the page's Content Security Policy (kept with the page in the cache, see "Site script safety"), and on a Staging address `X-Robots-Tag: noindex` (never on the Site's domains).

Every answer on a Site's hostname, whatever it is (a page, a 404, a file, a redirect, a Redirect domain's, a domain verification, a refusal, a Module's route, Edit mode's), leaves the pipeline through `withSecurityHeaders`, which adds the fixed security headers it doesn't carry already (see "Site script safety").
9. **A path with no page** gets the Site's **404 page** (`services.sitePages.notFound(host, pathname)`), in the path's language: the Page Staff chose for it or for the Site, once published, else the built-in one (`builtInNotFoundPage`: a heading and one sentence in the page's language), inside the Site template, with status 404 and `Cache-Control: no-store`. It is never kept in the page cache and has no ETag, so every miss reaches the Site (the 404 log, #94, hooks in here) and a page published at the path shows at once.

**The page cache** (`apps/server/src/site/page-cache.ts`) is in the web process's memory, 64 MiB by default, least recently used pages going first. Every page is kept under the Site's page cache generation, read with the hostname; `publish` raises the generation in Postgres in the publish's own transaction, so the whole Site's cache is cleared at once, in every web process, whichever process published (the worker too). A request that read an older generation never stores its page. The Content API (#108) and a CDN purge can key on the same generation and ETags.

Staging addresses show published pages for now; #68 makes them show Drafts, at which point Staging answers stop being cached.

### Element trees and the renderer

Templates are stored as element trees (`packages/renderer/src/tree.ts`, ADR 0002), the one canonical format the builder, Template markup and the renderer share:

```ts
{ version: 1, nodes: [
  { type: "element", id: "Xb3…", tag: "article", attributes: [], classes: ["<Class id>"], children: [
    { type: "element", id: "Q9z…", tag: "h1", attributes: [], classes: [], children: [{ type: "value", path: "title" }] },
    { type: "value", path: "publishedAt", format: { type: "date", style: "long" } },
    { type: "comment", text: " kept for Staff, never sent to visitors " },
    { type: "condition", branches: [{ test: { type: "value", path: "summary" }, children: [/* … */] }], otherwise: null },
    { type: "element", id: "k2P…", tag: "a", classes: [],
      attributes: [{ name: "href", value: [{ type: "text", text: "/blog/" }, { type: "value", path: "slug" }] }],
      children: [{ type: "text", text: "Read more" }] },
  ] },
] }
```

- Elements have a stable `id` (filled in when missing, kept when given), a lower-case `tag` from `TEMPLATE_ELEMENTS`, ordered `attributes` (a list: Postgres `jsonb` doesn't keep key order, and a round trip must lose nothing), `classes` (the ids of the Site's Classes, ADR 0009) and `children`. Text nodes are fixed text, as written and optionally in other languages (`translations`, see "Languages"); value nodes and attribute value parts are **bindings**: a `path` (`title`, `address.city`, `category.url`, `site.phone`; later `props.x`, `item.x`) and an optional `format`, which Edit mode (#72) reads to tag editable regions. Comments are kept and never rendered. Template commands' nodes (a Condition so far) come from the command registry (see "Template markup").
- `parseElementTree(input, options)` checks a tree and answers its canonical form (text next to text joined, empty text dropped, line breaks in comments as `\n`), or throws `ElementTreeInvalidError` with every problem and where (`nodes[0].children[2].attributes[1]`): scripts, elements outside `TEMPLATE_ELEMENTS`, `on…`, `style`, `class`, `srcdoc` and `data-wc-…` attributes, unknown value names (`isKnownValue`), Class ids the Site doesn't have (`classIds`), nesting a browser would change (a block inside `<p>`, a link inside a link, table parts out of place, `<li>` inside `<li>`), duplicate ids, children of void elements, NUL and broken characters, more than 64 levels or 10,000 nodes. The API answers it as `TEMPLATE_INVALID` with `data.problems`. The element and attribute rules are functions (`elementProblem`, `attributeProblem`, `nestingProblem`) the markup parser calls too, so both refuse the same things with the same words.
- New node types join the `TreeNode` union; a change old trees can't be read as raises `ELEMENT_TREE_VERSION`.
- `renderPage` (`packages/renderer/src/page.ts`) writes a whole document: `<html lang dir>` (the direction from the language), the title (`<title> · <Site name>`), a skip link as the first thing in `<body>`, then the Site template (the built-in one when the Site has none published) with the page's content (an Entry template, a Page's layout, the 404 page's content) rendered at its `{{@outlet}}`. The Site template's one `<main>` gets the id the skip link points at and `tabindex="-1"`, so following the link moves focus there; WebCraft adds them through `extraAttributes`. With `editMode` (`EditModePage`), `renderPage` writes the page for Edit mode instead: `noindex`, WebCraft's own files first in `<head>`, and editable regions tagged (`RenderOptions.editRegion`; see "Edit mode"). Landmarks (`<header>`, `<nav>`, `<footer>`) are the Site template's. The words WebCraft writes into pages (the skip link, the built-in 404 page) come from `pageWords(language)`: English, Italian, French, German, Spanish, Portuguese and Dutch, by the language's primary subtag, English for any other. **Accessibility hooks** the Design system (#64) styles from its base layer are named in `PAGE_HOOKS`: the skip link's class `wc-skip-link` (out of sight until focused), the main id `wc-main`, and the custom properties the focus style reads (`--wc-focus-color`, `--wc-focus-width`, `--wc-focus-offset`), set from Design tokens; it can be restyled but not removed (see "The Design system"). A body's hooks are there too: `wc-callout` (with the tones' custom properties `--wc-callout-info`, `--wc-callout-success`, `--wc-callout-warning`, `--wc-callout-danger`) and `wc-embed`. Values are typed (`TemplateValue`: text, numbers, true/false, dates, rich text, a body's Blocks, a table of contents, or a list of them); the Site pipeline hands dates over as dates and rich text marked with `richText(html)` (see "What a binding reads"). A list renders as its values joined with commas, each through the value's formatter. Text and values are escaped for text or double-quoted attributes; `href`, `src` and other URL attributes (each `srcset` candidate, each `ping` URL) keep only `http`, `https`, `mailto`, `tel`, relative paths and `#anchors`, anything else becoming `#`. A date without a formatter renders as `2026-03-02`. Rich text renders as its cleaned HTML in text and as its plain text in attributes and formatters. Comments are left out. No inline script, inline style or event handler is ever written: the `<head>` links the Site's stylesheet, and a page showing a theme toggle (or a body's video) links its script file.

## Domains

A Site's domains (ADR 0015; `packages/core/src/domains/`, behind `services.domains`; table `site_domains`, procedures `domains.*`; the admin's Site › Domains & Staging) are Site settings: everyone who sees the Site sees them (`domains.list`, `site.view`), Staff change them (`structure.edit`), each change applies at once and is logged (`domain.add`, `domain.makePrimary`, `domain.remove`), and none is part of Publish all.

- **Names** (`domains/names.ts`): `domainName` keeps a domain in lower case, without the trailing dot, international names in their ASCII form (`Bäckerei.example` is `xn--bckerei-…`; `displayName` shows them as written); it refuses an address with a scheme, a path or a port, an IP address, a wildcard and a single name (`DOMAIN_INVALID`, `reason: "format"`), and `isInstallName` the Install's own names: the admin host, the sites domain and every name under it (`reason: "install"`). A name is unique on the Install, whichever Site or Workspace has it, languages' domains included (`DOMAIN_TAKEN`, `data.name`).
- **Roles**: one **Primary domain** per Site, which serves it; any number of **Redirect domains**, which answer 301 to the same path and query on the Primary domain; and the **languages' domains** (`role: "language"`, `language` set), which serve that language without a prefix. A language's domain is set in Languages (`languages.add`/`update` write both `site_languages.domain` and its `site_domains` row; removing the language removes the row); here it is only listed, verified and checked (`DOMAIN_CHANGE_REFUSED`, `problem: "language"`, for the rest).
- **Adding** (`domains.add`): the first domain of a Site without a Primary domain becomes it, the rest are Redirect domains. With `withPartner`, the apex or `www` partner comes too (`partnerOf`: `www.bakery.ie` for `bakery.ie` and back), as a Redirect domain; one the Site has already is left as it is, one another Site has refuses the whole addition.
- **The DNS records** each domain lists (`records`): A and AAAA records to `WEBCRAFT_PUBLIC_ADDRESSES` (`address`, none without it), or for a subdomain a CNAME record to the admin host (`alias`). The screen shows them for the Install's `edge` first (`domains.list` answers it), with the steps for Coolify and Railway, where the domain is also added in the platform's panel.
- **Verification**: a domain serves nothing until the Install has seen it reach it. `checkReaches` (`domains/checks.ts`) resolves the domain, fetches `http://<domain>/_webcraft/verify/<token>` (on the web process's port for a development name under `.localhost`) and accepts only the answer this Install makes for that token. Token and answer are HMACs under a key derived from the Master key (`domainVerificationKey`): the token from the domain row's id and name (a domain added again gets a new one), the answer from the name and token, so neither is stored and no other Install, nor anything echoing the request, can make the answer. The Site pipeline answers the path before its hostname step (step 0 above), only for a domain's own token on that domain, `no-store`. A domain that doesn't resolve, or answers wrongly while pointing elsewhere than the Install's addresses, has the problem `dns`; one pointing at them that doesn't answer, `unreachable`; one answering something else, `response`.
- **What the checks call** (the SSRF line): every request goes through the guarded fetcher, `GET` only, no redirect followed (a redirect is a wrong answer), 1 KB, 10 seconds. Besides public addresses it may call **only the Install's own addresses** (`installAddresses`: `WEBCRAFT_PUBLIC_ADDRESSES` and what the admin host resolves to), since a domain must point at the Install, which may be on a private network or, in development, on this machine. A domain resolving to any other internal address is never called (`dns`), and nothing it answers reaches anyone: only whether it was the Install's own answer. Staff can't choose the path, the method or the port.
- **When**: `domains.verify-due` runs every minute (`coreSchedules`), claims each domain waiting for DNS whose `next_check_at` came (moving it on first, so no check runs twice) and queues one `domains.verify` job each: every 5 minutes for the first hour after the domain was added, hourly until 7 days, then only when Staff press **Check now** (`domains.check`), which checks at once and starts the round again. A verified domain clears the Site's page cache (its addresses changed) and has its certificate looked at, which also starts an on-demand one.
- **The Domain check**: `domains.check-all` runs hourly and queues one `domains.check` job per verified domain: it checks the domain as verification does, then its certificate over TLS (`checkCertificate`, through the `tls` port: `systemTls` in the processes, faked in tests; skipped for `.localhost` names): one that is missing or not trusted is `certificate-missing`, one running out within 14 days `certificate-expiring`. A failing domain is **Unreachable** (`unreachable_since`; it keeps serving, and Caddy keeps renewing its certificate) and active again once a check passes. The check that turns it Unreachable, and only that one, sends the `domain-unreachable` System email to the **Site's Owners**: the Members reaching the Site whose role manages the Workspace's Members (`member.manage`, which only Owners hold in v1), linking to `/sites/<id>/domains`. Check now on a verified domain runs the Domain check at once.
- **Making a domain the Primary domain** (`domains.makePrimary`): only a verified Redirect domain (`DOMAIN_CHANGE_REFUSED`, `problem: "not-verified"`); the Primary domain before it becomes a Redirect domain, so its links keep working. Clears the page cache.
- **Removing** (`domains.remove`, two steps: the first answers `preview: { name, role, live }`): the domain stops at once (no page, no certificate); to move it to another Site, remove it, add it there and verify it again. Without its Primary domain a Site is on its Staging address only, and its Redirect domains answer the plain 404 until another domain is made Primary.
- **Caddy's ask** (`GET /caddy/ask?domain=<name>` on the admin host, `apps/server/src/admin/caddy-ask.ts`; point Caddy's `on_demand_tls { ask … }` there): 200 for the admin host, the Staging address of an existing Site and every verified domain (Primary, Redirect and language, Unreachable ones too), 404 for any other name, 400 for what isn't a hostname, 405 for any method but `GET`. It reads at most one row and writes nothing: no rate limit, no log line. The ask comes from inside the deployment, so the deploy files (#83) must send it with the admin host as its `Host` (a network alias of the web service), and Caddy must answer `/_webcraft/verify/…` over plain HTTP without redirecting to HTTPS, since a domain has no certificate until it is verified.
- **Addresses** (`domains/addresses.ts`): `siteAddresses` answers where a Site's pages are for visitors (`main`: the verified Primary domain's origin, else the Staging address; `languages`: each language's verified domain), and `placeOf` where a path in a language is. hreflang and the Language switcher use them now; canonical URLs (#91), sitemaps (#92), Social cards and absolute Media URLs should too. Media files are served on whichever of the Site's addresses asks (`/_media/…` is relative).

## Edit mode

Edit mode (ADRs 0016, 0022) shows a Site on its own domain with its Drafts, and lets a signed-in person change Content in place. Core: `packages/core/src/edit-mode/` (`services.editMode`); the web side: `apps/server/src/site/edit-mode.ts`; the editing bar: `apps/server/src/site/edit-bar/`.

### Getting in: the signed link and the edit cookie

The admin's session cookie belongs to the admin's hostname and never reaches a Site's domain, so the admin hands over a link instead.

1. **"Edit on site"** (the admin's top bar on a Site's pages) calls `editMode.open({ siteId, path })` (`entry.edit`); its menu's "Edit in Safe mode" adds `safeMode: true`, and the link then says `&safe=1`, which starts Safe mode as the link is followed (any other link ends it). It answers a link on the Site's address (its verified Primary domain, else its Staging address; the edit cookie then lives on that hostname, and Edit mode keeps every language under its prefix there), `…/_webcraft/edit/enter?token=…`, which works **once**, within **60 seconds**, for this person, this Site and the admin session that asked (`edit_links`, only the token's SHA-256 stored). `path` must be a path on the Site (`isEditPath`: one leading `/`, no query, fragment, backslash or space), so a link can't send anyone elsewhere (`EDIT_PATH_INVALID`). A Site with no address answers `EDIT_MODE_UNAVAILABLE`.
2. **Following it** (`GET /_webcraft/edit/enter`, rate-limited like sign-in) uses the link up, checks that the admin session is still signed in and that the person still reaches the Site with `entry.edit`, starts an **Edit mode session** (`edit_sessions`, for at most **8 hours**, records `editMode.start`) and answers `303` to the page with the edit cookie: `__Host-webcraft.edit` (named `webcraft.…` like every cookie WebCraft sets on a Site's domain, so Modules' Site routes never see it), `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age` up to 8 hours (on a `.localhost` development host: `webcraft.edit`, without `Secure`). The answer has `Referrer-Policy: no-referrer` and `no-store`, so the token neither leaks nor stays in history. A used, expired, unknown or other Site's link is a plain `403`.
3. **Every request after that is checked again** (`services.editMode.session`): the session hasn't run out, its admin session is still signed in (`auth.activeSession(id)`: by id, server-side, without the cookie), and the person still reaches the Site with `entry.edit` (the data layer runs `can()`, with `via: editMode`). A session that fails a check is ended there. Both tables hang off the admin session (`ON DELETE CASCADE`), so **signing out, a revoked session or losing access ends Edit mode at once**; the next page is a visitor's and clears the cookie, the next edit request answers `401 EDIT_MODE_ENDED`.

### Pages in Edit mode

A page request with a session that holds gets `services.sitePages.render(host, path, editing)` (`notFound(host, editing)` for a path with no page): the same page found the same way as for visitors, showing the **Drafts of its Content** (its Entry and the Globals) through the **published Templates** and the published Components they place (Template and Component Drafts show in Code mode, see below, and on Staging, #68), rendered afresh and never kept in the page cache. It carries:

- **Tags on editable regions** (`RenderOptions.editRegion`): an element whose only content is one binding without a formatter, when the binding is the Entry's `title`, a text or rich text Field (in Groups too: `address.city`; `editableField` in `content/editable.ts`) or such a Global (`site.x`, in the content or the Site template), gets `data-wc-item` (`entry:<id>` or `globals`), `data-wc-field` (the binding's path within it), `data-wc-type` (`text`, `richText`), `data-wc-label` (the Field's label; none for the title, which the bar names itself) and the element's id as `data-wc-id`. Values beside other text, through a formatter, in Repeaters, Relationships, links and selects aren't tagged, nor is a body (its block editor comes to Edit mode with #79). Elements inside a Component are never tagged (their ids are the Component's, not the page's Template's). Page Props (#75) and Loop items (#62) add their bindings in `editRegions` (`site-pages/index.ts`). Pages for visitors carry none of this.
- **WebCraft's own files first in `<head>`**: `<meta name="robots" content="noindex, nofollow">`, the session's header token (`<meta name="webcraft-edit-token">`), the editing bar's script (a classic script, so it runs before any Site script) and the page stylesheet, all as hashed files at `/_webcraft/edit/assets/<name>-<hash>` (`public, max-age=31536000, immutable`).
- **Headers**: `Cache-Control: no-store`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY` and Edit mode's own strict policy, whatever the Site's mode (`editModePolicy`): scripts, styles and fonts only from the Site's own domain, requests to it and its allowed hosts (which only the Site's own scripts can make there), `frame-src https:` (iframe embeds still show), `frame-ancestors 'none'`, `base-uri 'none'`, `object-src 'none'`.
- **No outside scripts** (ADR 0022): `editMode` on `PageToRender` is the switch. Besides WebCraft's own, the renderer writes only the Site's own scripts: its Libraries (`data-wc-library`) and the published Site script and page script (`data-wc-script`, see "Scripts"). Each outside script shows instead as a labelled placeholder at the end of the page (`<aside class="wc-outside-scripts">`, styled by Edit mode's page stylesheet). In Safe mode the Site's own scripts are left out too (see "Site script safety").

### Edit requests

The editing bar talks to `POST /_webcraft/edit/api/<action>` on the Site's domain, with JSON. Each request needs, in this order: a `POST` from the Site's own pages (`Origin` the Site's, and `Sec-Fetch-Site: same-origin` when the browser sends it; else `403 EDIT_REQUEST_REFUSED`), an edit cookie whose session still holds (`401 EDIT_MODE_ENDED`), and the session's **header token** in `X-WebCraft-Edit-Token` (an HMAC of the session id under a key derived from the Master key, `editModeSigningKey`; `403 EDIT_REQUEST_REFUSED`). Refusals answer `{ code, message, data }` with the Management API's codes (`toApiError`).

| Action | Body | What it does |
| --- | --- | --- |
| `state` | `{ path }` | The page's state (`PageState`): its title and item, the person, the Site, the language, `canPublish` (`entry.publish`), the page's **changes** (its Entry's values, then those of the Globals it shows, that differ from what is published, each with its label, type and who wrote it), `publishAll` (the admin's Site page and how many other Drafts the Site has) and the Site's pages for the page switcher. Adds the bar's `words` in the person's Admin language (the `editBar` part of the admin's message files). |
| `save` | `{ item, field, value }` | Saves one region's value to the Draft through `saveDraft` / `saveGlobalsDraft` (the admin's path: rich text is cleaned, wrong kinds refused, broken rules kept and listed). Answers `{ status, value, problems }`, `problems` being those of that value. Only the title and text and rich text Fields (`EDIT_FIELD_INVALID` otherwise), and only on this Site. |
| `undo` | `{ path, item, key }` | Puts one of the page's changes back as published (`undoDraftChanges`, `undoGlobalsChanges`). |
| `discard` | `{ path }` | Puts every change of the page back, in one transaction. |
| `publish` | `{ path }` | Publishes the page's changed items (its Entry, then the Globals), all or none, with `entry.publish` (Authors get `FORBIDDEN`). Recorded as `entry.publish` / `globals.publish` with `via: editMode`. |
| `safe/start`, `safe/stop` | `{}` | Turns Safe mode on or off for this browser: the Safe mode cookie (`__Host-webcraft.safe`, `webcraft.safe` on `.localhost`), for the rest of the Edit mode session. |
| `end` | `{}` | Ends this Edit mode session and clears the cookie (and Safe mode's). |

Saving a Draft isn't written to the Audit log; publishing is. Edit mode never takes a Sensitive action (`assertSensitiveActionAllowed` refuses anything but the admin). #71 (Co-editing) turns `save` into changes to the Draft's shared document, through the same functions. Code mode's requests (`code/…`) go through the same checks, then `structure.edit` (see "Code mode").

### The editing bar

`editingBar` (`edit-bar/bar.ts`) is one self-contained function: the served script is its source text with its config (`edit-bar/assets.ts`), named by its hash, so it must use nothing from outside itself (no imports, no module-level values). It keeps the browser functions it needs as it starts, before any Site script, and draws itself in an open shadow root (`<webcraft-edit-bar>`, right after the skip link), styled by its own stylesheet there (`BAR_STYLES`); the page stylesheet (`PAGE_STYLES`) only makes room for it and outlines the regions. Everything is a file on the Site's domain: no inline scripts or styles (positions are set through the CSSOM, which the CSP allows).

- **The bar** (variant A of the inline editing prototype): the Site's name, the page switcher (a menu of the Site's pages), the Draft status, Edit and Preview (and Code, for those who may change the Site's Structure: `canCode` in the page state), device widths (desktop, 768 px, 390 px: the page's width, not its media queries), the current language (a menu of the page in each of the Site's languages when it has more than one), the Publish menu and the person's menu (open the admin, end Edit mode). A first-time hint explains Edit mode until dismissed (kept in local storage).
- **Editing in place**: regions get `contenteditable` (`plaintext-only` for text where the browser has it; Enter doesn't break a line). Focus or hover shows the region's label (`Intro · Rich text`); rich text shows a floating toolbar (bold, italic, link, lists, clear formatting, undo, Done) above it, or below when there's no room under the bar, reached from the text with **Alt+F10**, moved through with the arrow keys, left with Escape. Changes save to the Draft 0.8 s after typing stops and when focus leaves; each save is announced in the bar's live region (`role="status"`), and a value's problems show next to the region (and are announced).
- **The Publish menu** lists the page's changes, each with Undo, then Discard (with a confirmation) and Publish page; Authors see "Saved to Draft" instead. It links to Publish all in the admin (the Site's page until #68 builds it) with the number of other Drafts.
- **Focus**: the bar never covers the focused element (the page has `scroll-padding-top`, and the bar scrolls anything focused under it into view). Menus and the Publish menu open from their buttons, Escape closes them and returns focus; their items exist only while they are open.
- It reads the page's state again every minute and when the tab comes back, so a session that ended shows "Edit mode has ended" and stops editing.
- **Safe mode** (ADR 0022): the person's menu turns it on and off (`safe/start`, `safe/stop`, then the page loads again); while it is on (`<meta name="webcraft-safe-mode" content="on">`) the bar shows a "Safe mode" chip.
- **A failing Site script**: the bar listens for `error` events from the start, before any Site script runs. One from a file tagged `data-wc-script` or `data-wc-library` (a script that throws, or one that doesn't load) shows a notice under the bar (`role="alert"`): which script failed and its message with the line, "Open in Safe mode" (outside Safe mode) and, for those who may code (`canCode`), "Open it in Code mode", which turns Code mode on and leaves the script's kind in session storage (`webcraft-code-script`) so Code mode's JS panel opens at it, its editor focused.

### Code mode

Code mode (ADR 0016, `GLOSSARY.md`) is a third way of using Edit mode, for Staff and the Superadmin only (`structure.edit`). Core: `packages/core/src/code-mode/` (`services.codeMode`); the web side: the `code/…` actions in `apps/server/src/site/edit-mode.ts`; the panels: `apps/server/src/site/code-mode/`.

- **Turning it on**: the editing bar's Code button sends `code/start` (refused with `FORBIDDEN` for anyone without `structure.edit`), which sets the Code mode cookie (`__Host-webcraft.code`, `webcraft.code` on `.localhost`; `HttpOnly`, `SameSite=Lax`, for the rest of the Edit mode session), then reloads; `code/stop` clears it. The cookie only says the browser wants Code mode: every page and request checks the edit cookie's session and then opens the Site with `structure.edit` through the data layer (`codeMode.access`, `codeModeOf`), so a Member's page ignores it and visitors never get Code mode.
- **Pages in Code mode** (`PageEditing.code`) show the **Drafts of the Site's Structure** around the Drafts of its Content: the Entry template's and Site template's Drafts (the built-in Site template while there is none), the Components' Drafts (`siteComponents(scope, "draft")`), the Design system's Draft (its stylesheet at `/_webcraft/edit/css/<hash>.css`, built by `draftStyles` from the Draft and every Draft tree, served only to Staff in Code mode, `no-store`) and the scripts' Drafts. Content editing (Edit, Preview) keeps showing the published Structure, so Members and Content edits never see a half-made Template. The head loads Code mode's own script after the bar's, and `<meta name="webcraft-code-mode" content="on">`.
- **Tags**: every element carries `data-wc-code` (`RenderOptions.codeSource`), where it comes from: `content` (the page's Entry template) or `site` (the Site template), then the id of each Placement showing it, then its own id: `content/<placement id>#<element id>` (`readCodeRef`). Editable regions aren't tagged in Code mode: a click selects an element instead of editing it. Visitors' and Content editing's pages carry none of this.
- **Opening** (`code/open { path, ref }`, `ref` null for the page's content, else the Site template): follows the reference through the Drafts (`resolveSource`) and answers the Template or Component as Template markup with its **version**, `editable` (a Module's Component isn't), the element (its id and tag), its `path` in the source (`article › h1.title`, a Placement as `<Hero>`), the **breadcrumb** (each Template or Component on the way, with the reference that opens it at the next Placement), `usage.pages` for a Component (the "used on N pages" warning) and the **suggestions**: the Entry's Fields and built-in values and their parts (`address.city`, `link.url`, a Relationship's `title`), the Globals (`site.x`, with their Draft values), a Component's Props (`props.x`), the Components it may place with their Props (never one placing it), the Template commands from `TEMPLATE_COMMANDS` that this kind of Template may hold (each entry's `snippet`, so a new command shows by itself), WebCraft's presets (`BUILT_IN_PRESETS`; Modules' Structure presets, #110, join them), Loops (none until #62), and the Draft's Classes and token utilities. A reference the page doesn't show is `CODE_SOURCE_NOT_FOUND` (404).
- **Previewing** (`code/preview { path, markup?: { ref, text }, css?: { target, text } }`): renders the whole page as Code mode shows it with the unsaved markup read in place of its source's Draft (`readTemplateMarkup`, `readComponentMarkup`: the same rules as saving; inline styles become generated Classes for the preview only) and unsaved CSS read into the Design system's Draft (`withChange`), answering `{ html, stylesheet: { hash, css }, notices }`. Nothing is saved. Markup that doesn't parse answers `TEMPLATE_MARKUP_INVALID` with each problem's line and column (UTF-16 units); CSS the checks refuse, `DESIGN_SYSTEM_INVALID`.
- **Saving** goes through the same saves as the Management API, only when Staff save: `code/save { path, ref, markup, version }` (`templates.save…Markup`, `components.saveMarkup`), `code/saveCss { target, text, version }` (a Class's `styles`, one breakpoint's styles or its own `css`, or the Site CSS, through the Design system's Draft and its checks), `code/saveScript { path, kind, code, version }`. Each names the **version** it was opened at (null when there was nothing yet), and a Draft someone saved meanwhile answers `CHANGED_MEANWHILE` (409) with `data.version`, the version now: the panel offers to reload it, or to save again over that version (overwrite). Nothing is merged. `code/createClass { name }` adds a Class to the Draft for a name the HTML panel doesn't know. `code/css` and `code/scripts` read what the CSS and JS panels show.
- **Versions**: a Draft's version is `draftVersion` (16 hexadecimal digits of the SHA-256 of its JSON, keys in order); a Class's covers the whole Class, the Site CSS's its text, a script's is its Draft's hash. The Management API's markup reads and saves answer `version` and take `basedOn` (`templates.saveEntryTemplateMarkup`, `saveSiteTemplateMarkup`, `components.saveMarkup`), so the CLI can refuse stale pushes the same way.
- **The panels** (`code-mode/code.ts`, `codeMode`, like the editing bar one self-contained function served as a hashed file at `/_webcraft/edit/assets/code-<hash>.js` and drawn in an open shadow root, `<webcraft-code-mode>`, styled by `CODE_STYLES`): loaded only on pages in Code mode, so Content editing stays light; no library, so nothing outside the Site's domain and no inline styles (positions and colour swatches through the CSSOM; the preview's stylesheet through a constructed stylesheet, which the strict policy allows). The HTML, CSS and JS panels sit below the page (the page stylesheet makes room for them; they can be hidden), with the breadcrumb and the usage warning above. Each editor is a text area over the highlighted code (Template markup, CSS, JavaScript) with line numbers; Tab moves on (no trap), Enter keeps the indentation, Ctrl+S saves. Clicking an element of the page (or moving the caret into its markup) selects it. The HTML and CSS panels preview as Staff type (350 ms after they stop). **Format** puts elements on lines of their own only where whitespace never shows (next to a block boundary, between two tags, never next to text, values or commands, never in `<pre>`), so formatted markup saves to the same elements and reads back exactly. **Suggestions** open on `{{`, `{{@`, `<` and a capital, inside `class="`, and in CSS on a property or `--` (Ctrl+Space anywhere): a list box the text area points at with `aria-activedescendant`, showing nine options at a time around the active one, chosen with the arrows and Enter or Tab, closed with Escape; an unknown Class name offers "Create Class". The CSS panel's layout buttons (display, direction, justify, align, wrap) set declarations in the text. The JS panel's **Run** saves the script and runs the Site script then the page script on a freshly rendered page; the console (`role="log"`) shows the page's errors, rejected promises and console messages. A changed script never runs while Staff type.

## Site script safety

Scripts can't abuse Edit mode, and Sites run under a strict Content Security Policy (ADRs 0022, 0023). Core: `packages/core/src/site-scripts/` (`services.siteScripts`; what each page loads goes through `services.sitePages`); procedures `csp.*`, `outsideScripts.*` and `libraries.*` (`packages/api/src/procedures/site-scripts.ts`); screens Site › Libraries (Structure) and Site › Outside scripts (Site settings). All of it is Structure: `structure.edit`, Staff only, with no Draft. A change applies at once, clears the Site's page cache and is recorded in the Audit log; none is part of Publish all.

### The policy

- **No inline scripts, no nonces**: pages are cached, so WebCraft never writes a script into a page. Its own scripts, the Site's scripts, Libraries and the code of outside scripts' snippets are files on the Site's domain. Each page's policy is worked out when it renders (`pagePolicyHeaders`), returned with its HTML (`SitePage.headers`) and kept with it in the page cache, so everything that changes a policy clears the cache.
- **Modes** (`sites.csp_mode`, `csp.setMode`): `strict`, the default: `default-src 'self'`, `script-src`, `style-src`, `font-src`, `connect-src` and `frame-src` from `'self'` and the allowed hosts, `img-src 'self' data: https:` and `media-src 'self' https:` (Templates may show outside images), then the fixed directives. `relaxed` adds `'unsafe-inline' 'unsafe-eval'` to `script-src` and `'unsafe-inline'` to `style-src`, for tag managers that inject code. `reportOnly` sends the strict policy as `Content-Security-Policy-Report-Only` and enforces only the fixed directives.
- **Fixed headers on every answer** on a Site's hostname (`withSecurityHeaders` in the pipeline, `SITE_SECURITY_HEADERS`): `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN`, and on answers that bring no policy of their own `FILE_POLICY`: `object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'self'`. Media files get `MEDIA_POLICY`, the same without `object-src`, since a browser opens a PDF in its own viewer. Edit mode keeps its own stricter headers (see "Edit mode"). `form-action 'self'` never takes allowed hosts: forms never post elsewhere (ADR 0023).
- **Frames a page needs**: a page showing a body's video lets `PLAYER_ORIGINS` into `frame-src` (`renderDocument` answers the page with the `frames` it needs); other pages don't.
- **Allowed hosts** (`allowed_hosts`, at most 100): host names in lower case, or `*.` and a domain of at least two labels (`readHost` refuses anything else, so nothing but a host reaches the policy: `HOST_INVALID`), always over `https`. Each says how it got there: `hand` (`csp.addHost`, for what a tag manager loads) or `auto` (an outside script needs it; it goes with the last outside script needing it). Staff can remove either (`csp.removeHost`); an outside script needing a removed host shows it in `blockedHosts`. `csp.get` answers the mode, the hosts with the outside scripts using each (`usedBy`), and `moduleHosts`: the outside hosts of the Site-level Modules running on the Site (`modules.outsideHostsAt`), which its policy allows there and nowhere else. Approving, withdrawing or switching a Module with outside hosts clears the page caches it changes.

### Outside scripts

- **What they are** (`outside_scripts`, at most 50): a name, one https address or a pasted snippet, where they load (`head`: the end of `<head>`, after the Site's own scripts; `bodyEnd`: before `</body>`), their Consent category (`necessary`, `analytics`, `marketing`, `media`), in the Site's order. An address must be https on a host a policy can name, and loads `async`.
- **A snippet** (`readSnippet`, `snippets.ts`) may hold only `<script>` elements, comments and white space; `<noscript>` parts are left out. Anything else is refused with its line (`OUTSIDE_SCRIPT_INVALID`, `data.problems`): other elements (embeds belong in a Component), `on…` attributes, scripts that aren't JavaScript, addresses that aren't https on another host, a script never closed, a snippet with no script. Scripts loading from another host keep `async`, `defer`, `type="module"`, `id`, `crossorigin`, `referrerpolicy`, `integrity`, `charset` and `data-…`. A script holding code becomes a file, `/_wc/js/<hash>.js`, loaded where the snippet had it, without `async` or `defer`, so the order the snippet relies on holds. The hosts a snippet needs are those it loads from and those its code names in an `https://` address (a loader adding another script).
- **Never in Edit mode** (ADR 0022): there each shows as a labelled placeholder in the page's language instead; iframe embeds still show.
- **Consent**: each stores its category now; the Consent banner (#101) holds back what a visitor hasn't accepted (`PageOutsideScript.consentCategory` is the seam). Until then every outside script loads.

### Libraries

- **Adding** (`libraries.add`, at most 30 per Site) by package (`source: "npm"`: a name, a version that is exact, partial such as `3.13` for its newest release, or a tag such as `latest`, and optionally the `.js` file to serve) or by address (`source: "url"`, https). The download happens in the request, through the guarded fetcher, and is refused with `LIBRARY_REFUSED` and `data.problem` (`name`, `version`, `file`, `url`, `notFound`, `fileNotFound`, `integrity`, `size`, `empty`, `unreachable`, `limit`).
- **From the registry** (`npm.ts`), only `registry.npmjs.org`: the version's manifest (`/<name>/<version>`; a partial version reads the abbreviated list of versions first), then the archive from the registry's host only, at most 20 MB, checked against the manifest's `dist.integrity` (SHA-512; else `dist.shasum`), unpacked in memory (`tar.ts`). The file is the one given, else the first the manifest names that the archive holds (`jsdelivr`, `unpkg`, `browser`, `main`, then `index.js`); at most 5 MB. The licence the package declares is kept as data.
- **By address**: the file at the address, through the guarded fetcher to that host only, at most 5 MB.
- **Kept and served**: in the Install's storage, `<workspace id>/<site id>/libraries/<hash>-<file name>`, with a SHA-384 integrity hash; served at `/_wc/lib/<hash>-<file name>`, `immutable`. Pages load every Library in order with `defer` and `integrity`, before the Site script, in Edit mode too, never in Safe mode. A Library needs no allowed host.
- **Updates only when Staff ask**: `libraries.checkUpdates` asks the registry for each package's `latest` version and stores it (`latestVersion`; `newerVersion` when it is newer). `libraries.update` downloads the package's version (the newest unless given) of the same file, or downloads an address again; `libraries.remove` takes it off every page. The file an update or removal replaces is still served for 30 days.

### Safe mode

Edit mode with none of the Site's own scripts (ADR 0022): `PageEditing.safe` leaves out the Libraries, the Site script and page script (published, and the Drafts in Code mode); WebCraft's own scripts (the editing bar, Code mode's panels, the theme toggle, a body's video) and outside scripts' placeholders stay. It is the Safe mode cookie (`webcraft.safe`), set by an "Edit in Safe mode" link (`editMode.open` with `safeMode`) or by the editing bar (`safe/start`, `safe/stop`), for the rest of the Edit mode session; visitors' pages never read it. Pages in Safe mode say so in `<meta name="webcraft-safe-mode" content="on">`. A Site script that fails in Edit mode shows the editing bar's notice, with Safe mode and the script in Code mode a click away (see "The editing bar").

### Replaced files

Script and Library files are named by their hash and kept by browsers for a year, so a page loaded before a change still asks for the old one. The published Site script or page script a publish replaces, and the code of an outside script that a change replaces or removes, are kept in `retired_script_files`; Library files an update or a removal replaces, in `retired_library_files`. Both are still served for 30 days (`RETIRED_FILE_LIFETIME_MS`), then the daily `site-files.purge` (03:37 UTC) forgets them and removes the Library files from storage, unless a Library holds the same file again.

### Not Sensitive actions

Switching a Site to Relaxed, allowing a host and adding an outside script widen what a Site's visitors' browsers load, but none of them fits the list's rule (`SENSITIVE_ACTIONS`: changing a secret, a role, what a person reaches or how they sign in, or what a Module is granted), and none reaches an edit session: outside scripts never run in Edit mode, and Edit mode keeps its own strict policy whatever the Site's. Staff's own Site scripts, which do run in Edit mode, aren't Sensitive either. So they are Structure, Staff only and in the Audit log, and API tokens and AI clients with Structure access can manage them.

## Media

A Site's Media library (`packages/core/src/media/`, behind `services.media` and `services.storage`; ADRs 0026, 0027). Its tables (`media_folders`, `media`, `media_files`) are Site tables; `install_storage` holds the Install setting.

### Storage

- **One interface, two kinds** (`media/storage.ts`): `put`, `read`, `stream(key, range?)`, `delete`. **Local disk** keeps files under `WEBCRAFT_STORAGE_DIR` (written beside the final name, then renamed; each read opens and closes the file, so a visitor who goes away never keeps one open). An **S3-compatible bucket** (`media/s3-storage.ts`: AWS S3, Cloudflare R2, MinIO, …) is spoken to through `services.http`, every request signed with AWS Signature Version 4 (`aws4fetch`) by `services.clock`'s time, with a SHA-256 of the body. It goes to the endpoint the Superadmin set, not through the guarded fetcher: a self-hosted store is usually on an internal address.
- **Keys** have one folder per Workspace and Site: `<workspace id>/<site id>/media/<name>` for files visitors get, `<workspace id>/<site id>/uploads/<media id>` for raw uploads the worker hasn't cleaned (never served); Form uploads will get `…/form-uploads/…`. A bucket's `prefix` goes in front, so one bucket can hold several Installs.
- **The Install setting** (Install settings › Storage, `install.storage.get` / `update`): local disk (the default) or a bucket. Changing it is a Sensitive action (`storage.change`): the bucket's secret access key is the Install secret `storage.s3.secretAccessKey`, write-only like every secret; leaving it out keeps the stored one. A bucket is checked before it is saved: WebCraft writes, reads back and removes `webcraft-check/<random>`, refusing the change with `STORAGE_UNREACHABLE` when it can't. Recorded as `storage.change`, never with the secret.
- **Each stored file records which storage holds it** (`media_files.storage`), and is always read from there: switching storage changes only where new files go, and never breaks a URL. The S3 settings are kept when the Install switches back to disk, so files in the bucket stay readable. Moving files between them is `webcraft admin media move` (later).

### Uploads and the worker

- **Uploading** (`media.upload`, a File in the oRPC input): at most 50 MB (`MEDIA_TOO_LARGE`; quotas per Site come with #77). What a file is comes from its first bytes (`media/sniff.ts`), never its name or the type the browser claims: JPEG, PNG, WebP, AVIF, HEIC/HEIF and GIF images, PDF, MP4/MOV/WebM video, MP3/M4A/OGG/WAV/FLAC audio. SVG is refused (`MEDIA_TYPE_REFUSED`, `reason: "svg"`) until #77 cleans them; anything else is `reason: "unknown"`.
- **Images are cleaned before anyone sees them**: they may carry GPS data. The upload is stored apart (`uploads/`), the item is `processing`, and the `media.process` job runs in the worker: it strips every piece of metadata (EXIF with GPS and camera data, XMP, IPTC), turns the pixels upright by the EXIF orientation, converts to sRGB, converts HEIC to JPEG (other formats keep theirs), stores the result as the **original** visitors get, deletes the raw upload, marks the item `ready`, clears the Site's page cache and queues `media.variants`. A file that can't be read as an image is `failed` and never served.
- **Variants** (`media.variants`): every width of `VARIANT_WIDTHS` (320, 640, 960, 1280, 1920, 2560) up to the original's (equal counts), each in AVIF and WebP, stored together in one transaction, then the page cache is cleared. Until then pages show the original alone. Adding a width later means running the job over the library again.
- GIFs (kept animated), documents, video and audio are stored as uploaded and `ready` at once.
- **Image processing is a port** (`InstallPorts.images`, `media/images.ts`): `prepare` (the cleaned original) and `variant` (one width). Only the worker hands in the real one (`apps/worker/src/images.ts`: sharp on libvips, and libheif in WebAssembly for HEIC, which sharp's own libvips doesn't decode); the web process and server commands get `imagesOnlyInWorker`, so the Bun web process never loads the image library (ADR 0027). The test harness uses the real one, since it drains the worker's jobs.

### Serving

`/_media/<name>` on the Site's own domain (its Staging address for now) answers the Site's originals and variants by name, never a raw upload and never another Site's file. A name is the first 16 hexadecimal characters of the file's SHA-256 and a readable name: `3f9a1c2b7d4e5f60-sourdough-loaf.jpg`, `…-sourdough-loaf-640.avif`. So a name always holds the same bytes: `Cache-Control: public, max-age=31536000, immutable`, a strong `ETag` (the hash; `If-None-Match` gets 304), `X-Content-Type-Options: nosniff`, the stored `Content-Type`, `Accept-Ranges: bytes` with single byte ranges (206, 416), and `X-Robots-Tag: noindex` on a Staging address. The page cache never keeps them. The admin shows the same files at `/api/media/<site id>/<name>` on the admin host, only to signed-in people who reach the Site (`private` caching), so previews work whether or not the Site has an address.

### The library

- `media.list` (newest first; a folder, `none` for files in no folder; a search over file name, title and alt text in any language; a kind; `limit`, `offset`), `media.get`, `media.update` and `media.folders.list`, `create`, `rename`, `delete`. Folder names are unique on the Site whatever their case; deleting a folder keeps its files, in no folder.
- **Title, alt text and caption** are stored per language like Entry values (`{ values: { alt: { en: { value, by } } } }`, ADR 0003), in any of the Site's languages (`language` on `media.get`, `list` and `update`), falling back to the Default language one text at a time. They change at once, with no Draft, and clear the page cache: published pages show new alt text immediately. The Focal point comes with #77.
- **Who changes what**: everyone who reaches the Site sees the library and uploads to it; Authors change only their own uploads (`FORBIDDEN` otherwise), Editors, Owners and Staff every file and the folders. Each item says `canEdit` for the person asking.
- Trash, Used in, Replace file, quotas, SVG cleaning and Import from URL are #77.

### Media on pages

An `<img>` whose `src` reads `media:<id>`, written as fixed text in a Template or read from a media Field (Templates read a media Field as `media:<id>`), renders as a Media image (`packages/renderer/src/media.ts`):

```html
<picture>
  <source type="image/avif" srcset="/_media/…-320.avif 320w, /_media/…-640.avif 640w" sizes="(min-width: 800px) 800px, 100vw">
  <source type="image/webp" srcset="…" sizes="…">
  <img src="/_media/…-croissants.jpg" alt="…" width="800" height="400" loading="lazy">
</picture>
```

- `alt` is the Template's own when it gives one (`alt=""` makes it Decorative), else the Media library's in the page's language, else empty. `width` and `height` are the original's, or the Template's (one of them scales the other). `sizes` is the Template's, or made from the width shown. The Template's other attributes and Classes stay on the `<img>`.
- The first Media image of the page's content (inside the Site template's `<main>`, at its outlet) loads with `loading="eager" fetchpriority="high"`; every other one, the Site template's own included, `loading="lazy"`. A Template's own `loading` or `fetchpriority` wins, and a first image the Template makes lazy gets no high priority.
- Before variants exist, the `<img>` comes alone; before the original is cleaned, or for an id that isn't one of the Site's ready images, nothing renders. In any other URL attribute (`href`, a video's `src`), `media:<id>` becomes the file's address.
- Template markup writes it as it is stored, `<img src="media:<id>">`: the parser checks the id's form only (a file can be deleted later, so it isn't looked up), and `{{ photo }}` in an `src` reads a media Field the same way.
## Template markup

Template markup (`packages/renderer/src/markup/`, ADR 0017) is the one written form of element trees, for Code mode, the builder's code view, files, MCP, the CLI and imports. It is never stored: `parseTemplateMarkup(markup, options)` reads it into a canonical tree and `printTemplateMarkup(tree, options)` writes a tree as markup. Printing then parsing gives the same tree, for every setting (`tests/markup/round-trip.test.ts` checks it by hand and over generated trees).

```html
<article class="card" aria-label="Post" data-wc-id="Xb3kP9a2Lm4Q">
  <h1 data-wc-id="Q9zT2b7Rk1Wd">{{ title | truncate: 80 }}</h1>
  <!-- Comments stay in the markup and the tree; visitors never get them. -->
  {{@if summary and status != "draft"}}<p data-wc-id="r5Hs8Kq0Zx3N">{{ summary }}</p>
  {{@else if author}}<p data-wc-id="m2Lp7Vd4Ty9C">By {{ author }}</p>
  {{@else}}<p data-wc-id="w8Bn1Fj6Gu5E">Write \{{ summary }} to show the summary.</p>{{/if}}
  <time datetime="{{ publishedAt | date: datetime }}" data-wc-id="c3Xr9Ma1Pq7S">{{ publishedAt | date: long }}</time>
</article>
```

- **Element ids** are written as `data-wc-id`, always last. An element written without one gets a new id; when two elements carry the same id (a copied element), the first keeps it and the copy gets a new one, with a notice. Other `data-wc-` attributes are WebCraft's.
- **Classes** are written by name in `class` (printed first) and stored by id; a name the Site doesn't have is refused. An inline `style` is read strictly (declarations only, safe `url()`s) and becomes a **generated Class** (`style-` and a hash of the canonical declarations, so the same style finds the same Class), with a notice; pages never carry inline styles. Names come from the Draft of the Design system: its Classes and its token utilities (`classCatalogue`, `packages/core/src/design-system/classes.ts`). The inline style is checked like any CSS of the Design system (no addresses on other hosts, no `!important`) and the generated Class joins the Design system's Draft; it goes live with the Template that made it (see "The Design system").
- **Values**: `{{ path }}` or `{{ path | formatter }}`, in text and inside attribute values. Formatters are a fixed set (`packages/renderer/src/formatters.ts`): `date` (`short`, `medium` (the default), `long`, `full`, `time`, `iso`, `datetime`; in the page's language, in UTC until Sites have a time zone), `number` (optionally `number: 2` decimals) and `truncate: <length>` (cut at a word, then `…`). Which paths are known depends on the kind of Template (`isKnownValue`): an Entry template reads the built-in Fields, its Post Type's Fields and their parts, and the Globals (`site.x`; see "What a binding reads"); inside a Component its Props (`props.x`) and the Globals; Loop items (`item.x`) become known where they exist.
- **Fixed text in other languages**: `{{ "Read more" fr: "Lire la suite" pt-BR: "Leia mais" }}`, in text and inside attribute values: the text as written in double quotes, then each language's (`\"` for a quote, `\\` for a backslash, `\r` for a carriage return). It is a text node with `translations` (see "Languages"); the printer writes the languages in alphabetical order, and plain text without other languages as plain text. A language tag WebCraft doesn't keep, or one given twice, is refused where it is.
- **Escaping**: text prints `&`, `<` and `>` as references; `\{{` is a literal `{{` (the printer writes `{{` in text that way), and a `{` or `\` at the end of text prints as `&#123;` / `&#92;` so it can't run into a following `{{`. Whitespace is kept exactly: the printer adds none, so a file pulled, edited and saved shows only your changes.
- **Strict HTML**: every element needs its end tag (`<br>` and other void elements have none, `<br/>` is fine), nothing a browser would repair is accepted, and doctypes, `<script>`, `<style>`, `<meta>`, `on…` attributes and values in tag names, attribute names, `style`, `class`, `srcdoc` and `on…` are refused. A `media:` address must be `media:<id>` (see "Media on pages"). PascalCase tags place Components (see "Components"); the reserved commands are refused until their tickets.
- **Rules by kind of Template**: besides `isKnownValue` and `refuseElement`, a kind of Template gives `refuseCommand` (a command it can't hold: Entry templates refuse `{{@outlet}}`) and `checkTree` (rules about the whole tree once it is read, such as the Site template's one `<main>` and one outlet). Both parsers take them and report each problem where its node is.
- **Problems and notices**: `TemplateMarkupInvalidError` lists up to 20 problems, each `{ line, column, message }`; the API answers it as `TEMPLATE_MARKUP_INVALID` with `data.problems`. A save that works answers `notices` in the same shape.
- **API**: `templates.getEntryTemplateMarkup({ siteId, postTypeId })` answers `{ template, markup: { draft, published }, version }` (all null without a template); `templates.saveEntryTemplateMarkup({ siteId, postTypeId, markup, basedOn? })` saves the Draft (creating the template) and answers `{ template, markup, version, notices }`, the markup as stored now. With `basedOn` (the version it was made from, null for none yet), a save over a Draft someone changed meanwhile is refused with `CHANGED_MEANWHILE` and the version now in `data.version`. Both need `structure.edit`; `getSiteTemplateMarkup` and `saveSiteTemplateMarkup` do the same for the Site template. In core, `services.templates.entryTemplateMarkup` and `saveEntryTemplateMarkup` (`content/templates.ts`).

### Template commands and Conditions

`{{@name …}} … {{/name}}` blocks are **Template commands**, each one entry in `TEMPLATE_COMMANDS` (`packages/renderer/src/commands.ts`): its name, its node type, whether it is a block, the branch keywords allowed inside it (`else if`, `else`; a Loop's `empty`), the `snippet` Code mode's `{{@` menu inserts (`$0` where the caret goes), and how it reads from markup, prints, is checked as a stored node, lists its children and renders. The parser and printer handle every command through the registry, so **adding a command** is: a node type in the `TreeNode` union, an entry in `TEMPLATE_COMMANDS`, and removing its name from `RESERVED_COMMANDS` (`loop`, `empty`, `pagination`, `form`, `filter`, `popup`, refused until their tickets). A kind of Template that can't hold a command refuses it with `refuseCommand`.

`{{@outlet}}` is the content outlet: where the Site template shows each page's content. It takes nothing, holds nothing, and renders the page's content, already rendered (`RenderOptions.outlet`); only the Site template holds it, once (see "The Site template").

`{{@themeToggle}}` is the theme toggle: a button that switches the page between the Design system's light and dark values (see "The Design system"). It takes nothing, can't sit inside a link, a button or another control (`placementProblem`, which both parsers call), and renders only while the Site's published Design system has dark mode.

`{{@languageSwitcher}}` is the Language switcher: links to the page in each of the Site's languages (see "Languages"). It takes nothing, renders a `<nav>` and so can't sit inside a link, a control, a paragraph, a heading or inline text, nor directly in a list, and renders nothing on a Site with one language.

`{{@if}}` / `{{@else if}}` / `{{@else}}` is a Condition. Its tests are stored as data (`Expression` in `packages/renderer/src/expressions.ts`) and run by WebCraft's own interpreter, never `eval`: a value on its own passes when it isn't empty (blank text, false and empty rich text are empty; 0 is a value), `==` and `!=` compare (a number as a number, true/false as yes or no, otherwise as text; empty equals `""`), with `not`, `and`, `or` and brackets, and literals `"text"`, numbers, `true` and `false`. #62 adds compare, contains, language, date window and Loop position as more operators and kinds there. A test nests at most 32 deep.

### Rich text

`cleanRichText(html)` (`packages/renderer/src/rich-text.ts`) parses with parse5 (the HTML standard's algorithm, in a `<div>`'s context, as a browser would) and writes back only the allowlist: `p`, `br`, `strong`, `b`, `em`, `i`, `u`, `s`, `sub`, `sup`, `code`, `mark`, `small`, `ul`, `ol`, `li`, `blockquote`, and `a` with `href` (safe schemes only) and `title`. Scripts, styles, embeds, SVG, MathML, forms and comments go with their content; other elements keep their text. Nothing is matched with regular expressions, and the output is the cleaner's own, so cleaning clean rich text changes nothing. The rich text Field type (`content/field-types.ts`) cleans values on save (rich text with no text left is empty; at most 20,000 characters of cleaned HTML), and the renderer cleans them again on render.

### What a binding reads

`content/render-values.ts` works out what a binding's path names on a page (`entryParts`, `resolvePath`), and which paths a template may hold (`knownValues`, checked on save and on publish):

- a built-in Field or a Field of the Post Type: `summary`, `price`;
- a part of a Field: a Group's Field (`address.city`), a Repeater's Field across its rows (`team.name`: each row's name, a list), a link's `url` or `text`, a select's `value` or `label`, a body's `excerpt`, `image`, `reading_time` and `toc` (see "The Body field");
- what a Relationship points at, one level deep: the published Entries' `title`, `slug`, `url` (from their Post Type's URL pattern; a Page's path for a Page), dates (as dates, for the `date` formatter) and Fields (`category.title`, `category.url`, `authors.bio`); unpublished Entries are left out;
- `site.x`: the published Globals (`site.phone`, `site.address.city`).

On its own a select shows its label, a link its text (or its address), a Relationship its Entries' titles, rich text its cleaned HTML, a body its Blocks as HTML, true/false `true` or `false` (Conditions test them as they are); Groups and Repeater rows show nothing, and a media Field reads as `media:<id>` (see "Media on pages"). A list (a multi-select, a Repeater's Field, a multi-Relationship) shows its values joined with commas until Loops (#62) show them one by one.

## The Design system

Each Site's Design system (ADR 0009) is its Design tokens, Classes, base styles, custom CSS and dark mode setting. It is Structure (`structure.edit`, Staff only), has a Draft and a published version, and is published as one item. The pure parts (the document, tokens, colour ramps, CSS checking, the compiler, DTCG files, the theme toggle's script) are in `packages/renderer/src/design-system/`; storage, usage, publishing and the Site's stylesheet in `packages/core/src/design-system/`.

- **Storage**: one `design_systems` row per Site holds the Draft and the published version as documents (`DesignSystem`), made the first time the Site changes it. Until then the Draft is the default one (`defaultDesignSystem()`), and until the first publish visitors see the default one. Every change locks the row (`lockDesignSystem`). Sections a stored document lacks read as the default ones (`readDesignSystem`), which is how the Classes #58 made were moved in by a custom migration.
- **Tokens** (`tokens.ts`, `colour.ts`): colours, the space and text scales, fonts, radius, shadows, breakpoints, content widths and the focus style. Each has an id that never changes and a name, and becomes custom properties in the stylesheet's `tokens` layer: `--<colour>-<step>`, `--space-<step>`, `--text-<step>`, `--font-<name>`, `--radius-<name>`, `--shadow-<name>`, `--width-<name>` (breakpoints are used by Classes instead). A colour is one base colour; its shades (10, the lightest, to 95; the base is 60) are worked out in OKLCH and its transparencies (`a10` to `a90`) from the base, and any shade but 60 can be given its own value. Dark values run along the same steps the other way (10 stays the page's background end) from a dark base colour, the light one unless set, with dark overrides of their own: Light/Dark is one set of ramps. Scale steps are `base × ratio^exponent` at the smallest and the largest viewport (360 and 1440 px by default), written as `clamp()` in between; any step can be given its own sizes. The smallest named breakpoint is where phones end (768 px by default).
- **Classes**: `{ id, name, generated, styles, breakpoints, css }`. `styles` are declarations for every width, `breakpoints` declarations from a breakpoint's width up (by the breakpoint's id), `css` the Class's own custom CSS, declarations and rules nested with `&`. Names are unique on the Site, never the name of a token utility, and never start with `wc-` (`isReservedName`: WebCraft's own classes, `wc-skip-link`, `wc-theme-toggle`). Elements store Classes by id, so a rename changes every page once published.
- **Token utilities**: one-declaration classes the tokens make (`bg-primary-10`, `p-m`, `text-xl`, `radius-m`, `shadow-s`, `max-width-content`, …, `UTILITIES`). Elements name them like Classes and store them by an id made from the token's id (`u:bg:colour-primary:10`), so renaming a token renames its utilities everywhere.
- **CSS as stored** (`css.ts`): every piece of CSS (Class styles, breakpoint styles, a Class's own CSS, base styles, the Site's custom CSS, later a Component's) is read with css-tree before it is saved, and each problem has its line and column: syntax, unknown properties, values a property doesn't take (values with `var()` are left to the browser), at-rules out of place, `!important` (layers make it unnecessary), `@import`, `@layer`, `@charset`, `@namespace`, properties that only ever ran script, and any address outside the Site (`url()`, `image-set()`, `src()`, in custom property values too, escaped names read as CSS reads them): only paths such as `/_media/…` and `#ids`. It is stored as written, with each `--token` and each `.class` in a selector kept by id (`CssText`); printing writes today's names, so a rename changes every use. When a save sends CSS text unchanged from what it read, the stored references are kept, even if a name changed in the same save.
- **In use**: deleting a Class, or removing a token, that an element tree (any Template's or Component's Draft or published version) or the Design system's own CSS, focus style or breakpoint styles uses is refused with `CLASS_IN_USE` / `TOKEN_IN_USE` and `data.usedBy`, each use saying where (`usage.ts`: `treeSources` reads Templates and Components; Popups add theirs).
- **Template markup** reads Class and utility names from the Draft (`classCatalogue`). Saving and publishing a Template check its Class ids against the Draft. Visitors see a Class's name and styles once the Design system is published, except generated Classes, which go live with the Template that made them (`publishGeneratedClasses`): a one-off style shows with its Template; a Class Staff made or changed waits for the Design system.
- **The stylesheet** (`compileStylesheet`, `core/design-system/stylesheet.ts`): one per Site, built from what it has published: the published Design system (the default one before) and the Classes and utilities its published trees use, nothing else. Its cascade layers are declared first, `reset, tokens, base, classes, utilities, custom`, so later layers win whatever their selectors: `reset` (box sizing, media, `[hidden]` always hidden, reduced motion), `tokens` (`:root` custom properties, and dark values when dark mode is on), `base` (the focus style's custom properties from the focus token, base styles of plain elements, the skip link, the theme toggle, a body's callouts and videos: the info tone follows the primary colour token by id, the others have their own colours until custom CSS sets the `--wc-callout-*` properties), `classes` (Class styles, then each breakpoint's from the smallest up), `utilities`, `custom` (Classes' own CSS, Components' (#63, `StylesheetUse.componentCss`), then the Site's). Everything is written out by the parser from the stored CSS, never pasted, so nothing can end a layer early; each piece is checked again as it is built, and one that fails the checks is left out (`buildCss`), so CSS stored before the checks existed (Classes moved from the earlier `classes` table) never reaches a stylesheet unchecked. It is served at `/_wc/css/<16 hex digits of its SHA-256>.css` from the Site's domain with `Cache-Control: public, max-age=31536000, immutable`, an ETag and `nosniff`; its name changes whenever what it holds changes. The same published data always builds the same file, so every web process agrees on it; each process keeps a Site's built styles for the Site's page cache generation. Publishing a Template or the Design system keeps the stylesheet it replaced in `stylesheets` for 30 days (`RETIRED_STYLESHEET_LIFETIME_MS`), so a page loaded just before still finds its file; such publishes take the Design system's row lock before reading the current stylesheet, so two at once take turns and neither loses the one the other made. Paths are `/_wc/…`, never naming WebCraft, since Site output stays unbranded.
- **Base styles** (`BASE_TARGETS`): `body`, headings, paragraphs, links, lists, tables and the rest, from tokens; links in `<nav>` are at least 24 px so lists of links are big enough to tap (WCAG 2.5.8). Staff can change them; the defaults pass axe in light and dark.
- **Dark mode** (`darkMode`): off by default. With it on, pages say `<meta name="color-scheme" content="light dark">` and the dark values apply under `prefers-color-scheme: dark`, unless the visitor chose light with the theme toggle (`data-wc-theme` on `<html>`), and whenever they chose dark.
- **The theme toggle** (`{{@themeToggle}}`): a `<button class="wc-theme-toggle" aria-pressed hidden>` in the page's language. Pages never carry inline scripts (ADR 0023), so its script is a file, `/_wc/js/<hash>.js` (`THEME_TOGGLE_SCRIPT`), linked in `<head>` only from pages that show a toggle; it applies the stored choice (`localStorage` `wc-theme`) before the page shows, unhides the toggles and keeps `aria-pressed` true to the theme on screen. Without dark mode the toggle renders nothing and no script is linked.
- **DTCG files** (`dtcg.ts`): `designSystem.exportTokens` writes the tokens as DTCG 2025.10 JSON (every shade and transparency, each step's size at the smallest viewport, `$type` per group, the focus style as aliases such as `{color.primary.70}`), WebCraft's own details (ids, base colours, overrides, dark values, ratios, fluid ranges) under `$extensions.webcraft`; importing an export gives back the same tokens. `designSystem.importTokens` also reads files from other tools (plain colour tokens, hex strings or DTCG colour objects, `"16px"` or `{ value, unit }`): each top-level group it holds replaces that kind of token, kinds it leaves out stay, and a token keeps its id by `$extensions.webcraft.id`, else by name. A file it can't read is `TOKENS_FILE_INVALID` with `data.problems`.
- **API** (all `structure.edit`): `designSystem.get` (Draft and published, CSS as text with today's names, `status`), `saveDraft` (sections `tokens`, `classes`, `baseStyles`, `customCss`, `darkMode`; each given replaces that section, `classes` being every Class in order; tokens without an id are new), `createClass`, `updateClass` (rename or restyle), `deleteClass`, `exportTokens`, `importTokens` and `publish` (through `publishing.publish` with `{ kind: "designSystem" }`, clearing the page cache, logged as `designSystem.publish`). A Draft that can't be saved is `DESIGN_SYSTEM_INVALID` with `data.problems`, each `{ at, message, line?, column? }` (`at` such as `customCss`, `classes[2].styles`, `tokens.colours[0].light.base`).
- **Seams for later tickets**: Components' trees are in `publishedTrees` (`stylesheet.ts`) and `treeSources` (`usage.ts`), and a Component's generated Classes go live with it; Component custom CSS (stored with the Component's version, published with it) goes into `StylesheetUse.componentCss`; Code mode (#76) shows the Draft with `draftStyles` (`compileStylesheet(draft, { classIds })` over the Draft trees) and saves Class CSS and the Site CSS through `changeDraft`; the Design system screen is #65.

## Migrations

Migrations are drizzle-kit files in `packages/db/src/migrations`, applied by their own `migrate` step (ADR 0031), never by web or worker at start-up.

- Change the schema in `packages/db/src/schema/` (one file per area, re-exported from `index.ts`), then `bun run db:generate`. Commit the generated folder.
- Hand-written SQL (functions, triggers, data fixes) goes in its own custom migration: `bun run db:generate --custom --name=<what-it-does>`. Keeping it separate means a regenerated schema migration never loses it.
- Every change keeps the previous version working on the new schema: add first, remove in a later release. There are no down-migrations.
- `webcraft admin migrate` applies pending migrations in one transaction, then installs or upgrades the job queue (pg-boss) schema. Web and worker check both at start-up and refuse to run on a database that is behind; `/readyz` reports the same check.
- **Module migrations** run in the same step, after WebCraft's own (see "Modules › Tables and migrations"): each Module's pending SQL in its own schema, all in one transaction, recorded in `module_migrations` with a checksum. The schema check counts a pending Module migration as behind. `runMigrations`, `checkSchema` and `assertSchemaCurrent` take the build's Modules as `{ modules: moduleSchemas(FIRST_PARTY_MODULES) }`; `services.modules.schemas` holds the Install's.
- When two branches both add migrations, keep the integration branch's and regenerate yours on top with `bun run db:generate`. Git often merges two such migrations without a conflict, but both were generated from the same parent, so the newer snapshot misses the other's tables and the next `db:generate` would write them again. `tests/db/migration-chain.test.ts` fails when that happens: delete your migration's folder and generate it again (a custom one: recreate it with `--custom` and paste its SQL back).

## Jobs

Jobs are defined with `defineJob({ name, payload, queue, run })` (in `packages/core/src/jobs/`, or next to their module, such as `email/outbox.ts`) and listed in `coreJobs` (`packages/core/src/jobs/index.ts`); the worker only works listed jobs. `sample-ping.ts` is the sample to copy.

- `name` is the queue name, `area.action` (`email.send`). Never rename one that has shipped.
- `payload` is a Zod schema; it is checked when the job is sent and again when it runs.
- `queue` holds retry and expiry settings (`retryLimit`, `retryDelay`, `retryBackoff`, ...).
- `run(payload, services)` gets the same `InstallServices` as the web process: use `services.clock`, `services.http` and `services.log`, never `Date.now()`, `fetch` or `console` directly. To email someone, send a System email (see "Email"); never call `services.mailer`.
- Enqueue with `services.jobs.send(job, payload, { startAfter })`.
- A job that works on one Site's data opens it with `services.data.background(siteId)` (see "The tenant data layer"); `media.process` and `media.variants` are the examples.
- **Scheduled jobs**: `defineSchedule({ job, cron, payload })`, listed in `coreSchedules` (so far the daily `email.purge-log`, `rate-limits.purge`, `modules.purge-log` and `site-files.purge`, `domains.verify-due` every minute and the hourly `domains.check-all`). `cron` is read in UTC (`17 3 * * *` is every day at 03:17). The worker registers every listed schedule when it starts (and removes ones no longer listed); when it was down at a due time, the job runs once when it is back. The test harness's `drainJobs()` sends each scheduled job whose time came by the test clock since the last drain.

## Email

Everything about email is in `packages/core/src/email/`, behind `services.email`. Nothing else calls the `Mailer`: every email goes through the System email sender, which records it in the Email log and queues it.

**Sending a System email** (an email to a person with an account, or to an address about to get one, such as an invite):

```ts
await services.email.send({
	type: "review-submitted",                       // from the catalogue
	to: [{ personId }, { email: "new@client.example", language: "it" }],
	data: { authorName, itemTitle, siteName, reviewPath: `/sites/${siteId}/review/${id}` },
	related: { kind: "entry", id },                  // what the Email log links to
});
// → [{ recipient, status: "queued" | "logged" | "turned-off", emailId }]
```

- **The catalogue** (`email/catalogue.ts`) lists every System email type with its category and a Zod schema of its data. `security` emails (invites, resets, sign-in changes) always go; each `work` and `alert` type can be turned off by each person in Your account › Emails, and is then skipped for them (`turned-off`). Add a type to the catalogue, its wording to `email/wording/en.ts` and `it.ts` (a missing one fails the typecheck), and its name (and, for work and alert types, a description) under `emailTypes` in the admin's message files. Never rename a type that shipped.
- **Links** in data are admin paths (`/invites/abc`), never full URLs: the sender puts the admin's origin in front, so System emails only ever link into the admin.
- **Language and layout**: each recipient gets the email in their Admin language (a bare address: the `language` given, else the Install's default), in one built-in layout (`email/layout.ts`: logo or sender name on a bar in the accent colour, heading, paragraphs, one button, footer), under **Install branding** (Install settings › Email (SMTP): sender name, logo address, accent colour, footer text). Every value is escaped. Work and alert emails link to the person's switches.
- **Which SMTP**: each queued email names its SMTP (`SmtpChoice` in `email/outbox.ts`). System emails always use the Install SMTP; a Site's own SMTP becomes another choice with Site mail. The Install SMTP password is the Install secret `smtp.password`, filled in only for the send.
- **No SMTP yet**: until the Superadmin sets the Install SMTP, the email is written to the log (`warn`, with `to`, `subject` and `text`) instead of being sent, and the Email log says "Written to the log".
- **Delivery and retries**: the `email.send` job sends it. A failed attempt is tried again after 1 minute, then a wait that doubles up to 4 hours, until 24 hours after it was queued; then it is Failed. An address the server refuses for good (a 5xx answer to `RCPT TO`) is Failed at once. Completed `email.send` jobs, which hold the body, are deleted after an hour. Delivery is at least once: if the server takes an email but recording that fails, the job is retried and the email can go out twice. Every attempt carries the same `Message-ID` (`<Email log line id@sender's domain>`), so mail clients can drop the copy; losing an email (a password reset, an invite) would be worse than a rare duplicate.
- **Failing**: 3 failed sends in a row make the SMTP Failing: logged as an error, shown in Install settings › Email (SMTP) and as a notice on every admin page for the Superadmin (an email about a failing Install SMTP would go through it). A send that goes through, or saving new settings, clears it. Test emails don't count.
- **Test email**: `services.email.sendTest` sends at once through settings that may not be saved yet, and answers the server's reply.
- **The Email log** keeps time, type, recipient, subject, SMTP, status (Queued, Retrying, Sent, Failed, Written to the log), attempts, the server's last answer and the related item, never the body. The `email.purge-log` job deletes lines older than 90 days every day.
- **The Mailer** (`email/mailer.ts`) is the edge: `send(email, smtp)` over SMTP with Nodemailer (`email/smtp-mailer.ts`), rejecting with `SmtpDeliveryError` (the server's answer, and whether it refused the recipient for good).
- **Who manages it**: the Install SMTP, Install branding and the Email log procedures (`packages/api/src/procedures/email.ts`) are for the Superadmin, through one gate at the top of that file (`emailAdmin`). Changing the SMTP is a Sensitive action (`installSmtp.change`, see "Sensitive actions") and is recorded in the Audit log, never with the password.

## Secrets and the Master key

Every secret (SMTP passwords, AI keys, CDN tokens, Webhook and CAPTCHA secrets) goes through `services.secrets` (`packages/core/src/secrets/`). Secrets are write-only: code gets a value only inside a callback, and people see only "set" and its last 4 characters.

```ts
const password = { owner: { kind: "install" }, name: "smtp.password" } as const;

await services.secrets.set(password, value);                      // stores or replaces it
await services.secrets.useWith(password, (value) => smtp.login(user, value));
await services.secrets.describe(password);                        // { set: true, lastFour: "…", updatedAt } or { set: false }
await services.secrets.remove(password);
```

- **Owners**: a secret belongs to the Install (`{ kind: "install" }`: Install SMTP, shared AI keys), a Workspace (its AI key) or a Site (its SMTP, CDN token, Webhook and CAPTCHA secrets). `services.secrets` holds the Install's own; a Workspace's or Site's are reached only through the data layer, `workspace.secrets.set("ai.key", value)`, so code can't name another Workspace's secret (see "The tenant data layer"). They have foreign keys to their Workspace and Site, and go when it is deleted. A name is unique within its owner: 1 to 200 letters, digits and `.:_-`, such as `smtp.password` or `webhook:<id>:signing`.
- **No read-back**: there is no function that returns a value. `useWith` refuses a callback that returns the value (or a string holding it), so fill the secret into the call inside the callback and return the call's result. Never log a value, put it in a job payload or send it to the browser. `describe` shows no characters of a secret shorter than 16 characters, so never more than a quarter of one shows.
- **Errors**: `useWith` throws `SecretNotSetError` for a secret nobody set, and `useWith` and `describe` throw `SecretUnreadableError` for one that was changed outside WebCraft. Messages name the secret, never its value.
- **Encryption**: AES-256-GCM, with a random 12-byte nonce per value, under a key derived with HKDF-SHA256 from the Master key and the secret's key version. The authenticated data binds each ciphertext to its owner and name, so a ciphertext copied into another row can't be decrypted there. Only Web Crypto is used, so the same code runs on Bun and Node.
- **Key versions**: the table `master_key_versions` holds the fingerprint of every Master key the Install has had (never a key). The Install's first secret records its key as version 1; each rotation adds the next. Every secret stores the version it is encrypted under.
- **Fingerprint**: `masterKey.fingerprint()` (a `MasterKey` comes from `loadMasterKey(env)` or `parseMasterKey(value, source)`) is a one-way value, 64 hexadecimal characters, safe to store and show. Backup manifests carry it, and restore compares it with the running key (ADR 0032).
- **Start-up**: web and worker read the key with `loadMasterKey`, then open secrets with `openSecrets`, which refuses a key that isn't the Install's current one. An Install with no secrets yet accepts any key.

### Rotating the Master key

`webcraft admin rotate-key` decrypts every secret with the old key and encrypts it again under the new key as the next key version, in one transaction. If any secret can't be decrypted, nothing changes and the command lists it. The new key goes where web and worker will read it from afterwards, `WEBCRAFT_SECRET_KEY`; the key being replaced is passed once, in `WEBCRAFT_OLD_SECRET_KEY` or a file.

1. Make the new key: `openssl rand -base64 32`. Store a copy outside the server.
2. Stop web and worker.
3. Put the new key in `WEBCRAFT_SECRET_KEY` in the Install's environment.
4. Run the command in that environment, with the old key:

   ```sh
   WEBCRAFT_OLD_SECRET_KEY='<old key>' webcraft admin rotate-key
   # or: webcraft admin rotate-key --old-key-file /run/secrets/old-master-key
   ```

   It prints how many secrets it re-encrypted, the new key version and the new key's fingerprint.
5. Start web and worker. Then remove the old key from wherever you passed it; it opens nothing any more.

Running the command again after it finished changes nothing. It refuses a new key the Install used before, and an old key that isn't the current one. Web or worker left running with the old key can no longer read or write secrets, and both refuse to start again until they have the new key, naming the key version they need.

### When the Master key is lost

Secrets can't be recovered without their Master key, and web and worker refuse to start with any other key while secrets exist. To start again with a new key, deleting every secret:

1. Make a new key with `openssl rand -base64 32` and put it in `WEBCRAFT_SECRET_KEY`.
2. `webcraft admin rotate-key --old-key-lost` lists the secrets that would be deleted and the lost key's version and fingerprint, and changes nothing. If you still have the old key, or mistyped the new one, stop here and rotate normally.
3. `webcraft admin rotate-key --old-key-lost --confirm-fingerprint <first 12 characters of that fingerprint>` deletes them and makes the new key the next key version. Typing the fingerprint proves you read the listing for this Install; a bare "yes" would not. It refuses when `WEBCRAFT_SECRET_KEY` is still the current key.
4. Start web and worker, and set the listed secrets again.

## Outgoing calls and the guarded fetcher

`services.http` (`OutgoingHttp`) is WebCraft's one way to other servers: `(Request, { connectTo? }) => Promise<Response>`, faked in tests. Calls to hosts someone else chose (a Module's outside hosts, Domain verification and the Domain check, Library downloads; later CAPTCHA verification, Webhooks, Import from URL, AI providers) go through the **guarded fetcher** on top of it (`createGuardedFetch({ http, dns })`, `packages/core/src/guarded-fetch.ts`):

- only `http` and `https` URLs without credentials, on the hosts allowed (`allowedHosts`);
- the host is resolved first through the `Dns` port (`services.dns`; `systemDns` in the processes, `install.dns` in tests) and refused when any address is loopback, private, link-local, shared (CGNAT), multicast, reserved, documentation or benchmarking space (`isPublicAddress`, IPv4 and IPv6, IPv4 inside IPv6 and NAT64 included); the same after every redirect;
- the call is **pinned to the address checked**: outgoing HTTP gets the first address the host resolved to as `connectTo` and connects there, never resolving the name again, so a DNS server that answers the check with a public address and the connection with an internal one (DNS rebinding) can't reach inside the network; each redirect is checked and pinned again;
- at most 3 redirects (`maxRedirects: 0` hands a redirect back without following it); 303, and 301/302 after a POST, become a GET;
- a timeout (10 s by default, 30 s at most) and a size limit (5 MB, 20 MB at most): the body is read in full, and a larger one is refused.

`installAddresses` lets one caller, the Install's checks of its own domains, also call the Install's own addresses although they aren't public (see "Domains"); nothing else passes it. Refusals throw `GuardedFetchError` with `problem` (`scheme`, `host`, `address`, `redirects`, `timeout`, `size`, `unreachable`).

Each process has its own outgoing HTTP, wired in `openInstall` (`openInstallForCommand` uses the web one):

- **Web and server commands (Bun)**: `createBunHttp()` (`packages/core/src/http-bun.ts`). A pinned call is Bun's `fetch` to the address as the URL's host, with the URL's host name in the `Host` header and as `tls.serverName`, which Bun sends for SNI and checks the certificate against.
- **Worker (Node)**: `createNodeHttp()` (`packages/core/src/http-node.ts`). A pinned call goes over `node:http`/`node:https` with `host` set to the address and the host name as `servername`, which Node sends for SNI and checks the certificate against (a custom `checkServerIdentity` would stop Node reusing connections); the body streams as it arrives, decoded (gzip, deflate, br) as `fetch` decodes it.

On both, the certificate must be valid for the host name, never for the address (an address in the URL is checked as an address); a kept connection is reused only for the same address and host name; a pinned call never follows a redirect itself (the guarded fetcher does, checking each hop), and its timeout and size limit are the guarded fetcher's (the call stops when its signal fires; the body is read as it streams). A call without `connectTo` (S3 storage, the leaked-password check, the sample job) is the runtime's own `fetch`, as before. Each adapter refuses to start on the other runtime. `ca` (`createBunHttp({ ca })`) makes pinned calls trust a certificate authority a test made instead of the usual ones.

The guarded fetcher connects to the first address only; when it doesn't answer, the call is `unreachable` even if another address of the host would have. In development, `.localhost` names resolve to `::1` first on most systems, where `vite dev` listens.

## Modules

A Module is a self-contained feature that reaches WebCraft only through the Module SDK (ADRs 0012, 0024). v1 loads first-party Modules only, in the same process as Core; the boundary is built so that a sandbox later changes the runtime, not the API.

### The SDK and the boundary

`@webcraft/module-sdk` (`packages/module-sdk`) is the public, versioned contract (`SDK_VERSION`, the same as its package version; additions raise the minor version, a change that could break a Module the major one). It holds the manifest schema, `defineModule`, `procedure`, `siteRoute`, `job`, `component`, the table helpers, the event catalogue, the context types Module code gets, `ModuleError` and `ModuleRefusedError`, and re-exports what Modules need of Drizzle (column builders and comparison operators, never raw `sql`) and Zod, so every Module uses WebCraft's versions.

- **A Module imports nothing from WebCraft but the SDK**, and nothing that reaches around it: no `@webcraft/*` package, no Drizzle, Zod, `pg` or `pg-boss` of its own, no `node:` or `bun` modules, no `fetch`, `process`, `Bun`, `require` or `globalThis` globals. Biome refuses them in `modules/**` and `tests/modules/sample/**`; `tests/modules/boundary.test.ts` scans every Module's imports, globals and `package.json` too. A real Module package depends only on `@webcraft/module-sdk` (and its own outside packages), and Bun's isolated installs then can't resolve anything else of WebCraft's.
- **First-party Modules** are workspace packages, `modules/<id>`, each default-exporting a `defineModule(…)`, listed in `FIRST_PARTY_MODULES` (`packages/core/src/modules/first-party.ts`). Web, worker and the `migrate` step all load that list (`openInstall({ modules })` defaults to it).
- **The sample Module** (`tests/modules/sample/index.ts`, with the Workspace-level `board.ts`) uses every extension point and is the Module the host's tests drive; copy its shape.

### The manifest

```ts
export default defineModule({
	manifest: {
		id: "sample",                                    // lower-case words joined by dashes
		name: { en: "Sample notes", it: "Note di esempio" },
		description: { en: "…", it: "…" },
		version: "1.0.0",
		sdk: "^1.0.0",                                   // the SDK versions it works with
		level: "site",                                   // switched per Site, or "workspace"
		onByDefault: true,                               // on wherever Staff haven't switched it off
		adminLanguages: ["en", "it"],                    // every label in each; the first is the fallback
		permissions: [{ key: "notes.edit", label: { en: "Write notes", it: "…" }, roles: ["staff", "owner", "editor"] }],
		uses: ["email"],                                 // WebCraft services it uses
		outsideHosts: ["hooks.sample.example"],          // the only hosts it may call
		routePrefix: "sample",                           // its Site routes: /_wc/m/sample/…
		siteScript: null,                                // or the Consent category of the script it adds
	},
	// tables, migrations, procedures, siteRoutes, adminPages, events, jobs, components
});
```

The manifest is checked with Zod (`moduleManifestSchema`), and the whole definition against the SDK's rules, when the Install loads it (`loadModules` in `packages/core/src/modules/registry.ts`): the SDK range must include `SDK_VERSION`; ids and route prefixes are unique; labels come in exactly the declared languages; a procedure or admin page names a Permission the Module adds or one of WebCraft's checked at its level; tables are in the Module's own schema and follow the tenant rule; migrations sort oldest first; Site routes need a route prefix and a Site-level Module; events are in the catalogue; unknown extension points are refused. A Module that breaks a rule is listed on the Modules screen as `cannot-run`, with the reason, and never runs; the rest of the Install runs on.

### Approval (the consent screen)

Nothing a Module asks for is granted until the Superadmin approves it on Install settings › Modules (`modules.list`, `modules.approve`; Permission `module.approve`, held by the Superadmin only). Approving is a Sensitive action (`module.approve`) and is recorded in the Audit log with what it granted.

- **What a Module asks for** is a list of consent items (`consentItems`): `permission:<key>:<role>` for each role it gives one of its Permissions, `use:email`, `host:<host>`, `script:<category>`. The consent screen shows them in WebCraft's own words (the admin's message files, English and Italian), never the Module's, so a Module can't word what it asks for itself; only its Permissions' labels are its own.
- **An approval** (`module_approvals`) stores the version approved and the items granted. A later version that asks for nothing more runs on it; one that asks for more is `update-waiting`: off everywhere (its switches and data kept) until the Superadmin approves it, the new items marked. Only one version of a first-party Module's code exists in a build, so "held at the approved version" means off until approved.
- `modules.approve` names the version the screen showed: another version answers `MODULE_CHANGED`. `modules.withdraw` takes a Module back to waiting, off everywhere, data kept.
- **The setup wizard** ends with the Modules step: the Modules waiting for approval, ticked (all Modules WebCraft loads are first-party), each with what it asks for.

### Switches and removing data

Staff switch Site-level Modules on each Site and Workspace-level Modules on each Workspace (`modules.siteList`, `modules.setOnSite`, `modules.workspaceList`, `modules.setOnWorkspace`; Permission `module.manage`, held by Staff and the Superadmin). The switch is a row of `module_switches` (a Workspace table); without one, the Module's `onByDefault` applies, to later Sites too. A Module **runs** at a place when it is approved for this version and switched on there; only approved Modules can be switched on. Switching off keeps the Module's data.

**Removing a Module's data** (`modules.removeSiteData`, `modules.removeWorkspaceData`) takes two calls, through `askConfirmation`/`useConfirmation`: the first answers how many rows of each of its tables and how many of its secrets would go, and a confirmation id; the second deletes them (tables in reverse order of the definition's list, so list parents first), removes its secrets there and switches it off. It is logged as `module.removeData`.

### Extension points

- **Tables and migrations.** A Module's tables live in its own Postgres schema, `m_<id>` (dashes become underscores), declared with `moduleSchema(id).table(name, { ...siteColumns(), … })` (or `workspaceColumns()`). A Site table has `workspace_id` and `site_id` with `FOREIGN KEY (workspace_id, site_id) REFERENCES sites (workspace_id, id) ON DELETE CASCADE`; a Workspace table `workspace_id` with `REFERENCES workspaces (id) ON DELETE CASCADE`. Site-level Modules have Site tables only. Migrations are SQL in the definition (`{ name, sql }`, names sorting oldest first), run once each by the `migrate` step after WebCraft's own, with the Module's schema first on the search path. The step refuses, rolling everything back: a migration that changes anything outside the Module's schema (compared before and after through Postgres's catalog), changes or reads rows outside it (the transaction's own table statistics and locks, before and after; reading `sites` and `workspaces` and locking them, which foreign keys need, is allowed, changing them isn't), a table or view the Module doesn't declare, a table without its tenant key, a declared table or column the migrations never made (checked on every run, so the TypeScript and the SQL can't drift), and a migration that changed or disappeared after it was applied (by checksum). Never change a shipped migration: add one. The schema check counts pending Module migrations, so web and worker refuse to start until `migrate` ran them.
- **API procedures**, by name and in groups, become `m.<module id>.<name>` in the Management API (`adminRouter(services)` in `packages/api/src/module-router.ts`, built from the Install's Modules, served at `/api/rpc` and to the admin's own pages). Each takes `siteId` (Site-level) or `workspaceId` besides its own input, runs only where the Module runs (`MODULE_NOT_FOUND` otherwise), through `can()` with the Permission it names (`FORBIDDEN` with `data.permission`). A `ModuleError` it throws is its answer (`MODULE_ERROR` with its status and `data.code`); anything else is a failure: it goes to the Module log and the API answers `MODULE_FAILED` (500).
- **Permissions** a Module adds are named under its id (`sample.notes.edit`), checked at its level, and held by the Superadmin and the built-in roles it lists (ADR 0028).
- **Site routes** answer `/_wc/m/<route prefix>/<path>` on Sites where the Module runs: declared paths (`/notes`, `/notes/:id`) and methods only (405 with `Allow` for another method on a declared path, HEAD for GET routes), never cached as pages (`Cache-Control: no-store` unless the route sets its own), `X-Robots-Tag: noindex` on Staging addresses like every Site answer. A route never sees WebCraft's own cookies (`webcraft.*`, `isWebCraftCookie` in `packages/core/src/cookies.ts`) and can't set one: name every cookie WebCraft sets on a Site's domain (Edit mode's) `webcraft.<what>`. A route that throws answers the plain 500 and goes to the Module log.
- **Admin pages** (`adminPages: [{ path, label, permission }]`) join the sidebar of the Sites (or Workspaces) where the Module runs, for people holding their Permission (`sites.get` and `workspaces.get` answer them as `modulePages`), at `/sites/<id>/m/<module id>/<path>`. Their screens are registered in the admin's `MODULE_PAGES` (`apps/server/src/ui/modules/pages.tsx`) by the first-party Module that ships one; without one the page says so.
- **Events.** Modules react afterwards, as background jobs (ADR 0024): an Audit log entry the catalogue maps (`entry.publish` → `entry.published` with the Entry's `path` and the `pathChanges` the publish made, `entry.delete` → `entry.deleted`, `template.publish`, `globals.publish`) queues a `modules.event` job for each Module with a handler, once the change commits. The job runs only if the Module still runs there. Saving and publishing never wait for a Module and never fail because of one.
- **Jobs** of the Module's own (`jobs: { remind: job({ payload, run }) }`), queued with `context.jobs.send(name, payload, { delaySeconds })`, run as `modules.job` in the place they were queued from; payloads are JSON, checked when sent and when run. A job queued inside `context.transaction` is sent once it commits, never after a rollback.
- **Components** (SDK 1.1): `components: [component({ name, label, props, markup })]`, declarative: Props declared as Fields are (labels and help in each admin language; no Relationships, since each Site has its own Post Types) and output in Template markup reading only `props.x` (no Globals, Classes, inline styles or Components, which differ on every Site). Site-level Modules only. The Install checks them when it loads the Module (names unique across Modules); they get the id `<module id>:<Name>`, never change on a Site, and are placed like the Site's own Components, only on Sites where the Module runs (`services.modules.components`, the `ComponentSources` the content store reads). Approving, withdrawing or switching a Module that adds Components clears the page caches it changes; its Placements show nothing where it doesn't run. The consent screen lists them under what it adds. Never rename one that shipped.
- **Seams for later tickets**: `structurePresets` (#110), `blockTypes` (#103) and `widgets` are declared in the definition type and refused until their SDK version.

### What Module code gets

Procedures, Site routes, events and jobs get a `ModuleContext` (`packages/core/src/modules/runtime.ts`), limited to one place and to what the manifest declares; anything else throws `ModuleRefusedError` with a `reason` (`permission`, `table`, `host`, `use`, `job`, `secret`, `email`):

- `data`: its own tables in the place, through the data layer (`select`, `first`, `count`, `insert`, `update`, `delete`); the Workspace and Site are filled in, and any other table is refused. `transaction(work)` runs table changes and Audit log entries together.
- `audit(action, details)`: recorded under the Module's id. In a procedure the person acted (`via: admin`); elsewhere the Module did (`via: module`, no person).
- `email.send(message)` (needs `uses: ["email"]`): the `module-message` System email (a work email people can turn off), in the Module's words for each recipient's Admin language (else its first), in the built-in layout, recorded in the Email log.
- `http(url, options)`: the guarded fetcher, to its declared hosts only. When a call fails the Module gets WebCraft's own error (`GuardedFetchError` with its `problem`, or `ModuleRefusedError`), never the error behind it, which could name the address.
- `secrets`: `set`, `describe`, `remove` its own secrets in the place (stored as `module:<id>:<name>`), and `placeholder(name)`, which WebCraft replaces with the value inside an outgoing call (URL, header or body) to a declared host, percent-encoded in the URL (its path and query) so no character of it can change the address; Module code never sees a value, and a call carrying a secret never follows a redirect.
- `jobs.send`, `log.info/warn/error` (the Module log), `now()`, `module`, `place`; a procedure also gets `person` and `can(permission)`.

When a Module acts by itself it is a `ModuleActor` for `can()`, opening its place through the data layer like anyone.

### The Module log

`module_log` keeps what Modules wrote and every failure while they ran (a procedure, Site route, event or job that threw, an event that couldn't be queued), with the Workspace, Site and details (never a stack or a secret), 90 days (`modules.purge-log`, daily). The Superadmin reads it on Install settings › Modules (`modules.log`). A failed event or job is tried twice more; a refusal is logged and never retried, since the Module must change.

### Testing Modules

`createTestInstall({ modules: [sample, sampleBoard] })` loads Modules (this build's first-party Modules unless given); every test database has had `TEST_MODULES`' migrations (`tests/harness/modules.ts`: the first-party Modules and `SAMPLE_MODULES`). `tests/modules/first-party.test.ts` fails when a first-party Module can't run or its migrations break the step's rules. The isolation guard (`tests/isolation/procedures.test.ts`) lists every test Module's procedures too: add a line for each procedure a first-party Module adds. `moduleApi<typeof sample>(browser, "sample")` (`tests/harness/modules.ts`) calls a Module's procedures, typed from its definition (`ModuleApi` in the SDK). `install.restart({ modules })` runs another version; `install.migrate()` runs the `migrate` step. Tests are in `tests/modules/`.

## Signing in and the setup wizard

- **`@webcraft/auth`** is the only way into sign-in: `services.auth.signIn`, `session(headers)`, `signOut`, `createPerson` (inside the caller's transaction). Better Auth 1.7.18 (pinned in the root `package.json` catalog) sits behind it in `packages/auth/src/auth.ts`; no other package imports it. Its own HTTP endpoints are not served: WebCraft's procedures call it. When you upgrade it, read its security advisories and keep the version exact.
- **People** are the `people` table; their password hash is a row in `credentials`. Install-level roles are text keys in `install_roles` (`superadmin` and `staff`, ADR 0028; see "Tenancy and permissions"). Emails are stored in lower case.
- **Passwords** need at least 12 characters (`assertNewPasswordAllowed`). Extra checks plug in as `passwordChecks` in `createAuth`; `createInstallServices` plugs in the leaked-password check.
- **The leaked-password check** (`leakedPasswordCheck` in `packages/auth/src/leaked-passwords.ts`) checks every new password (new accounts, password changes) with a partial-hash lookup through `services.http`: only the first 5 characters of the password's SHA-1 hash leave the server (`GET <range service>/range/<prefix>` with `Add-Padding: true`), and the password is refused (`PASSWORD_REFUSED`, `leaked`) when the answer lists the rest of its hash as seen at least once. It fails open: when the service can't be reached, times out (5 seconds) or answers with an error, the password is accepted and a warning is logged. The Superadmin switches it off in Install settings › Security (`install.security.update`, a Sensitive action), for an Install that is always offline.
- **Sessions** end after 7 days unused and 30 days after sign-in, by WebCraft's clock (`services.clock`), so tests move them with `install.clock.advance`. `auth.activeSession(id)` reads one by its id, without renewing it, for checks away from the admin's hostname (Edit mode). A session in use is renewed at most every 10 minutes, and records the client address it was used from. The cookie is `HttpOnly`, `SameSite=Lax` and `Secure` (except on a `.localhost` development host), signed with a key derived from the Master key: a new Master key signs everyone out.
- **Your sessions** (Your account › Sessions): `me.sessions.list` shows each session's browser and system (from its `User-Agent`), its network (the client address with the end hidden, `203.0.113.*`; no outside location lookup, which would send people's addresses to another company) and when it was last used. `me.sessions.revoke` signs one out at once (this browser's own one too, clearing its cookie), `me.sessions.revokeOthers` every other one. `me.changePassword` (a Sensitive action) signs out every other session in the same transaction; changing 2FA does the same with `auth.revokeOtherSessions`.
- **Lockout** (`packages/auth/src/lockout.ts`): 10 wrong passwords in a row, signing in or confirming who you are, lock the account for 15 minutes. While it is locked nothing is checked, not even the right password, and trying doesn't make the lock longer; a right password, or the lock, starts the count again. Addresses nobody signs in with never lock. The answer is `ACCOUNT_LOCKED` (423) with `retryAfterSeconds` and a `Retry-After` header. When an account locks, `onAccountLocked` sends the `account-locked` security email and writes `account.lock` to the Audit log with the address of the last attempt.
- **Rate limits** on the auth endpoints (signing in, confirming who you are, setup tokens, invite links): at most 10 requests a minute from one client address, counted in Postgres (`services.rateLimits`, `RATE_LIMITS` in `packages/core/src/rate-limits.ts`) so every web process shares the count; then `TOO_MANY_REQUESTS` (429) with `Retry-After` until the minute is over, and one warning in the log. Requests whose address the web process can't tell share one count. The `rate-limits.purge` job deletes ended counters every day. Better Auth's own rate limiter stays off: its endpoints aren't served.
- **The setup token**: while the Install has no Superadmin, every start of the web process prints a new one-time token and a `setupUrl` in the log (`warn`, fields `setupToken` and `setupUrl`). Only its SHA-256 hash is stored; the last 10 printed stay valid. Claiming the Install with one creates the Superadmin and deletes every token. Creating the Superadmin is serialised with a Postgres advisory lock, across processes.
- **`webcraft admin create-superadmin <email> [--name <name>] [--language <en|it>]`** does the same headless: the password is asked twice on a terminal, or read from the first line of standard input (`printf '%s\n' "$PASSWORD" | webcraft admin create-superadmin ops@agency.example`); it is refused on the command line. It needs the Install's environment (`DATABASE_URL`, `WEBCRAFT_ADMIN_HOST`, `WEBCRAFT_SECRET_KEY`) and finishes setup, so the wizard never opens.
- **Setup stages** (`services.setup.stage()`): `claim` (no Superadmin: the wizard asks for the token), `continue` (the Superadmin exists and goes through the wizard's remaining steps, signed in), `done` (the wizard answers 404 for good).
- **The Master key banner** shows to the Superadmin until they confirm the running Master key is stored outside the server. The confirmation stores who, when and the key's fingerprint, and is logged; with another key the banner returns.

## The admin

The admin is a TanStack Start app in `apps/server/src/routes` (file routes) and `apps/server/src/ui` (everything else). It reads and changes data only through the Management API: `getApi()` (`ui/api.ts`) calls the procedures in-process while a page renders on the server, and `/api/rpc` in the browser.

- **Shell context**: the root route loads `shell.context` on every navigation (who is signed in, Admin language, theme, setup stage, banners); routes read it with `Route.useRouteContext()`. After a change that affects it, call `router.invalidate()` or navigate.
- **Text**: every word people see comes from `apps/server/src/messages/en.json` and `it.json`, through `useT()` (`t("shell.nav.overview")`, with ICU placeholders such as `{name}`). Add each key to both files; a missing key fails the typecheck, and `tests/i18n/admin-messages.test.ts` checks that every language has every key with the same placeholders. Page titles come from `pageTitle(language, key)` in the route's `head`.
- **Right to left**: `<html lang dir>` follows the Admin language (`ADMIN_LANGUAGES` in `@webcraft/core/admin-languages`). Use logical classes (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start`, `border-s`) and flip direction icons with `rtl:rotate-180`.
- **Light and dark**: `<html class="light|dark">` when a person chose, no class to follow the device (`prefers-color-scheme`); the `dark:` variant and the colour variables in `packages/ui/src/styles/globals.css` handle all three.
- **Levels and the sidebar**: `ui/shell/levels.ts` holds each level's sidebar groups and items (`label`, `icon`, `to`, `requires`: the Permission that shows it). A group can carry `requires` too: the Site level's Structure group requires `structure.edit`, so Members see Content items only (and its `note` says "Staff only"). The Site level's groups are Content (Overview, Pages, each of the Site's Post Types, Media, Globals: the Post Types come from `place.postTypes`), Structure (Post Types & Fields, Libraries) and Site settings (Languages, Outside scripts, Modules); Module pages follow. The levels are the Install, a Workspace and a Site: pages under `routes/_admin/workspaces.$workspaceId.tsx` are at the Workspace level and pages under `routes/_admin/sites.$siteId.tsx` at the Site level. Those two routes load the Workspace or Site and the person's Permissions there, and set `place` in the route context; the sidebar, the breadcrumbs (the Workspace's and Site's names first) and the context switcher read it. A page reads `Route.useRouteContext().place.permissions` to decide what to offer, never a role name. A page sets its breadcrumb with `staticData: { crumb: "<message key>" }`, or, when its name is data (a Post Type's name, an Entry's title), with `crumb` in what its loader answers; `pageTitleOf` makes such a page's `<title>`.
- **Pages** inside the shell are routes under `routes/_admin/` (signed in only). Start a page with `PageHeader`; use the shadcn components from `@webcraft/ui/components/*`.
- **The setup wizard's steps** are the list in `ui/setup/steps.tsx`: each has a title, a hint, a stage and a panel. After `two-factor` comes `email` (the Install SMTP, which can be skipped), then `modules` (approving the first-party Modules, ticked). The last step finishes setup.
- **Content screens** (`ui/content/`): Post Types & Fields (`routes/_admin/sites.$siteId.post-types*.tsx`, Structure: `structure.edit`), each Post Type's Entries and the Entry editor (`sites.$siteId.entries.$postTypeId*.tsx`) and the Globals editor (`sites.$siteId.globals.tsx`).
  - **Field rules in the browser**: the Field types, their traits (translatable by default, can be required, can have a default) and limits come from `@webcraft/core/field-rules`, which imports nothing, so the admin reads the same rules the content store checks. Never import `@webcraft/core` itself into browser code (types only).
  - **One control per Field type** in `FieldValues.tsx` (`FieldValue`, used by the Entry editor, the Globals editor and a Field's default), and one set of settings per type in `FieldSettingsPanel.tsx`. A new Field type adds its control and its settings there; `offeredTypes` (`FieldBuilder.tsx`) decides which types a new Field can be where it is (a Body field only on a Post Type that has none, at the top). Media Fields choose files through `MediaPicker` (`ui/media/`, built on the Media library's preview pieces in `ui/media/preview.ts`); rich text is edited in `RichTextEditor`, which cleans pasted HTML with the same cleaner the server uses (`@webcraft/renderer/rich-text`).
  - **The Field builder** (`FieldBuilder.tsx`, `StructureEditor.tsx`) keeps Fields as drafts (`field-drafts.ts`) until the screen saves the whole list (`postTypes.update`, `globals.setFields`); a problem the server answers (`fields[2].fields[0].key`) is located on its Field and setting, and shown there (in the server's words) and in a list above the Fields.
  - **Drafts save by themselves** through `useAutosave` (`autosave.ts`): a moment after typing pauses, the changes (merged by value) go to `entries.saveDraft` or `globals.saveDraft`, one save at a time; a refused change is kept and sent again with the next one, leaving the page saves what is waiting, and the browser asks before a tab with unsaved changes closes. Co-editing (#71) replaces this with the shared document. A save that loses a race shows `CHANGED_MEANWHILE`'s words with Try again and Reload.
  - **Problems in words**: `problemText` (`problems.ts`) words every rule code (`VALUE_RULES`) from the Field's settings, and values refused as the wrong kind by what they are; `errorMessage` (`ui/errors.ts`) words the content error codes (`ENTRY_*`, `GLOBALS_*`, `PATH_TAKEN`, `PAGE_*`, `POST_TYPE_*`, `CONFIRMATION_INVALID` by its `problem`); `settingProblemText` words a refused setting from its `SETTING_RULES` code (`content.settingProblems.*`, with Field and Block types by their names), falling back to the server's English for a code it doesn't know.
  - **The block editor** (`ui/content/body/`): a Body field's Blocks, each edited in place, in our own small editor over the Block JSON (no editor library: the same contenteditable approach as `RichTextEditor`). `InlineEditor` is one piece of formatted text (the browser types into it; `inline-dom.ts` reads it back as runs and places the caret by character); `BodyEditor` holds the Blocks and the keys between them (Enter splits, Backspace at the start joins or turns a Block back into a paragraph, the arrow keys cross Blocks, Ctrl/⌘ with B, I, E, K and Shift+X format, Alt+Shift with the arrows moves a Block, Ctrl/⌘ with `]` and `[` nest list items; Tab always leaves); `BlockMenu` is the `/` menu and Add Block (a combobox over a list box, filtered by what the Field allows, `choices.ts`). Markdown shortcuts turn a paragraph into a Block as it is typed (`## `, `### `, `#### `, `- `, `* `, `1. `, `> `, then ```` ``` ```` and `---` on their own). Checks are worked out in the browser with the renderer's `bodyChecks` and shown, with the server's problems, under their Block.
  - **Every drag has a keyboard way**: lists that drag by a handle (`useDragOrder` in `reorder.tsx`) also offer Move up and Move down in each item's menu, and say where the item went (`Announcer`).
  - **Languages**: `sites.get` answers the Site's `languages` (`{ default, all }`, the Default language first), carried in the Site's `place`; the language tabs of the editors and the chips of the Entries list show them all.
- **Times** are shown in UTC with `formatUtc`, and days with `formatUtcDate` (`ui/format.ts`), in one fixed form: the server renders pages first, and its date formatting differs from the browser's in small ways, which breaks hydration.
- **shadcn components** come from preset `b1Fk3bmIS` (`style: base-vega`, zinc, RTL on, see `packages/ui/components.json`). Add one with `bunx shadcn add <name>` in `packages/ui`, then run `bun run lint`: generated code sometimes fails the accessibility rules; fix the component (several are marked `WebCraft:`) rather than switching a rule off, and give every visible or screen-reader string a prop so it can be translated.

afterAll(async () => {
	await install.close();

test("the sample job emails the status of a URL", async () => {

Tests in one file share their Install, so give each test its own data (its own Workspace, its own email address) or create an Install per test when they must not see each other. `tests/worker/node-worker.test.ts` starts the real worker with `node`, the way to check something runs on Node; give it `install.env`. `tests/outgoing-http/pinned-address.test.ts` calls real servers on 127.0.0.1 and ::1 with both processes' outgoing HTTP, Bun's in the test and Node's in a `node` process (`node-calls.ts`, one JSON call per line); its HTTPS servers use certificates from `createTestCertificateAuthority()` (`tests/harness/certificates.ts`), which issues certificates for made-up names and addresses, trusted only by a client given its `cert` as `ca`. Start a real `bun` process (the CLI, the web entry) in an empty directory when a test leaves a setting out on purpose: Bun fills missing variables from the `.env` in the directory it starts in (see `tests/secrets/start-refusal.test.ts`).

**Workspace isolation**: every procedure that takes a `workspaceId` or `siteId` gets one line in `tests/isolation/procedures.test.ts`, proving it works on the caller's own Workspace and refuses another's (404 or 403). The last test there fails when a procedure is missing:

**Seam 2** is a real browser, for accessibility (and later the editors). `tests/browser/harness.ts` starts a test Install served by the production web process (`bun run build` first; started through `tests/browser/web.ts`, which hands it the test suite's Modules) on `http://admin.localhost:<port>`, with Sites' Staging addresses on `http://<site slug>.sites.localhost:<port>` (`browserInstall.siteUrl(slug, path)`), and Chromium through Playwright; `tests/browser/checks.ts` holds the checks; files are named `*.browser.ts` so `bun test` leaves them out, and `bun run test:browser` runs them. - `expectAccessibleScreen(page, where)`: axe-core finds no violation of WCAG 2.0, 2.1 or 2.2 at A or AA, nor of its best practices; the first Tab reaches "Skip to main content" and following it moves focus into the `<main>` it points at; Tab visits every link, button and field in page order (a date or time box once, though the browser stops on each of its parts), each with a visible focus indicator; no positive `tabindex`; Tab always moves on (no traps); the page logged no errors.

`startBrowserInstall()` also gives the test Install behind the web process (`browserInstall.install`), to prepare data through the Management API, send System emails and drain jobs before the page opens (see `tests/browser/email.browser.ts`).

## Conventions

- **Words**: use `GLOSSARY.md` terms exactly, in code, tests, UI text and commits. British spelling in prose ("licence", "normalise").
- **TypeScript**: strict, with explicit `.ts`/`.tsx` extensions on relative imports and only erasable syntax (no `enum`, `namespace` or parameter properties). That lets Node run shared code and the worker without a build step.
- **Runtimes** (ADR 0006): `packages/*` and `apps/worker` use standard Web and Node APIs only; Biome rejects the `Bun` global and `bun:*` imports there, and their tsconfigs don't load Bun's types. `apps/server`, `apps/cli`, `tests` and `scripts` may use Bun.
- **Edges go through ports**: time through `Clock`, email through `Mailer` (only the email sender calls it; features send System emails with `services.email.send`), calls to other servers through `services.http`. Tests replace them with fakes; nothing else is faked.
- **Secrets** go through `services.secrets` only: never in another table, a log line, a job payload or a response (see "Secrets and the Master key").
- **Workspace data** goes through the data layer (`services.data`), which runs `can()` first (ADR 0007); no query on tenant data without a Workspace, and no check of a role name: check a Permission.
- **Errors**: Site visitors and unknown hostnames see plain, unbranded answers. Unexpected errors are logged and answered with a plain 500.
- **Logs**: JSON lines through `Logger` (`services.log`), with fields rather than values pasted into the message.
- **Licences**: every workspace's `package.json` says `"license": "AGPL-3.0-or-later"`; new dependencies must pass `bun run check:licences`.
- **Commits**: Gitmoji + Conventional Commits with the ticket number, such as `✨ feat(auth): add setup wizard (#50)`.
- **Before you finish**: `bun run lint`, `bun run typecheck` and `bun run test` all pass.

## Reference-material denylist

Names of third-party products that informed WebCraft must never appear in anything tracked (ADR 0013, `docs/reference-material.md`). `scripts/check-denylist.sh` enforces it: it reads one case-insensitive extended regular expression per line from `WEBCRAFT_DENYLIST` or from the file named by `WEBCRAFT_DENYLIST_FILE`, and checks tracked files, file names, the messages of the commits in `--range` and a `--branch` name. It prints only where a match is (file and line, commit, branch), never the list or the matching text.

```sh
WEBCRAFT_DENYLIST_FILE=~/.config/webcraft/reference-denylist.txt bun run check:denylist -- --range main..HEAD
```

To check every commit locally, turn on the opt-in hooks (staged files before a commit, then the commit message):

```sh
git config core.hooksPath .githooks
export WEBCRAFT_DENYLIST_FILE=~/.config/webcraft/reference-denylist.txt   # in your shell profile
```

Without a list the check is skipped locally with a warning and fails in CI.

## CI

`.github/workflows/ci.yml` runs on pull requests and on pushes to `main`:

- **Lint, typecheck, build and licences**.
- **Tests** against a Postgres 18 service, with the current Node LTS installed for the worker test.
- **Accessibility (browser)**: builds the admin, installs Playwright's Chromium and runs `bun run test:browser`.
- **Reference-material denylist** over tracked files, the commit messages being added and the branch name, with the list from the `REFERENCE_DENYLIST` repository secret. It fails when the secret is missing, as it is for pull requests from forks.
