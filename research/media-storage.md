# Media storage and image processing for a self-hosted, multi-Site Install

Research for GitHub issue #31. Facts and options only — no recommendation. Today: 2026-11-07.

## 1. Storage backends: local disk vs S3-compatible

**Local disk**
- Simplest option: no extra service, no egress cost, works out of the box in every comparable CMS surveyed below.
- Breaks down for multi-process or multi-host deployments: a worker process (our pg-boss worker on Node LTS) and the web process (Bun) must share a filesystem, which usually means a bind-mounted volume in Docker Compose — fine on a single VPS, awkward once there's more than one web/worker host or on Railway, where local disk is explicitly ephemeral. Payload's own Railway deployment guide calls out that "by default, Payload stores media on the local filesystem, which is ephemeral on Railway" (https://docs.railway.com/guides/payload-cms).
- No built-in CDN story; a reverse proxy (Caddy) or external CDN has to be pointed at the volume.

**S3-compatible object storage (S3, R2, MinIO, others)**
- Cloudflare R2 exposes an S3-compatible API: "you can use any S3 SDK, library, or tool to interact with your buckets... by changing the endpoint URL" to `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` (https://developers.cloudflare.com/r2/api/s3/). R2 is a hosted service, not self-hosted, but it fits a self-hosted Install as an external storage target with no egress fees for standard requests.
- MinIO is the common choice for a fully self-hosted S3-compatible store: a single binary/container implementing the S3 API, deployable via Docker Compose or systemd, with multipart upload, versioning, lifecycle policies, replication, and IAM-style policies (min.io/docs/minio/linux/index.html, per third-party guides — the official docs page itself wasn't directly fetched in this pass and should be re-checked).
- Other S3-compatible targets mentioned in current CMS docs: Backblaze B2, DigitalOcean Spaces, Scaleway, Tigris, Supabase Storage, Wasabi. Directus's Supabase integration guide shows Supabase Storage driven through its generic `s3` driver with a custom endpoint and `forcePathStyle: true` (https://directus.com/docs/raw/guides/integrations/supabase/use-supabase-storage-with-directus.md).
- Multi-tenant angle: object storage buckets/prefixes map cleanly to per-Workspace or per-Site isolation (one bucket, or one prefix per Site, with scoped IAM credentials), which is harder to reproduce safely with local disk across tenants on one host.
- Trade-off common to all three comparable CMSs surveyed (Payload, Directus, Strapi): local is the zero-config default; S3-compatible is the documented path for anything beyond a single persistent host, and all three support pointing the same S3 adapter at R2 or MinIO by overriding the endpoint.

## 2. On-request vs upload-time resizing, and where it runs

**Upload-time (eager) resizing**
- Precomputes a fixed set of derivative sizes when a file is uploaded, storing each as its own object. This is the pattern in Payload and Strapi today (Strapi's Media Library and Payload's `imageSizes` config both generate named sizes at upload time).
- Simple to serve (static files, cacheable forever, no runtime image service required) but inflexible: adding a new breakpoint or format later means reprocessing the entire media library, and storage grows with every size/format combination kept.

**On-request (lazy/on-the-fly) resizing**
- A dedicated image service receives the original plus desired transform parameters in the request (URL) and returns/caches the processed result. Directus's `/assets` endpoint does exactly this, bounded by config such as `ASSETS_TRANSFORM_MAX_CONCURRENT` (default 25), `ASSETS_TRANSFORM_TIMEOUT` (7500 ms), `ASSETS_TRANSFORM_MAX_OPERATIONS` (default 5), and `ASSETS_TRANSFORM_IMAGE_MAX_DIMENSION` / `..._MAX_OUTPUT_DIMENSION` caps to stop upscale-based DoS (https://directus.com/docs/configuration/files).
- Standalone resizing services following this pattern: **imgproxy** — "a standalone HTTP server for image processing," built on libvips, taking transform options in the request URL, supporting signed URLs, header-based auth, and source restriction to prevent abuse; outputs include JPEG, PNG, GIF, WebP, AVIF, and JPEG XL; Apache-2.0 licensed core with a paid Pro tier (advanced watermarking, object detection, smart cropping, best-format selection) (https://github.com/imgproxy/imgproxy). It can fetch sources over plain HTTP, so it can sit in front of either local disk (via an internal URL) or an S3-compatible bucket.
- A page cache or CDN in front of the renderer (both already in scope for WebCraft Sites) naturally caches on-request image results too, which mitigates the main downside (repeated processing cost) without going fully eager.

**Running the resizer on Bun vs Node**
- `sharp` (the dominant Node image library, wrapping libvips) states its runtime requirement as "a Node-API v9 compatible runtime e.g. Node.js >= 20.9.0" and lists install commands for npm/yarn/pnpm/bun/deno — `bun add sharp` is explicitly shown on the install page (https://sharp.pixelplumbing.com/install). The page does not itself make a compatibility claim beyond listing the Bun install command.
- Bun's own docs say Node-API is implemented "from scratch" and that "most existing Node-API extensions work with Bun out of the box," loaded via `require()` on the `.node` binary or `process.dlopen` (https://bun.com/docs/runtime/node-api). Bun's Node.js-APIs page states the broader compatibility philosophy: "if a package works in Node.js but doesn't work in Bun, we consider it a bug in Bun" (https://bun.sh/docs/runtime/nodejs-apis).
- sharp's own GitHub issue tracker shows mixed real-world results: issue #3511 reports sharp working under early Bun (v0.6.14) and being resolved; issue #4152 (opened July 2024) reports sharp failing to load on `linux-arm64` inside several `oven/bun` Docker base images under Bun 1.1.17, while working fine outside Docker on macOS; sharp's own bug-report template (#4003) lists Bun among the runtimes it accepts reports for, i.e. Bun is an officially supported-enough runtime to get bug triage (https://github.com/lovell/sharp/issues/3511, /issues/4152, /issues/4003). No source found in this pass confirms resolution of the Linux-arm64/Docker case for current Bun 1.4 + current sharp.
- Practical implication for WebCraft's split (Bun 1.4 web process, Node LTS worker): running sharp inside the **Node LTS worker** avoids the open Bun-native-addon questions entirely, since sharp's primary support target is Node >= 20.9. Running it inside the **Bun web process** (e.g., for request-time resizing) currently carries unresolved platform-specific risk per the above issues and needs a same-architecture-as-production smoke test (particularly Linux/arm64 and musl/Alpine-style images) before relying on it.
- sharp's current release line (per third-party package/registry notes, not sharp's own changelog page which only lists up to 0.34.x) is reported around 0.35.x bundling libvips 8.18.x, with recent security advisories about libvips CVEs affecting versions prior to 0.35.0 and experimental prebuilt Linux RISC-V 64-bit binaries added in the same line. This should be re-verified against `npm view sharp version` and sharp's GitHub `docs/src/content/docs/changelog.md` at implementation time, since search results disagreed on the exact libvips point version (8.17.3 vs 8.18.3 appeared in different sources).
- `@img/sharp-wasm32` is an optional WebAssembly build "for multi-threaded Wasm in Worker-capable runtimes," explicitly excluding browser use, single-threaded environments, native text rendering, and tile-based output — a fallback path if native sharp proves unreliable under Bun, at a performance cost.
- Alternative pure-JS/WASM image libraries exist (e.g., `@squoosh/lib`-style WASM codecs, `jimp` in pure JS) that sidestep native-addon questions entirely at a speed/feature cost; not deeply researched in this pass.

## 3. Modern formats and responsive output

- Browser delivery mechanism: the `<picture>` element holds zero or more `<source>` elements plus a fallback `<img>`; the browser "skips any `<source>` whose `type` it doesn't support," so an AVIF source, then a WebP source, then a JPEG `<img>` fallback is the standard pattern (MDN: https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/picture).
- `srcset`/`sizes` on `<img>` (or inside `<source>`) let the browser choose among width-described variants of the *same* format — MDN's guidance: `sizes` only has effect when width descriptors (not pixel-ratio descriptors) are used in `srcset`. web.dev frames the distinction as "srcset gives suggestions, picture gives commands" — use plain `srcset`/`sizes` for resolution switching, and `<picture>` specifically for format switching or art direction (https://web.dev/learn/design/picture-element).
- Both imgproxy and Directus's `/assets` endpoint can produce AVIF/WebP outputs on demand from a single stored original, which removes the need to pre-generate every format × size combination at upload time.
- Historical adoption data (HTTP Archive 2020 Almanac — dated, cited only for context) found 83% of pages using `<picture>` for format switching included WebP as one of the variants; AVIF support reached Chrome in version 85. Current (2026) baseline support for AVIF/WebP across major evergreen browsers should be re-checked at implementation time rather than relied on from this 2020 figure.

## 4. How comparable self-hosted CMSs store private uploads

- **Payload CMS**: files keep Payload-native URLs (`/collectionSlug/staticURL/filename`) by default, and requests are proxied through Payload so the collection's `read` access-control function still gates them — this is the private-by-default path. Setting `disablePayloadAccessControl: true` instead points URLs directly at the cloud host, bypassing Payload's access control (so those files must be public). For S3 specifically, `signedDownloads` can generate presigned, time-limited URLs, optionally gated per-file via a `shouldUseSignedURL` condition (e.g., only for large videos) (https://payloadcms.com/docs/upload/storage-adapters). Azure containers created by Payload's adapter default to private (`containerAccess: 'private'`).
- **Directus**: the files configuration docs are comparatively thin on access control, deferring to a separate "Security Best Practices" doc for file-upload permissions and "asset access tokens"; concretely documented access knobs are Cloudinary's `access mode` (`public`/`authenticated`) and S3's ACL setting (https://directus.com/docs/configuration/files).
- **Strapi**: ships a Local upload provider by default; the official `@strapi/provider-upload-aws-s3` package supports S3 or any S3-compatible service (Cloudflare R2, Scaleway, MinIO, Tigris, Neon, etc.) via an `endpoint` option. Strapi Cloud's guide specifically calls out updating the CSP `media-src`/`img-src` directives to the bucket's domain when switching providers — directly relevant to WebCraft's strict Site CSP requirement (https://docs.strapi.io/cms/configurations/media-library-providers/amazon-s3, https://docs.strapi.io/cloud/advanced/upload).
- Common pattern across all three: **local storage defaults to "served by the app, so access control is whatever the app enforces"**; switching to cloud/object storage either (a) keeps requests proxied through the app (private, slower, no CDN offload) or (b) serves directly from the bucket/CDN (fast, cacheable, but then privacy must be enforced by the storage layer itself — presigned URLs, bucket policy, or a private bucket plus a signing proxy). None of the three documents a built-in per-tenant bucket/prefix isolation model out of the box; that's left to deployment-level bucket/credential configuration.

## 5. Sanitizing uploaded SVGs

- SVG is XML and can carry `<script>`, event-handler attributes (`onload`, etc.), and `<foreignObject>`-embedded HTML — the standard reason uploaded SVGs need sanitization before being served inline or even as `<img>`/background-image (serving as `<img>` already blocks script execution in most browsers, but inline embedding or direct navigation does not).
- **DOMPurify** (cure53/DOMPurify) ships an SVG-aware profile: `USE_PROFILES: { svg: true, svgFilters: true }` allows "all safe SVG elements and SVG filters" with no HTML/MathML; `USE_PROFILES` *overrides* `ALLOWED_TAGS` and the two should not be combined (https://github.com/cure53/DOMPurify). Its README shows `<svg><g/onload=alert(2)//<p>` sanitized down to `<svg><g></g></svg>`.
- Running DOMPurify server-side (Node/Bun) requires a DOM implementation; the README "strongly recommend[s]" an up-to-date **jsdom**, explicitly states that **happy-dom "is not considered safe at this point"** for this purpose, and mentions a third-party `purify-edge` project without endorsing it. This matters for WebCraft's worker (Node LTS) if SVG sanitization runs there.
- Caveats called out directly in the README: sanitized output must not be re-processed by another HTML-mutating library afterward (can reintroduce vulnerabilities); `SAFE_FOR_XML: false` is discouraged for anything touching SVG/MathML since it can reopen XSS; and DOM-API-constructed or XML-parsed nodes can bypass string-based sanitization, so input must be consistently treated as a string until sanitized.
- The README does not give file-upload-specific guidance (it's a DOM/HTML sanitizer, not a file-format linter), so a full pipeline for uploaded SVGs — MIME/content sniffing, size caps, stripping XML entities/DOCTYPE (XXE), and then DOMPurify's SVG profile — is assembled from general web-security practice rather than one single doc; not further verified against a dedicated SVG-sanitization library (e.g. `svg-sanitizer`-equivalents in the Node ecosystem) in this research pass.

## Options at a glance

| Axis | Option A | Option B | Option C |
|---|---|---|---|
| Storage backend | Local disk (bind-mounted volume) | Self-hosted MinIO (S3-compatible) | Hosted S3-compatible (R2, S3, Spaces, etc.) |
| Resizing timing | Upload-time, fixed size set | On-request via standalone service (imgproxy) | On-request via app code (sharp in worker) |
| Resizing runtime | Node LTS worker (sharp, well-supported) | Bun web process (sharp, unresolved Docker/arm64 reports) | WASM fallback (`@img/sharp-wasm32`, slower) |
| Format output | Pre-generate WebP/AVIF at upload | Convert on demand (imgproxy/Directus-style `/assets`) | Original format only, no conversion |
| Private file access | Proxy through app (access-control enforced) | Presigned/time-limited URLs from bucket | Public bucket + CDN (no app-level privacy) |
| SVG handling | Reject SVG uploads entirely | Sanitize with DOMPurify (+jsdom) server-side | Sanitize client-side only (weaker guarantee) |

## Questions for the grilling

1. Does any Workspace/Site need multi-host or serverless deployment (Coolify/Railway-style ephemeral disk), or is single-VPS-with-volume acceptable for v1 — which decides whether local disk is viable at all?
2. Is per-Site or per-Workspace storage isolation (separate buckets/prefixes/credentials) a hard requirement, or is a shared bucket with app-level access control acceptable?
3. Should image resizing happen in the Node worker (via pg-boss job) or synchronously in the Bun request path — and is a same-architecture Bun+sharp Docker smoke test (Linux/arm64, musl) a prerequisite before committing to Bun-side sharp?
4. Is a standalone resizing service (imgproxy) worth the extra moving part, given it already solves signed URLs, format negotiation, and source abstraction — or does that duplicate pg-boss-job-based resizing we'd build anyway?
5. For the 10 MB private form-upload attachments: do these need image processing at all, or just access-controlled storage + the SVG/MIME sanitization question?
6. What's the acceptable staleness/complexity trade-off for on-request resizing's cache (page cache vs CDN vs imgproxy's own cache) versus the simplicity of pre-generated sizes?
7. Do we reject SVG uploads outright for user-generated Media (sidestepping sanitization entirely), or is inline SVG support a real requirement that justifies the DOMPurify+jsdom pipeline in the worker?
8. Given strict CSP on Sites, does serving media from a different origin (bucket/CDN domain) versus the Site's own domain change the CSP policy needed, and who owns keeping that in sync per Site?
