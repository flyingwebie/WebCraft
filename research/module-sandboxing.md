# How other platforms isolate third-party extension code

**Ticket:** "How do other platforms isolate third-party extension code?"
**Date:** 2026-11-05

## Summary

Platforms split cleanly into two camps: those that run third-party code **in-process with no sandbox** (WordPress, Strapi, Payload, Sanity Studio — isolation is "trust the review process, or trust nothing at all"), and those that run it inside an **explicit sandbox with a capability/permission model** (Shopify Functions' Wasm, Figma's custom JS VM, Cloudflare's V8 isolates, Extism/WASI's capability imports, Deno's `--allow-*` flags, Directus's `isolated-vm`). Admin/editor UI extensions are almost always either in-process React/Preact components (Payload, Strapi, Sanity, Directus app extensions) or an iframe talking to the host over `postMessage` (Figma, Shopify Admin UI extensions) — nobody in this set uses Module Federation for *third-party, untrusted* code. Every in-process model has produced real incidents (Directus's vm2 escape, the Strapi npm supply-chain campaign, WordPress's multi-thousand-CVE-a-year plugin ecosystem); the sandboxed models' incidents are mostly sandbox-escape bugs in the sandbox library itself (Figma's Realms shim, Directus's vm2) rather than in individual extensions. No platform surveyed does code signing of extension *binaries* in the traditional sense — "review" ranges from fully automated (Shopify Functions' resource caps, WordPress's new 2026 AI/Jetpack Scan gate) to manual human review with a multi-day SLA (Figma, Shopify App Store) to nothing at all (Payload, Strapi, Sanity, self-hosted Directus extensions).

## Sections

### Execution model spectrum

Two poles, with everything else a variant:

- **No isolation, shared process, full trust**: WordPress (PHP), Strapi/Payload/Sanity (Node.js server and/or browser JS), Ghost (N/A — no code execution model). Extension code runs with the same privileges as the host application. The *only* defense is whatever review happens before the code reaches a production Install, plus runtime conventions (capability checks, hooks) that extension authors can simply ignore.
- **Explicit sandbox with enforced boundary**: Shopify Functions (Wasm, resource-capped, no I/O), Figma plugins (custom JS VM + iframe split), Cloudflare Workers/Deno (V8 isolates with explicit allow-lists), Extism/WASI component model (capability imports, default-deny), Directus sandboxed extensions (isolated-vm + scope declarations). The boundary is enforced by the runtime regardless of what the extension author intends.

### Permission/capability models

The sandboxed group converges on **capability-based, default-deny** security: nothing is reachable unless explicitly granted (WASI's "no ambient authority," Deno's `--allow-*`, Extism's host-function registration, Directus's `requestedScopes`, Shopify's OAuth access scopes). The unsandboxed group uses **role/scope checks as convention** (WordPress's `current_user_can`, Strapi's policies, Payload's access-control functions) — these shape what the extension is *supposed* to do, not what it is *able* to do; a malicious or compromised extension bypasses them trivially because it shares the process.

### What extensions can hook into

- **Data**: direct DB/ORM access is universal in the unsandboxed group (WordPress, Strapi, Payload, Sanity); the sandboxed group instead exposes data through typed, host-mediated calls (Shopify Functions' GraphQL input/output, Directus's `directus:api` module, Extism host functions).
- **UI**: in-process React/Preact component injection is the norm for admin/editor surfaces across Payload, Strapi, Sanity, and Directus's "app" extensions (the unsandboxed half of Directus). Figma and Shopify Admin extensions are the two iframe/postMessage-style cases in this set, and even then Shopify's extension UI isn't a raw iframe with arbitrary HTML — it's a sandboxed runtime that can only render Shopify-supplied components, closer to a DSL than a full iframe.
- **Events/HTTP**: lifecycle hooks (Strapi, Payload, WordPress actions/filters) vs. explicit webhook/API surfaces with no code execution (Ghost) vs. typed event targets (Shopify Functions' "targets").

### How admin UI extensions are loaded

No platform surveyed uses **Module Federation** for untrusted third-party code. The real split is:
- **In-process, same bundle** (Payload, Strapi, Sanity, Directus app extensions): simplest to build, zero isolation — a malicious component can read `document.cookie`, intercept fetches, exfiltrate admin session tokens.
- **iframe + postMessage** (Figma's UI iframe, Shopify's embedded app pages via App Bridge): standard web-platform isolation (separate origin, no DOM access across the boundary) at the cost of a message-passing API surface and UX friction (can't directly manipulate host DOM).
- **Host-controlled component set, no arbitrary DOM** (Shopify Admin UI extensions' Preact runtime, Figma's main-thread JS VM for document access): strongest UI-level containment, but extensions are limited to whatever components/APIs the host chose to expose — most restrictive to build *for* the platform, least flexible for extension authors.

### Install/update/signing/review

Nobody does cryptographic code signing of extension packages in this set. "Review" ranges along a spectrum: fully automated resource limits enforced at runtime (Shopify Functions), automated static/AI scanning gating releases (WordPress since Sept 2026), manual human review with multi-day SLA (Figma, Shopify App Store), to no review at all beyond npm's registry trust (Payload, Strapi, Sanity, self-hosted Directus). Update flows are mostly "ship a new version, same trust level as the first" — only Figma calls out that "material" updates trigger re-review; everyone else re-review is either absent or not documented.

### Notable security incidents

Two failure patterns recur:
1. **Sandbox-escape bugs in the sandbox library itself** — Figma's Realms shim (2019) and Directus's vm2 (GHSA-22rr-f3p8-5gf8, fixed by switching to isolated-vm). These affect every extension running under that sandbox simultaneously, but are comparatively rare and get fixed once, platform-wide.
2. **Supply-chain / ecosystem-scale compromise in unsandboxed models** — the Strapi npm campaign (36 fake packages, install-time RCE, April 2026) and WordPress's standing multi-thousand-CVE-per-year plugin ecosystem (Patchstack: 11,334 new vulnerabilities in 2025, 91% in plugins). These are continuous and scale with ecosystem size, not single fixable events.
Shopify's July 2024 breach (~180k customer records) was attributed to a compromised *third-party app*, not a flaw in Shopify's own sandbox — illustrating that even a well-isolated platform (Shopify Functions, scoped OAuth) still carries risk through apps that hold broad API scopes and get compromised independently of the platform's sandbox.

## Distinct isolation patterns and what each costs to build

1. **No isolation (shared process trust)** — *Cost: ~zero.* Extensions are just more code in your app (WordPress, Strapi, Payload, Sanity). Fastest to build and for third parties to write against; all defense is social (review, reputation) and reactive (patch after disclosure). Appropriate only when extension authorship is tightly controlled or trust is otherwise established.
2. **Process/isolate-level sandboxing of general-purpose code (V8 isolates)** — *Cost: high.* Cloudflare Workers/Deno/Directus's isolated-vm. Requires embedding or building an isolate runtime, a capability-grant layer around it, and ongoing patching of the isolate engine (V8) itself against new side-channel classes (Spectre). Buys strong confidentiality/integrity isolation while keeping near-native JS semantics for extension authors.
3. **Wasm/WASI capability sandboxing** — *Cost: medium-high.* Shopify Functions, Extism, the Component Model. Requires a compiler toolchain story for extension authors (not every language is equally ergonomic to target), a host-function/import design, and resource-limit enforcement (time/memory/IO). Buys default-deny capability security with a formally specified model (WASI) rather than a bespoke one, at the cost of restricting extensions to deterministic, mostly-synchronous computation (hard to do long-running or stateful work).
4. **Custom JS VM + iframe split for UI** — *Cost: very high, bespoke.* Figma's approach: build (or adopt and then rebuild) your own JS engine to strip browser/DOM APIs from "logic" code, and push anything needing browser APIs into a separate iframe. This is the most expensive option in the set — Figma's own blog post describes three attempts before landing on this — and the sandbox library itself becomes a security-critical dependency you must track.
5. **Host-controlled component/DSL for UI, scoped OAuth for data** — *Cost: medium (framework/design cost), low runtime cost.* Shopify's Admin UI extensions: no general-purpose UI sandbox needed because extensions never get arbitrary DOM access — they render only a fixed set of host-defined components. Pairs naturally with scoped OAuth for data access. Cheaper at runtime than a VM/iframe approach, but constrains what extension UIs can look like, and the design work to define a sufficiently expressive component set is nontrivial.
6. **No code execution at all, API keys + webhooks only** — *Cost: lowest, but weakest capability.* Ghost's model. Zero sandboxing problem because there's no third-party code running inside the host process — but this also means no in-admin extension UI and nothing resembling WebCraft's "Module" concept; it only suits integration-style extensibility, not feature packages.

## Implications for WebCraft (options, not decisions)

WebCraft's threat model is explicitly multi-tenant at the **Install** level: one Install holds many Workspaces' secrets (SMTP passwords, AI keys) and content, and Modules are meant to eventually come from third-party GitHub/GitLab repos. That combination — multi-tenant secrets *and* untrusted third-party code in the same process — is closer to Directus/Strapi/WordPress's risk profile than to Shopify's or Figma's, because WebCraft is self-hosted (no central platform operator reviewing every Module before it reaches a given Install).

Options surfaced by this research, roughly cheapest-to-build → strongest isolation:

- **A. No sandbox, in-process Modules (WordPress/Strapi/Payload/Sanity pattern).** Cheapest, fastest to ship a Module ecosystem, most ergonomic for Module authors (plain TS/JS, direct access to WebCraft's APIs and DB). Carries the WordPress/Strapi risk profile squarely: a single malicious or compromised Module can read every Workspace's SMTP passwords and AI keys on that Install, not just its own Workspace's. This risk is specific to WebCraft's one-Install-many-Workspaces shape and is worse than it would be for a single-tenant app.
- **B. Capability-scoped host API, still in-process (Directus "app extensions" / Extism host-function pattern without the Wasm boundary).** Medium cost: design a `webcraft:api` surface Modules must go through (akin to Directus's `directus:api` module or Extism's host functions) instead of touching the DB/secrets store directly, and gate it by declared scopes per Module per Workspace. Does not stop a determined malicious Module (it's still in-process JS, can monkey-patch, reflect, or just not go through the API), but raises the bar and makes the *intended* boundary visible and auditable — closer to "convention as documentation" than "convention as enforcement," same caveat as WordPress's capability checks.
- **C. True sandboxed execution for first-party-untrusted-Module logic (Wasm/WASI or isolated-vm/V8-isolate pattern).** Higher cost: pick a sandbox technology (isolated-vm, a Wasm/WASI runtime like Extism, or a V8-isolate-based approach) for the parts of a Module that touch data/secrets, with explicit capability grants per Workspace (which AI key, which SMTP credential, which Site's content). This is the only option in this survey that actually enforces Workspace-level secret isolation against a hostile or compromised third-party Module, at the cost of restricting what Module code can do (synchronous/limited APIs, a compiler/packaging story, ongoing sandbox-library maintenance — recall Directus's own vm2 escape).
- **D. Mixed model by Module trust tier.** Core Modules (shipped by WebCraft itself) run in-process/unsandboxed (option A), since they're first-party-trusted; third-party Modules installed from a repo run under option B or C. This mirrors Cloudflare's trust-tiered isolate placement and avoids paying sandbox cost for code WebCraft already trusts, while still bounding the blast radius once the "install from GitHub/GitLab" feature ships. Requires deciding, in advance, what marks a Module as needing the stronger boundary (and reconsidering that decision is harder to do retroactively once an ecosystem exists — see Directus's note that pre-framework extensions kept running unsandboxed after the framework shipped).
- **UI extension loading**, independent of the data-layer choice above: in-process component injection (Payload/Strapi/Sanity style) is cheapest but gives a Module's admin UI the same DOM/cookie access as WebCraft's own admin — a compromised Module's UI code could exfiltrate the Superadmin's session. An iframe+postMessage boundary (Figma/Shopify Admin pattern) or a host-defined-component-only surface (Shopify Admin UI extensions) costs more up front but is the only approach here that contains a malicious Module's *UI* layer the same way option C would contain its *data* layer — worth deciding together rather than treating "logic sandboxing" and "UI sandboxing" as the same problem, since every platform surveyed solved them separately.
- **Review/signing**, whatever execution model is chosen: no surveyed platform solves this with cryptographic signing; the realistic choices are (i) no review at all (fastest, WordPress/Strapi/Payload/Sanity's actual default), (ii) automated static/AI scanning at install or publish time (WordPress's Sept 2026 model, cheap to run, catches only known-bad patterns), or (iii) manual human review before a Module reaches any Install (Figma/Shopify App Store pattern — not really applicable to a self-hosted, GitHub/GitLab-sourced Module ecosystem without a central marketplace operator).
