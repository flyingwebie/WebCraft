# Install lifecycle research: updates, migrations, backup/restore (issue #32)

This document gathers facts and options from self-hosted, Docker-deployed applications comparable to WebCraft (TanStack Start + oRPC + Postgres/Drizzle + pg-boss, Bun web process + Node worker, Docker Compose/Caddy). It is fact-finding only — no option is recommended. A follow-up "grilling" ticket will make the actual decisions.

## 1. Update channels and in-app update notices vs. pulling a new image

- **Ghost** ships weekly open-source releases. Admins check for updates explicitly with `ghost check-update`, and apply them with `ghost update`. Upgrade paths differ by current major version/database: Ghost 3.0+ on MySQL can update directly; anything below 3.0, or any SQLite production install, is recommended to do a full reinstall instead of an in-place update. The docs give no formal rollback procedure beyond "run `ghost backup` before updating" as a precaution. (https://docs.ghost.org/update/)
- **Directus** is distributed purely as a tagged Docker image. The docs are explicit that restarting a container does **not** move you to a newer version — you must pull a new tag — and recommend pinning to an explicit version (e.g. `directus/directus:11.1.1`) rather than `latest` for production, specifically because upgrades can carry breaking changes. (https://directus.com/docs/self-hosted/docker-guide.html, https://directus.com/docs/self-hosting/deploying)
- **Supabase** self-hosted and Payload CMS's deployment docs did not surface explicit in-app update-notification mechanisms in the pages checked; Payload's production deployment doc focuses on environment variables (`DATABASE_URL`, `PAYLOAD_SECRET`, `PAYLOAD_CONFIG_PATH`) and persistent storage, not update signaling. (https://payloadcms.com/docs/production/deployment)
- **Coolify**, as a deployment platform rather than an app, offers scheduled backups across six database engines and explicitly warns that "a successful backup only proves that Coolify created a file" — restore testing is called out as a separate concern from the backup mechanism itself. (https://coolify.io/docs/knowledge-base/databases/backups)

Options surfaced across these apps for an update channel:
- Manual check via CLI command (Ghost's `check-update`) vs. no built-in check at all (Directus: you decide when to pull a new tag).
- Pin to an explicit version tag in production (Directus's explicit recommendation) vs. tracking `latest`.
- In-app admin UI banner for new versions (not confirmed in any source fetched) vs. relying on release notes/changelogs read externally.

## 2. DB migrations on container start vs. a separate explicit step, and rollback handling

- **Drizzle ORM** itself supports both patterns and does not recommend one over the other: the `drizzle-kit generate` → `drizzle-kit migrate` CLI workflow applies only not-yet-applied SQL migration files tracked in a migration-history table; alternatively, calling `migrate(db)` programmatically at application startup applies pending migrations as part of boot. Drizzle's docs tie the runtime-`migrate()` pattern to two deployment models: monolithic apps running migrations during a zero-downtime deploy (with DDL rolled back on failure), and serverless apps running migrations once via a custom deploy resource. `drizzle-kit push` is offered as a third, schema-first option that pushes diffs directly without migration files — called suitable for prototyping, with a note that some teams use it in production anyway. (https://orm.drizzle.team/docs/migrations)
- **Directus** and **Payload** deployment docs did not describe whether migrations run automatically on container start or via a separate CLI invocation; this remains unconfirmed from the specific pages fetched (Directus's self-hosting/deploying page explicitly omits migration mechanics; Payload's production deployment page likewise omits migration/update process entirely).
- **Ghost**'s upgrade docs route database schema changes through its major-version-specific upgrade/reinstall guidance rather than describing an explicit "migration step" abstraction; no automated-rollback mechanism is described — the stated safety net is taking a `ghost backup` beforehand. (https://docs.ghost.org/update/)

Rollback handling, where mentioned at all, is backup-based (restore a prior backup) rather than true migration-level down-migrations, except where Drizzle's CLI itself exposes `migrate:down`-style file-based reversals as a general ORM capability (not confirmed as used by any surveyed app in its own deploy process).

## 3. Postgres backup options: logical, physical/WAL, and purpose-built S3 tools

**Logical backups (pg_dump / pg_dumpall)** — per PostgreSQL's own docs:
- `pg_dump` produces an internally consistent snapshot as of when it started, without blocking most concurrent operations (exceptions: operations needing exclusive locks, like most `ALTER TABLE`). Output formats include plain SQL, custom (`-Fc`, compressed, supports selective/parallel restore via `pg_restore -j`), and directory format (supports parallel *dump* via `-j`). `pg_dumpall` adds roles/tablespaces across the whole cluster but does not synchronize snapshots across multiple databases. Restoring a plain-SQL dump can leave a partially-restored database on error unless run with `psql --single-transaction`. pg_dump output is portable across PostgreSQL versions and hardware architectures; file-level/physical backups are not. pg_dump cannot be used for WAL replay. (https://www.postgresql.org/docs/current/backup-dump.html)

**Physical / continuous archiving (WAL-based PITR)** — per PostgreSQL's own docs:
- Combines a file-system-level base backup (via `pg_basebackup`, or the low-level `pg_backup_start()`/`pg_backup_stop()` API) with a continuous sequence of archived WAL segments. Recovery restores the base backup then replays WAL, optionally stopping at a chosen `recovery_target_time`/named restore point/xid — this is what enables point-in-time recovery. The base backup itself need not be internally consistent, since replay corrects it. `pg_basebackup --incremental` + `pg_combinebackup` support incremental/delta base backups. The doc explicitly contrasts this with pg_dump: continuous archiving/PITR covers the whole cluster only (not a single database/table), has no formal RPO/RTO numbers but implies RPO is bounded by how far archiving has fallen behind (configurable via `archive_timeout`) and RTO scales with WAL volume since the last base backup. Storage is larger (full base backups + WAL) versus pg_dump's typically smaller output, and admin complexity (timelines, archive monitoring, retention of backup chains) is higher. Config files (`postgresql.conf`, `pg_hba.conf`, `pg_ident.conf`) are **not** captured by PITR and must be backed up separately. (https://www.postgresql.org/docs/current/continuous-archiving.html)

**Purpose-built S3-shipping tools:**
- **pgBackRest**: supports repositories on S3-, Azure-, and GCS-compatible object storage or SFTP, with automatic credential retrieval in cloud environments. Offers full, differential, and incremental backups at file or block level (block-level copies only changed file portions), configurable retention per backup type, parallel backup/restore, lz4/zstd compression, checksummed integrity, repository encryption, multiple repositories, and backups taken from a standby. (https://github.com/pgbackrest/pgbackrest)
- **WAL-G**: an archival/restoration tool (successor to WAL-E) supporting Postgres, MySQL/MariaDB, and MS SQL Server (MongoDB/Redis in beta). Backs up to configurable storage backends including S3 (via `WALG_S3_PREFIX`); the fetched README did not explicitly confirm S3-*compatible* (non-AWS) endpoint support. Supports `wal-push`/`wal-fetch` for continuous WAL archiving, `backup-push`/`backup-fetch`/`backup-list` for base backups, delta backups with a `FIND_FULL` retention option, and multiple compression methods (LZ4/LZMA/ZSTD/Brotli). (https://github.com/wal-g/wal-g)
- **Supabase** uses WAL-G specifically (not pgBackRest, per its own docs) to implement PITR for paid tiers: daily physical snapshots plus WAL archived at least every two minutes (or sooner if a size threshold is hit), giving a worst-case RPO of two minutes on that product's PITR tier. Enabling PITR disables the separate daily-logical-backup path. Restores are described as destructive to current state unless done into a new project. Free-tier Supabase projects have no automatic backups at all — users are told to run `supabase db dump` / `pg_dump` manually and store copies off-platform. (https://supabase.com/docs/guides/platform/backups)

Trade-off summary (as described by the sources, not ranked):
| Dimension | Logical (pg_dump) | Physical/WAL (PITR) | Purpose-built (pgBackRest/WAL-G) |
|---|---|---|---|
| RPO | As of last dump | Bounded by archive lag / `archive_timeout` | Can be minutes (e.g. Supabase's 2 min via WAL-G) |
| RTO | Dump+restore time, parallelizable with `-j` | Scales with WAL volume since base backup | Parallel restore, delta restore reduce RTO |
| Granularity | Per database/table possible | Whole cluster only | Whole cluster; some incremental/delta support |
| Portability | Cross-version, cross-architecture | Server-version-specific | Server-version-specific (physical) |
| Operational complexity | Lower | Higher (timelines, retention chains) | Higher, but packaged/managed by the tool |
| Object storage support | Not built-in | Not built-in (manual scripting of archive_command) | Native S3/Azure/GCS support |

## 4. Backing up uploaded media files alongside the database

- **Ghost** stores uploaded images by default on the local filesystem (`content/images`, with `content/media` and `content/files` for other upload types, or a custom content path). Ghost's docs give no backup procedure for these directories and no guidance on syncing their backup with a database backup; the docs do note that migrating to S3 does not auto-migrate existing files — you must copy `content/images`/`content/media`/`content/files` into the bucket under the same prefixes, or old uploads 404. (https://docs.ghost.org/config/)
- **Mastodon**'s official backup guidance explicitly ranks what to back up: (1) the Postgres database (most critical — its loss is "complete failure of the server"), (2) application secrets (`.env.production` — losing them logs out all users and breaks 2FA/push), (3) user-uploaded media (`public/system` if stored locally; if using S3/GCS/Wasabi, the provider is relied on for durability instead), and (4) Redis (least critical, regenerable). The fetched page does **not** give explicit warnings about keeping the database and media backups consistent/in-sync with each other. (https://docs.joinmastodon.org/admin/backups/)
- **Discourse** backs up the database by default and, separately, uploads — controlled by a `backup_with_uploads` setting that is enabled by default; disabling it backs up only the database. A community note on the same doc flags that uploads stored on S3 are *not* included in the database-backup bundle, meaning S3-stored media needs its own backup strategy independent of the app's backup feature. Discourse also explicitly disallows sharing one S3 bucket/prefix between backups and regular uploads. (https://meta.discourse.org/t/configure-automatic-backups-for-discourse/14855)
- **GitLab**'s default backup Rake task includes uploads, LFS objects, and (filesystem-stored) container registry images, but explicitly **excludes** any data living in configured object storage — "the backup command does not back up registry data stored in object storage either." GitLab therefore requires users with object-storage-backed uploads to arrange backup of that storage independently of the Rake-task archive. (https://docs.gitlab.com/ee/administration/backup_restore/backup_gitlab.html)
- **Supabase** daily backups do not include Storage API objects — only their metadata is captured; the actual file blobs are excluded from the automatic backup product.

Recurring theme across sources: once media moves to S3-compatible/object storage, the app's own "backup" feature typically stops covering it, shifting consistency and retention to the storage provider or to a separately-scripted process — and no source fetched described a built-in mechanism to guarantee transactional consistency between a DB snapshot and a media snapshot taken at a different moment.

## 5. Keeping an encryption master key with vs. separate from backups

- **GitLab** gives the most explicit guidance found: its backup Rake task **does not** store configuration files, and specifically **excludes** the secrets file (`/etc/gitlab/gitlab-secrets.json` for the Linux package; `config/secrets.yml` for self-compiled; the config volume for Docker). GitLab's docs give two explicit reasons: (a) the database holds values encrypted under that key (two-factor secrets, CI/CD secure variables), so storing the decryption key alongside the encrypted data "defeats the encryption"; (b) the secrets file can change across upgrades, so it needs independent versioned safekeeping. Losing it means GitLab can never decrypt what's in the database backup. (https://docs.gitlab.com/ee/administration/backup_restore/backup_gitlab.html)
- **Mastodon** similarly treats `.env.production` (which holds `SECRET_KEY_BASE` and similar values) as its own backup category, separate from the database dump, noting these values "rarely change" so a single safely-stored copy generally suffices — implying a different backup cadence/location than the frequently-changing database. (https://docs.joinmastodon.org/admin/backups/)
- No source fetched described using an external secrets manager/vault product by name for this specific master-key use case; the pattern described by both GitLab and Mastodon is "keep this one file safe, separately, with different handling than the recurring data backup" rather than naming a specific vault technology.

Trade-off as stated by these sources (not evaluated further, per scope): bundling the key with the backup archive makes a stolen/leaked backup immediately decryptable (defeating the point of encrypting secrets in the DB at all), whereas storing it separately means a restore is a two-part operation (data + key, from two different places/cadences) and losing the separate copy makes the DB backup's encrypted contents permanently unreadable.

## 6. Export/import of a single tenant between separate instances

- **GitLab**'s project export/import feature is the clearest analogue found for moving a single logical unit (a project) between separate instances. Exports are NDJSON files packaged as `.tar.gz`, downloadable from the UI (Settings > General > Advanced > Export project) and importable into a different instance via "Import project > GitLab export." Included: repositories, wiki, uploads, issues (with comments/milestones), merge requests (latest diff/pipeline only), labels, releases, design files, LFS objects, boards, archived CI/CD pipelines, protected branches/tags, and (as of GitLab 17.7) direct project members and vulnerability data. Explicitly excluded: CI/CD variables, job traces/artifacts and triggers, package/container registry images, webhooks, encrypted tokens, secure files, and deploy keys/issue-link relationships. GitLab explicitly warns "export files should not be used as backups" — it is a distinct, lossier mechanism from the backup/restore Rake task. Known limitations include user-identity remapping rules (contributions only map to the same user under specific email-matching conditions), a same-or-newer destination version requirement, GitLab.com's 5 GB import cap and rate limits (6 exports/6 imports per minute), and 24-hour deletion of export files. (https://docs.gitlab.com/user/project/settings/import_export/, note this is distinct from GitLab's separate "direct transfer" migration method, which the docs recommend for most migrations instead of file export)
- None of the other surveyed self-hosted apps (Ghost, Directus, Strapi, Payload, Supabase, Discourse, Mastodon) are themselves multi-tenant in the WebCraft sense (one Install → many Workspaces → many Sites), so none of their docs describe a "move one tenant to another instance" feature; their export/import concepts (where present) operate at the whole-instance level, not a sub-instance tenant level. Directus's and Strapi's specific export/import or schema-snapshot tooling could not be confirmed from the pages fetched (both returned pages lacking migration/export-command detail, and direct attempts at Strapi's Docker-deployment docs 404'd).

## Options at a glance

| Topic | Option A | Option B | Option C |
|---|---|---|---|
| 1. Update delivery | Pin to explicit image tag, manual pull (Directus-style) | Track `latest`, restart to get new code | In-app/CLI update check command (Ghost's `check-update`) |
| 2. Migrations | Run automatically at process start (Drizzle `migrate()` at boot) | Separate explicit CLI step before/after deploy (`drizzle-kit migrate`) | Schema-push without versioned files (`drizzle-kit push`) |
| 2. Rollback | No automated down-migration; restore from backup | File-based down-migrations if authored | Zero-downtime deploy pattern with DDL rollback on failure |
| 3. Backup type | Logical: `pg_dump`/`pg_dumpall` | Physical/WAL: continuous archiving + PITR | Purpose-built S3 tool: pgBackRest or WAL-G |
| 4. Media backup | Bundle media into the app's own backup feature (Discourse-style, toggleable) | Exclude object-storage-backed media from app backups, rely on provider (GitLab/Supabase-style) | No built-in consistency guarantee between DB snapshot and media snapshot (no source describes one) |
| 5. Master key handling | Bundle key with backup archive (simpler restore, weaker security) | Store key separately from data backups (GitLab/Mastodon pattern; safer, two-part restore) | External secrets manager/vault (not confirmed as used by any surveyed app) |
| 6. Tenant export/import | Per-project/tenant export-import file (GitLab project export, lossy, not a backup substitute) | Whole-instance migration only (most surveyed single-tenant apps) | No tenant-level export concept at all |

## Questions for the grilling

- Should WebCraft pin Docker image tags by default in its Compose/Coolify/Railway files, or track `latest` with a separate update-check mechanism?
- Should Drizzle migrations run automatically when the web or worker process boots, or as an explicit `drizzle-kit migrate` step in the deploy pipeline (and if the latter, who/what runs it — Docker Compose entrypoint, a one-off job, CI)?
- Is there an acceptable RPO/RTO target for WebCraft's Postgres data yet? That determines whether `pg_dump` alone is sufficient or whether WAL-based PITR / pgBackRest / WAL-G is warranted.
- Once the media storage decision (local disk vs S3-compatible) is made, does the backup story differ — e.g., does local-disk media get bundled with DB backups while S3-compatible media is left to the object-storage provider, as several surveyed apps do?
- Is any guarantee needed that a DB backup and a media backup represent the same point in time, or is "eventually consistent enough" acceptable, as seems to be the norm among surveyed apps?
- Should `WEBCRAFT_SECRET_KEY` ever be included in the same backup artifact as encrypted secrets stored in Postgres, or must it always be backed up/distributed through a separate channel (per the GitLab/Mastodon pattern)?
- Does WebCraft need a per-Workspace or per-Site export/import feature for moving a tenant between Installs, and if so, at what fidelity (full fidelity vs. GitLab-style lossy export with documented exclusions)?
- Who is the target operator for backup/restore — a technical agency admin running CLI commands, or someone who needs an in-app "Backup now" / "Restore" button? This shapes which of the above options are even viable.
