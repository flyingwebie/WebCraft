# Custom domains + automatic TLS for a self-hosted WebCraft Install

Researched 2026-11-05.

## Summary

For an Install serving `admin.agency.com` plus many client Site domains, the practical self-hosted options are Caddy on-demand TLS (ask/permission endpoint) or Traefik with per-router ACME — both free, both subject to Let's Encrypt's 50-certs/registered-domain/week limit, and both need the agency to run and secure an edge proxy. Cloudflare for SaaS and CDN-host deployment (Pages/Netlify/Bunny) trade self-hosting purity for near-zero TLS ops, at a small per-domain cost (Cloudflare: ~$0.10/hostname/month after a free tier) or a hosting-provider API integration; both still require the client to add a CNAME (and, off-Cloudflare, a TXT) and both push form/webhook traffic back to the Install through CORS or a same-domain proxy. Apex (bare) domains are the recurring pain point everywhere except Caddy/Traefik (which just need an A record) — Cloudflare apex support needs the zone on Cloudflare (or an Enterprise add-on), and CDN hosts generally want `www` as primary with an ALIAS/ANAME workaround for apex.

## Caddy on-demand TLS

Caddy can "dynamically obtain a new certificate during the first TLS handshake that requires it," so Site domains don't need to be listed in config ahead of time — useful when domains belong to clients and aren't known at startup ([Caddy docs, Automatic HTTPS](https://caddyserver.com/docs/automatic-https#on-demand-tls)).

- **Ask endpoint.** On-demand TLS "must be both enabled and restricted to prevent abuse." The restriction mechanism is the `ask` endpoint (now deprecated in favor of a `permission` module, with an HTTP permission module kept as the backwards-compatible implementation of `ask`): for each domain seen in a handshake, Caddy calls out to an HTTP endpoint you run, which must decide whether that domain is allowed to get a certificate — e.g., "query your accounts table to see if a customer has registered that domain" (same doc page; deprecation and `permission` module confirmed in Caddy source via community search, e.g. [Caddy community: Add new domain via API?](https://caddy.community/t/add-new-domain-via-api/14070)). This is exactly the gate WebCraft would use: only issue for domains attached to a live Site.
- **Rate limiting.** "Caddy's internal rate limit is currently 10 attempts per ACME account per 10 seconds," on top of whatever the CA enforces ([Caddy docs, Automatic HTTPS](https://caddyserver.com/docs/automatic-https#on-demand-tls)). A community thread notes Caddy once had separate `interval`/`burst` on-demand rate-limit config but these are now discouraged in favor of relying on the ask/permission gate ([Caddy community search summary](https://pkg.go.dev/github.com/team-swisscenter/caddy-tls-permission-allowlist) — secondary, treat as indicative only).
- **Scale claim.** The docs state businesses use on-demand TLS to serve "tens of thousands of sites" from one Caddy instance at lower cost than wildcard-per-tenant schemes — directly applicable to the 50–500 Site range in the ticket.
- **First-hit latency.** Only the first handshake for a new domain is slow (a few seconds, since it waits on the CA); certs are cached after that and renewed in the background.
- **Implication for WebCraft:** the `ask` endpoint maps naturally onto "does this hostname belong to an active Site in some Workspace in this Install" — a single DB lookup. No outside product needed; this keeps the whole flow inside the Install.

## Traefik + ACME

Traefik's certificate resolvers are configured per-resolver under `certificatesResolvers.<name>.acme`, requiring `email` and `storage` (cert cache file, default `acme.json`) ([Traefik docs, ACME certificate resolvers](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/)).

- **Challenge types:** `httpChallenge` (HTTP-01, needs port 80 reachable, compatible with HTTP→HTTPS redirect), `tlsChallenge` (TLS-ALPN-01, needs port 443 reachable), `dnsChallenge` (DNS-01 via the Lego library, required for wildcards, supports CNAME delegation to a different DNS zone).
- **Dynamic domains, no ask gate.** Domains come from the dynamic routers you define (file provider, Docker labels, etc.) — Traefik reads the `tls.domains.main` value or the `Host()`/`HostSNI()` rule of each router and requests a cert per domain/SAN. Unlike Caddy, there is **no built-in authorization callback**: whatever domain you point a router at gets a certificate request. The gating has to live in whatever process creates/updates the router config (e.g., WebCraft's own control plane only writing a router once a Site's domain is verified).
- **HA caveat:** "Running multiple Traefik instances with Let's Encrypt is not supported" without extra tooling (cert-manager or Traefik Enterprise) — relevant if an Install ever wants more than one edge node for availability.
- **New-domain gap:** a brand-new router may serve Traefik's default (self-signed) cert until Traefik notices and completes issuance — a real but temporary rough edge during onboarding of a new Site domain.

## Cloudflare for SaaS (custom hostnames)

Cloudflare for SaaS lets an agency add client vanity domains ("custom hostnames") to the agency's own Cloudflare zone, with Cloudflare terminating TLS and routing to a "fallback origin" (the Install) by default ([Cloudflare docs, Cloudflare for SaaS overview](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/)).

- **Domain verification flow:** when you create a custom hostname via the API, Cloudflare returns an `ownership_verification` TXT value; the client adds that TXT record at their own DNS provider, the hostname goes active within minutes, and the TXT record can then be removed. Alternatively, an HTTP token can be placed at a `.well-known` path on the client's origin instead of DNS ([Cloudflare docs, Pre-validation methods](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/pre-validation/)). For non-wildcard hostnames, Cloudflare also does an HTTP certificate-validation pass once the hostname points at your target, even if TXT was chosen; a hostname is production-ready only once both hostname status and SSL status show active (per Cloudflare's "common API calls" documentation, surfaced via search).
- **CNAME requirement:** the client points their domain (typically a subdomain, e.g. `app.client.com`) via CNAME at the agency's SaaS target hostname.
- **Apex handling:** apex domains need either the client's zone to also be on Cloudflare (so Cloudflare auto-creates the CNAME-equivalent), or the agency's Enterprise plan's "Apex Proxying" add-on, which supports apex even when the client's DNS provider won't allow CNAME-at-apex ([Cloudflare docs, Cloudflare for SaaS overview](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/)).
- **Pricing (as researched; verify before quoting to clients):** Cloudflare's current published rate is about $0.10 per custom hostname per month after the first 100 are free, with a 50,000-hostname cap on Free/Pro/Business plans and custom Enterprise pricing beyond that (per Cloudflare's plans page and blog, surfaced via search — a commenter on Cloudflare's community notes this rate isn't easy to find in-dashboard, so confirm directly with Cloudflare). At 50–500 Sites this stays inside the free allowance or low tens of dollars/month.
- **TLS issuance:** Cloudflare manages its own CA relationships (Let's Encrypt, Google Trust Services, SSL.com are all named as CAs whose CAA records must be allowed) — the agency never touches an ACME account or rate limit directly.
- **Rate-limit exposure:** none directly on the agency; Cloudflare absorbs CA-side issuance at its own scale.

## Static export to a CDN host (Cloudflare Pages / Netlify / Bunny) via API

This model treats each Site as a build artifact pushed to a CDN platform, with the Install remaining the authoring/admin backend and the published Site becoming static files elsewhere.

- **Cloudflare Pages:** custom domains are managed via a documented REST API — `GET/POST /accounts/{account_id}/pages/projects/{project_name}/domains` to list/add, `DELETE .../domains/{domain_name}` to remove, `PATCH .../domains/{domain_name}` to retry validation ([Cloudflare API reference, Pages domains](https://developers.cloudflare.com/api/operations/pages-domains-add-domain)). An **apex** custom domain requires the apex to be a zone on the *same* Cloudflare account as the Pages project (nameservers pointed at Cloudflare); a **subdomain** only needs a CNAME at the client's existing DNS provider to `<project>.pages.dev` ([Cloudflare docs, Pages custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/)). Adding the domain in Pages *before* creating the CNAME is required, or the domain fails with a 522.
- **Netlify:** domains are added via the dashboard/API first, then DNS is pointed at Netlify — either delegating to Netlify DNS (enables automatic SSL + wildcard certs, and the docs say apex and subdomain configs "perform equally well") or keeping external DNS, where Netlify explicitly recommends making `www` the primary domain because "apex-domain performance is limited by third-party DNS resolution," with ALIAS/CNAME-flattening as the fallback for apex on providers that support it, or a bare A record (`75.2.60.5`) otherwise ([Netlify docs, Custom domains](https://docs.netlify.com/domains-https/custom-domains/)). TLS is automatic; the specific CA isn't named on this page. DNS propagation is quoted at up to 48–72 hours.
- **Bunny (CDN / Pull Zones):** a custom hostname is added to a Pull Zone, pointed via CNAME at the zone's `b-cdn.net` hostname (Cloudflare proxying must be disabled on that CNAME, since a proxied record hides the resolution SSL validation needs); clicking "Verify & Activate SSL" issues a free Let's Encrypt certificate, and if the domain's DNS is hosted on Bunny DNS, Bunny auto-issues/renews a wildcard cert instead ([Bunny docs, Custom hostname](https://bunny.net/docs/cdn/custom-hostname) — accessed via search cache; fetch of the canonical doc URL 404'd during this research, so re-verify the live page before relying on exact UI copy). Bunny's API exposes certificate endpoints for DNS/HTTP validation (`requestExternalDnsCertificate`, `completeExternalDnsCertificate`, `requestExternalHttpCertificate`, `completeExternalHttpCertificate` under `api.bunny.net/pullzone/{id}/`) for issuing a cert before DNS cutover, but no documented single "add hostname to pull zone" endpoint was found in this pass — confirm against `api.bunny.net` reference docs directly. Bunny explicitly warns that requesting certificates too often can trip Let's Encrypt's own rate limits for "up to a week."
- **Forms/webhooks from a CDN-hosted static Site:** none of the three platforms run Install-side code, so a form submit or webhook has to reach the Install by one of:
  1. **Plain `<form>` POST** cross-origin — works with zero CORS headers on the Install, because a native form submission is a "simple" cross-origin request the browser always allows to be *sent*; the Install still needs CSRF defenses since any site can submit to it ([MDN, CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)).
  2. **`fetch`/XHR from client JS** — needs the Install to return `Access-Control-Allow-Origin` (simple requests) or handle an `OPTIONS` preflight (JSON bodies, custom headers) with `Access-Control-Allow-Methods`/`-Headers`; cookie-based auth additionally needs `Access-Control-Allow-Credentials: true` with an explicit (non-wildcard) origin, subject to browser third-party-cookie restrictions (same MDN source).
  3. **A same-domain path proxy** (e.g., a Cloudflare Worker, Netlify Edge Function, or Bunny Edge Script bound to the Site's own custom domain at a path like `/api/*` or `/forms/*`) that forwards to the Install's API — avoids CORS entirely because the browser sees only same-origin requests. Cloudflare's own Worker examples show the basic "respond with another origin's response" proxy shape but no ready-made path-based router ([Cloudflare docs, Worker examples](https://developers.cloudflare.com/workers/examples/respond-with-another-site/)) — WebCraft would need to write this proxy logic itself per platform.

## Let's Encrypt rate limits (apply to Caddy/Traefik self-hosting; not to Cloudflare/CDN-host options)

Per Let's Encrypt's own rate-limits documentation ([Let's Encrypt, Rate Limits](https://letsencrypt.org/docs/rate-limits/)):

- **New orders:** up to 300 per ACME account per 3 hours (refill: 1 every 36 seconds); overridable by request.
- **Duplicate certificates:** up to 50 per *registered domain* (e.g. `agency.com` covers all its subdomains) per 7 days, counted globally across accounts, refilling at 1 every ~202 minutes; overridable for a specific domain/account.
- **Exact identifier set:** up to 5 per 7 days for the exact same set of names on one cert; not overridable.
- **Authorization failures:** 5 per identifier per account per hour, capped at 1,152 consecutive failures before pausing issuance for that identifier.
- **Guidance explicitly for SaaS/hosting providers:** use one ACME account for many customers rather than one per customer; keep fewer identifiers per certificate; use an ARI-enabled ACME client, since ARI-driven renewals are exempt from rate limits; request a higher limit in advance (processing takes a few weeks) if scaling past defaults; test in the staging environment first.
- **Practical read for WebCraft:** since each client Site domain is typically its own registered domain (not a subdomain of `agency.com`), the 50-certs/week limit is **per client domain**, not shared across an agency's whole client base — so 500 Sites is not inherently a problem unless many Sites sit under one registered domain (e.g. many subdomains of one client's domain) or a client repeatedly reissues (restarts/misconfigures) its cert within a week.

## Apex vs www

- **Caddy / Traefik:** apex just needs a plain A/AAAA record — no special handling, since these are ordinary web servers, not a CNAME-based platform.
- **Cloudflare for SaaS:** apex requires the client's own zone to already be on Cloudflare (so Cloudflare can synthesize the equivalent of a CNAME at the apex) or the agency's Enterprise "Apex Proxying" add-on; `www`/subdomains work on every plan with a plain CNAME.
- **Cloudflare Pages:** apex requires the apex to be a Cloudflare-managed zone under the *same account* as the Pages project; subdomains only need a CNAME at any DNS provider.
- **Netlify:** recommends `www` as the primary domain on external DNS because of apex/ALIAS limitations; apex works best through Netlify's own DNS or an ALIAS/ANAME-capable provider.
- **Bunny:** no apex-specific statement found in this pass; CNAME is the documented mechanism, implying the same "apex via ALIAS/ANAME at your DNS provider, or host DNS with Bunny" pattern as the others — re-verify directly if this choice is pursued.

## Preview/draft hosts

Not covered in depth by any single primary source in this pass; reasoning from the mechanisms above:

- **Caddy/Traefik self-hosted:** cheapest to support — a preview/draft host is just another hostname (e.g. `draft--{site-id}.agency.com`) routed by the same on-demand TLS / dynamic-router mechanism already used for production Sites, gated the same way (Caddy's `ask` endpoint, or Traefik's router-creation logic) with no extra cert cost beyond the normal per-domain issuance.
- **Cloudflare for SaaS:** every preview host is itself a custom hostname, so each one separately counts against the per-hostname pricing/limits above — likely only worth it for a shared `*.previews.agency.com` wildcard custom hostname rather than one per draft.
- **CDN hosts (Pages/Netlify):** both platforms already generate a free preview URL per deployment on their own subdomain (`*.pages.dev`, Netlify's deploy-preview URLs), which is the natural fit — a custom domain is unnecessary for previews unless the agency wants branded draft links, in which case it's the same CNAME-per-domain cost as production.

## Implications for WebCraft (options, not decisions)

- Caddy on-demand TLS's `ask`/`permission` endpoint is a close structural match for WebCraft's domain model: "is this hostname attached to an active Site in this Install" is a single query the Install already needs to answer for routing anyway, so Caddy could be bundled as the Install's reference edge proxy with minimal extra moving parts.
- Traefik is a viable alternative if the Install is already Docker/Kubernetes-centric and wants per-Site dynamic routers managed declaratively, but WebCraft's own control plane — not Traefik — would own the authorization step (there is no built-in equivalent to Caddy's ask endpoint).
- Offering Cloudflare for SaaS as an *optional* path (rather than the only path) would let agencies who are already on Cloudflare skip running/securing their own ACME edge entirely, at a small, usage-based cost, in exchange for routing all Site traffic through Cloudflare and losing self-hosted purity for that function.
- The CDN-export path is architecturally the most different: it implies WebCraft Sites can be built as static artifacts, which has implications for inline editing, forms, and any server-rendered personalization — those would all have to be re-routed back to the Install via CORS or a per-platform edge proxy/function, which is extra code to write and maintain per supported CDN host.
- Whichever of Caddy/Traefik is chosen for the self-hosted default, the per-registered-domain Let's Encrypt limit (50/week) means a Site domain that is itself a subdomain of one client's larger domain portfolio (many Sites under one registered domain) is the one scaling case worth flagging to agencies up front; ordinary "each client brings their own apex domain" usage comfortably clears 500 Sites.
- Draft/preview hosts are cheap to add under the self-hosted options (just another on-demand/dynamic domain) but become a recurring per-hostname cost under Cloudflare for SaaS unless consolidated behind a wildcard custom hostname — worth deciding whether previews live on a shared Install subdomain regardless of which TLS strategy a Workspace's production Sites use.
